# ADR-0015 · 决策权归属：可检查、可被效果纠正的技术问题不进 OwnerGate

## 1. 上下文

- 立项讨论中，agent 把三件事列成了「需要 owner 拍板」：编译粒度（每任务现编 vs 按任务类缓存）、
  编译包是否逐个过 OwnerGate、编译器是 agent 还是「规则 + 模型」。
- owner 指出这三件都不该由 owner 定，并给出了判定一件事是否需要 owner 的通用标准（见 §2）。
- 既有口径里 OwnerGate 触发面已是「仅战略性问题」（`agent协作体系.txt:71`）；
  但「战略性」此前没有可操作的判据，导致 agent 把可检查的技术选型也上交。本条补上判据。

## 2. 决策（owner 原话 / 记载）

owner 原话（逐字摘录）：

> 「一个事情本身是否要我来决策，核心就在于看这个东西，它是不是一个由 agent 去执行高确定性的事情。」
>
> 「这些具体的编译策略……它也是一个可以检查的，而且即使前面编译错了，或者有些东西没那么完美，也不重要，
> 因为我们后面会根据各种真实任务的效果……通过各种测评来去看实际的表现。所以这种事情我认为是完全不需要我来决策的。」
>
> 「执行完以后，如果效果不好，那不还得把它改回来吗？所以我觉得这是应该是一个技术问题，
> 而不是一个去由领导拍板，领导去承担决策责任的问题。」

关于编译器形态，owner 给的是**第一感觉，不是拍板**：

> 「一定是一个代码和模型之间结合的一个状态……非常适合决策模型，也就是说不输出文本的那种决策模型……
> 决策模型只需要去输出具体的决策就好了。」
>
> 「这个决策模型，我们是用一些现有的呢还是说我们现在自己去训练一份呢？……要根据实际的效果，
> 根据任务本身的性质，根据整个系统的一种性能……去考虑。」

### 2.1 可操作判据（agent 据原话整理）

一件事**不需要** owner 决策，当且仅当以下三条同时成立：

1. **可检查**：存在结构校验、测试、测评或独立模型验证，能判断做得好不好；
2. **可纠正**：做错了能改回来，且改回的代价不超过它带来的信息（试错是便宜的）；
3. **有反馈**：真实任务的运行结果或测评分数会回流，能驱动下一次修正。

三条任一不成立时，才进 OwnerGate。典型情形：不可逆操作（如删除唯一密钥副本）、
验证手段弱且错误代价高、涉及 owner 偏好或对外承诺（采购、合同、品牌）。

## 3. 后果

**影响**

1. 编译粒度、编译包审批面、编译器形态、决策模型「用现成的还是自训」，都归为**技术问题**，
   由 agent 按测评结果决定和迭代，不再列入 owner 拍板清单。
2. 判据本身写进任务-策略编译包：编译器的 OwnerGate 决策点按 §2.1 三条判定，
   只对「不可逆」或「弱验证 + 高代价」的动作生成人工闸
   （`tools/strategy_compiler/decisions.py` 的 `owner_gate` 决策点）。
3. 既有「待 owner 拍板」项应按本判据复核：属于技术问题的，转为 agent 自决 + 测评验收。
   本 ADR 不批量改写既有 ADR 的状态，复核在各自下一张卡里做。

**后续动作**

- 编译器 v0 用确定性规则做基线；决策模型通过 `Decider` 接口接入，
  与规则基线在同一批真实任务和测评上比较，胜出者上线。
- agent 写拍板清单前先过 §2.1 三条；不满足「需要 owner」的，不得列入。
