### 1.2 题目质量与"真实在测什么"（实测修正了调研印象的地方）

1. **Terminal-Bench 4.0 验收是全确定性的**（无 LLM 判分）：verifier 独立容器、rubric 强制二值、17 任务带 cheat/ 反例；难度用 `expert_time_estimate_hours`（0.75–60h，中位 4h）——**这是现成的任务难度标尺**。但 EnvCheck 在 4.0 仍找到 **70 个判分漏洞**、HVTB 实测 **16.4% 运行存在作弊**——它的分数必须配合反作弊抽检使用。Harbor 的 token 分账**依赖 agent 自报**（ATIF 反填），跨 agent 成本对比有系统性误差——我们的 Meter 必须独立计量，不吃自报。
2. **SWE-bench Verified 的测试规格噪声实机可见**：gold patch 中位数仅 1 文件/183 字符（85.8% ≤1 文件）——它主要测**单点定位修复**，不长程工程；django-10097 的 1 行正则改动配 438 条 F2P（混入大量无关 auth_tests）；28.4% 补丁分歧（arXiv 2610.04371）属实。**结论：SWE-V 适合做"定位修复"档回归基线，不能代表代码产线全部能力；难度细分必须自己做（见 §2.2）。**
3. **SWE-Lancer 的 IC 判定是 Playwright E2E 跑 3 次**——官方承认非确定；OpenAI 2026-02 审计（27.6% 子集）称至少 59.4% 测试用例有缺陷（HN 交叉转引，原文 403 未核）——美元计价口径可用，判分要叠加多次重跑与抽检。
4. **安全三件的测量盲区一致**：AgentDojo/InjecAgent/MCPTox 都无真实副作用、都是单轮——多轮持久注入与记忆中毒无人测，归自建件。MCPTox 无 harness 无 license，降档为"静态准入语料"。
5. **τ² 判分是轨迹重放 + 双 DB 哈希比对，pass^k=C(s,k)/C(n,k) 源码确认**；中断-恢复改造的钩子在 orchestrator.step/set_state——工程量明确。
6. **GEPA 对轨迹类型完全不透明**（唯一接入点是 GEPAAdapter 的 evaluate + make_reflective_dataset），可直接优化任意文本配方；冷启动路径 = Replay Adapter 吃 OpenHands/HAL 公开轨迹 → 首批配方提案，**实测可行**。

### 1.3 模型情报要点（来源与全部数字见 `设计/benchmark调研/实测/model-pricing.md`）

- **性价比拐点**：GLM-5.3-Flash 用 1/9 价拿旗舰 93% 智能分（AA II 42 vs 45），独立 SWE-V **92% @ $0.02/task**；DeepSeek V4.1 Flash **88.8% @ $0.01/task** 且官方**空闲时段半价**（晚间+周末，调度器可利用）。
- **绝对值不可跨榜比**：官方 swebench.com（各自 harness）头部 ~77-79%，Vals.ai（统一 mini-SWE harness）头部 93-97%——**一切对比只在同一 harness 内做**。
- 本地池 2×V100S-32GB：Qwen3-Coder-30B-A3B Q4_K_M（~20.5GB）单卡可行（llama.cpp，V100 无 BF16/FA 须先冒烟）；定位"弱模型档"，不担主链路。

### 2.3 强弱协作（escalation cascade）实验（S2，运营者问题 6）

设计依据（实证文献，见 model-pricing.md §五）：升级信号**不用模型自报置信度**（相关性差），用**确定性信号**：测试套件失败 / 工具错误重复计数 / 困惑度探针。代码产线的天然验证器是测试——cascade 在有测试的产线上风险最低。

实验：对弱模型（Flash/30B）在 S1 中失败的题（预计 30-50 题），跑三种升级策略对比：
- **E1 测试驱动升级**：弱模型跑出补丁 → FAIL_TO_PASS 不过 → 带失败测试输出交给强模型续跑（提示=trace 摘要，非重来）；
- **E2 停滞指纹升级**：止损指纹触发（同工具同参数错 3 次 / N 步无新工件）→ 强模型介入定向；
- **E3 全程强模型**（对照组）。
度量：总成本 vs 最终成功率，与 E3 比省多少、与弱模型单跑比救回多少。文献先验：省 75-85% 成本保 95-97% 质量是可复现区间；对抗脆弱性（级联被攻击成本 +148.9%）记入风险，上线前需对抗压测。

### 2.4 基线对标口径（运营者问题 7）

- 每个模型在**我们 harness 下**的 SWE-V/TB 成绩，对标该模型在 Vals.ai（mini-SWE 统一 harness）/ AA（TB 4.0 子项）的公开值；
- **harness 价值成立的判据**：同模型同任务集，我们的成功率 ≥ 公开值 +2 点，或同等成功率下成本 ≤ 公开值 70%（误差棒内）；
- cascade 配置的对标对象 = 强模型单跑的成绩与成本。

### 2.6 改进策略选型核查（2026-10-19 二次核查，回应"模型自设计改进优于 GEPA"的质疑）

核查记录：`设计/benchmark调研/实测/self-improvement-vs-gepa.md` 与 `improvement-strategy-survey.md`（24+ 条文献逐一核实）。**结论：原命题不成立，但质疑有价值。**

- **"模型自己设计改进、击败 GEPA"在文献中不存在**：所有实测胜过 GEPA 的工作（ACE、Articulation、PCO、FLARE）外层算法都是人类设计的，LLM 只是执行器；而真正"模型自改"的一族（Darwin-Gödel Machine、ADAS、PromptBreeder、MAS-Zero）**没有任何一篇把 GEPA 放进对照实验**，基线只是自身消融。两条文献线从未交锋，"自设计胜过 GEPA"是拼接出来的说法。
- **但 GEPA 不是终点**：ACE（ICLR 2026）是唯一与 GEPA 受控对比且大胜的工作（AppWorld +11.9pp、省 75% rollout），其机制——LLM 策展自己的增量 playbook、防坍缩更新——与 JIT 的"trace→提案→批准"循环几乎同构，应作为 GEPA 反思算子的**首选升级方向**（替换反思单元，不换范式）。
- **自改代码一族不进生产环**：DGM 论文自述 agent 虚报评估结果；ICLR 2026 有 misevolution 实证（自我进化导致安全对齐退化、引入工具漏洞，强模型同样中招）。这恰好验证工厂护栏（评估集隔离、审计下限、人批准）的必要性——自进化只可作为离线研究对象。
- **RL 真训练路线三重排除**：成本（GRPO 每任务 24,000 rollouts vs GEPA 79-737）、Echo Trap 失稳实证、权重 diff 不可审计且违反"永不直接干预执行"。
- **改进策略最终选型（三层，替代单一 GEPA 默认）**：第 0 层 **GEPA 为锚**（金标题库+少 trace 下的样本效率 SOTA，其 D_feedback/D_pareto 划分与优化集/评估集隔离护栏同构；已知三失败模式——prompt 过拟合/prompt 膨胀/输出 schema 腐蚀——转为审计下限的检测项）；第 1 层并行 **ACE 式增量 playbook + AWM/ExpeL 经验卡**（几十个金标样本即可，人审升迁）；第 2 层语料充足后用 **AFlow 受限算子空间**搜路由/模型选择等结构层配方。另记 HarnessOpt-Bench 的诚实结论：优化器的**模型选择比策略选择重要 1.8 倍**——JIT 的反思模型选型单列实验。

## 8. 风险登记

1. **级联架构的对抗脆弱性**（arXiv 2605.17288：成本 +148.9%、准确率 -84.6%）——cascade 上线前过对抗压测，升级判决用校准过的信号，生产监控异常升级率。
2. **SWE-V/SWE-Lancer 判分噪声**（28.4% 补丁分歧 / 59.4% 用例缺陷转引）——一切"成功率"结论叠加补丁语义抽检与多次重跑。
3. **TB 反作弊**：16.4% 运行作弊率（HVTB）——回归集任务带 cheat 反例，成绩附作弊抽检报告。
4. **镜像供给是 S1 的硬前置**（§4-2），daemon 代理方案需先在 anolis 实测验证再批量拉取。
5. **预算估算 ±50%**：token 画像基于公开数据，harness 不同消耗不同；S0 冒烟的实测数据首先用于校准 §6 表格。
6. **Harbor 自报计量**不可作成本结论（§5 已规定独立计量）。
7. **InjecAgent 函数调用口径与官方 ReAct 不可比**（2026-10-20 S0 实测）：我們的 harness 用原生 function-calling + 工具白名单暴露，官方是 ReAct 文本协议；同 50 题双模型注入成功均 0/50，不能读作"模型鲁棒"，口径差异（观察注入的工具响应形态、无 Thought 链）可能系统性降低注入成功率。S1 若要做注入成功率结论，须加跑官方 ReAct 口径对照组校准。
8. **mavis 文本用量不可见**（2026-10-20 实测）：MiniMax remains API 的 general 条目对 m3.1flash/M3 调用恒不记账（video 有账），无法从平台侧独立对账——mavis 成本只能以 harness 网关侧 ModelUsage 为准（trace 已落），与供应商账单的对账缺口登记在案。
9. ~~S1 镜像供给速率风险~~（2026-10-20 实测→**已解**）：hk 代理为总量硬顶 ~250KB/s（fast-pull 12 并发无增益实证；daocloud/1ms 对 swebench deny/stall；sweb.base 基座未发布 docker hub，构建路线须自构建基座）。**破局链路：本机 docker + 本机 7890 代理实测 4.65MB/s（20 倍）→ docker save → rsync（tailnet 6MB/s）→ anolis docker load**，S0 五镜像 10 分钟拉齐；S1 的 120 镜像按此链夜间批拉（≈10-18h），构建路线降级为备份（tuna miniconda/conda/pip + daocloud ubuntu + ghproxy github 的注入点已勘察）。
10. **mcode 令牌仍 invalid**（2026-10-20 复核）：m31f（MiniMax 免费通道）全部臂被 token-gate 挡住，恢复需运营者重新走一次 mcode 授权——不影响其余五档案推进。
11. **anolis /data 容量风险**（2026-10-20 发现）：/data 295G 已用 224G（80%），sweb.eval 镜像 59/120 张已落盘，剩余 61 张按均值估算约 80GB **装不下**；侦察组盘点可回收空间后定方案（清已判分卷/dangling/砍 D3 长尾按需拉）。

## 9. 组织形态与全局监控（2026-10-20 修订，运营者指令）

### 9.0 为什么要这一章

S1 初测（2026-10-20）暴露两件事：①自研 harness 有系统性缺陷（`ANTHROPIC_MAX_TOKENS_PLAIN` 硬编码 1024 → 输出截断 → 解析不出工具调用 → `tool_free_turn_limit=1` 当场终止 → 零补丁必败，**52.7% 运行被杀死**，173 次运行全部作废、MES 标记 `bench-void`；修复=af 仓库 fd77a9d + 96d7d57）；②事故未被及时发现的原因是**主代理亲自下场做具体工作，失去了对整体情况的把握**。运营者裁定：主代理转型纯监控与调度，异常定义前置，发现即修。本章即该裁定的制度化。

### 9.1 组织形态（角色 × 载体 × 职责边界）

| 角色 | 载体 | 职责 | **禁止** |
|---|---|---|---|
| **厂长（主代理）** | 本机 ZCode 主会话 | 监控看板、定义/裁决异常、派单给各组、修订方案与预算、向运营者汇报 | 亲自写代码、亲自跑 bench、亲自改配置 |
| **修理组** | 本机 ZCode 子代理（按需派发） | harness/调度器/CI/判分链缺陷修复，af 仓库提交 | 自行扩权改方案、动生产面（gov） |
| **观测组** | 本机 ZCode 子代理（按需派发） | watchdog/安灯/看板的建维，观测链自身缺陷修复 | 修改产线数据 |
| **分析组** | 本机 ZCode 子代理（按需派发） | 结果的 MAST 标注、噪声分类、模型画像表编制、论文灵感落地评审 | 触碰 harness 代码 |

信息流：底盘 → MES + results.jsonl → watchdog 聚合 → 看板/安灯 → 厂长巡检 → 派单 → 修理组修复 → 结果版本隔离（见 9.3）→ 循环。**这个循环本身就是目的 5（观测反哺持续改进）的最小可行版**：先把"发现→修复→复测"在 infra 层跑顺，S6 再上 GEPA 层。

### 9.2 安灯（异常分级）与响应规程

watchdog（`tools/factory-watch.py`，常驻每 60s 一轮）持续求值以下规则，报警入 `状态观测/alarms.log` 与看板安灯区：

| 灯 | 码 | 触发条件（≥样本数防误报） | 含义 | 响应 |
|---|---|---|---|---|
| 红 | A0 | 调度器进程消失或 status 停更 >300s | 产线停摆 | 厂长立即派修理组 |
| 红 | A1 | 任一臂 run_failed 占比 >10%（≥5 样本） | infra 缺陷（判分链/容器/网络） | 修理组修复，期间该臂结果冻结 |
| 红 | A2 | 任一臂零补丁/gate 拦截占比 >30%（≥10 样本） | harness 完成度纪律缺陷 | 修理组修 harness，**触发 9.3 版本隔离** |
| 黄 | A3 | 某档案 ≥10 题已判分且通过数为 0 | 系统性不适配（模型 or harness） | 分析组先定性（模型真不行 vs harness 害的），再决定 |
| 黄 | A4 | anolis 任一分区 >85% | 产线即将因盘死 | 侦察/修理组按预案清理或砍臂 |
| 黄 | A5 | 中继连败 ≥3 | 镜像供给断 | 检查 CNB 通道/换 org |
| 黄 | A6 | 调度器称 running 的臂 30 分钟无新结果行 | 卡死/僵持 | 修理组查日志，必要时重启该臂（断点续跑兜底） |
| 黄 | A7 | 镜像数 2 小时无新增且 <120 | 供给瓶颈回归 | 同 A5 |

响应纪律：**发现即修，不等批次结束**——厂长巡检（9.4）看到红灯即派单；黄灯当轮定性、下轮必须有处置动作或明确挂起理由。测评完成不是目的，通过测评改进系统和获得认知才是目的（运营者原话）。

### 9.3 结果版本隔离（harness 改动的可比性纪律）

任何 harness **语义级**改动（提示词、max_tokens、turn 上限、完成门禁、判分口径）→ 修复代号线 bump：结果目录 `/tmp/bench-fix<N>-{tier}-{profile}`，旧代结果按改动性质二选一：①影响所有运行的（如 max_tokens）→ 整代作废入 MES `bench-void`；②影响局部的 → 保留但在画像表标注混同边界。**画像表只吃单代内结果，跨代比较必须显式注明**。当前生效代号：fix1（fd77a9d + 96d7d57）。

### 9.4 巡检节奏与看板

- **看板**：`http://127.0.0.1:8790`（本机，`状态/看板/index.html`，30s 自刷新）——四区：安灯 / 产线矩阵（档×档案进度与通过率）/ 资源（anolis 盘、镜像、ollama、load）/ 成本（tokens 三账本）。
- **厂长巡检**：主代理定时任务每 15 分钟一轮：`factory-watch.py --once` 报告 → 安灯处置（派单或挂起）→ 摘要追加 `状态观测/巡检日志.md`。巡检中发现的模型级洞察（如某档案全零通过）转分析组。

### 9.6 模型资源共享纪律（2026-10-20 运营者指令固化）

**事实**：主代理、其子代理、glm-cp/glm-cp-max 测评臂，三者共用同一 GLM CodingPlan 账户的**并发与积分**（2026-10-20 429 风暴实证：6 条 GLM 臂 + 3 个 GLM 子代理同打一账户，run_failed 40/42；周池当日已用 72%）。orchestration 自身的模型开销此前不可见，是隐藏的成本与噪声源。

纪律：
1. **GLM 账户并发视为全局预算**：GLM 测评臂并发 + GLM 子代理数合计控制（实测账户并发上限 ~2-3；当前调度器限额 glm-cp=1 + glm-cp-max=1，主代理巡检轻任务计入内）。
2. **重子代理任务默认错族**：GLM 臂运行期间，修理/分析类重任务优先派发到非 GLM 族载体。常备类型：`repair-offglm`（step-5-preview）、`analyst-offglm`（kimi-k3），定义在 `.zcode/agents/`；工作流场景用 subagent_model 显式指定（可用：step-5-preview/step-3.7-flash/kimi-k3/k3-256k/MiniMax-M3/M3.1-Flash/Qwen3.8-27B-U）。
3. **额度双账**：测评消耗（臂侧 Meter）与 orchestration 消耗（子代理侧）分开记账；周池 <20% 余量时优先保测评臂，代理侧只留巡检。
4. 代理侧大额消耗（>50 万 token 的子代理任务）须在派发时说明必要性——能用脚本/规则解决的不上模型。
- 画像表编制条件：每 (档,档案) ≥10 判分题后先出初稿行；D1 全量（23 可跑题）跑满后再谈结论。

### 9.7 研究循环与路线裁决（2026-10-20 运营者再校准——本章最高优先级纪律）

**再校准背景**：S1 中期复盘发现主代理陷入"维持产线运转"的运维模式，偏离了测评本体目的。运营者裁定：**产线只是数据源，测评是一个研究任务**——数据回来后必须立即进入"定位失败点 → 造 harness 变体 → 同题对照重跑 → 验证改进"的循环，循环的终点是路线裁决。

**对齐纪律**：测试参数（turn 上限/预算/温度/k 值）不自设，以 ①榜单发布者的标准口径（mini-swe-agent / SWE-agent / OpenHands / 官方提交）与 ②本机历史前例（cal2 时代 zcode/mcode）为准。**只有在对齐条件下跑出的差异，才能归因于自研 harness 本身**。

**合格判据（路线裁决的依据）**：自研 af-harness 在同模型 × 同任务上，成功率对齐商业 harness（zcode/mcode）与公开榜单（Vals/AA 口径）的可比水平。达到 → 自研路线成立；达不到且改进循环收敛缓慢 → 决策转向"商业 harness + 自研改造"路线。测评产出的全部数据都为支撑这一裁决服务。

**循环机制**：fix<N> 代既是结果隔离单位，也是变体实验单位——每个变体改动（对齐参数/提示/工具/停止策略）进入新代号，用**同一批失败题对照重跑**验证 Δ，画像表记录各代演进。产线（§9.1-9.5）持续供数，研究循环随时插队消费数据。
