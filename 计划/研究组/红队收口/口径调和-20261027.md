## 二、为什么两处口径不同（机制，亲读工作流脚本）

数据流（脚本 `.zcode/workflow-runs/dwfrun-c19fc663-8777-4e53-9fbc-0fb1ad41c563.mjs`，即产出 final-summary.json 的那次收口循环）：

1. 每波修复按域并行：域修复员（ask#5）上报，`fixes = perDomain.flat()` —— 只收录域修复员的原始上报，W2 的 7 条域外交接项在此以上报时点值 `fixed=false` 入账。
2. 随后汇总员补修（ask#6：合龙域分支 + 补修未闭环项 + 跑九门），**但 ask#6 的返回值未被脚本捕获、没有并回 `fixes`**（`await __host.ask("ask#6", …)` 裸调，结果丢弃）。
3. 之后 `waveRecords` 携 `fixes` 原样写入 `/tmp/af-redteam-final-summary.json`（机读总账）；而波次记录（ask#8）在 ask#6 之后由修复员书写，包含补修闭环后的全貌。

即：**final-summary.json 的 fixed 字段 = 域修复员上报时点的中间态快照；wave2-记录.md = 补修闭环后的终局态。** 账实差（book-keeping lag）源于步骤 2 的返回值丢弃，属脚本记账缺口，不改变终局事实。

同源佐证：JSON 中 7 条的 `how` 文本与记录书中同 7 条「修复（docs 域修复员上报，交接时 fixed=false）」段逐字同源（如 C-10 均含 `graph_unit.rs:852-857`/`pkg/sweng.rs:717-722` 取证）——证明 JSON 的 fixed=false 确是「交接时点」值，且记录书自己就保留了两时点的对照。

## 三、以哪个为准

**以 wave2-记录.md 的终局态为准：W2 real 50 条全部修复闭环（50/50）。** 佐证链：

1. 7 条逐条有终局处置段与载体（§一事实 B），域分支合并提交（`8cbd79b`/`1dc8fc9`/`e312277`/`76ccdd5`/`4ed9c04`）记录称经 `git merge-base --is-ancestor` 亲验在 phase2-redteam-fixes。
2. 全域合龙批九门终跑全绿（证据 `4800a67`）——7 条补修与五域修复同树合验，未闭环不可能过线。
3. 下游合流终裁反向佐证：《红队W3修复合流-终验终裁-20261027.md》——phase2-redteam-fixes（tip `239f16a`，领先 90 commits）合入 phase2 主线（合并提交 `3e2194c`）后九门复跑 exit 0 全绿（证据 `43e8215`）并双远端推送；合流面带着全部 W2 修复收口。

对 final-summary.json 7 条 `fixed=false` 的正确读法：**域外交交时点未闭环的历史快照 + 记账缺口，不表示收口时存在开放缺陷**。该 JSON 作为机读总账，其 W2 `fixed` 字段偏旧；引用该字段时必须附本调和说明（或改引记录书终局态）。其余两波无此问题：机算自归档 final-summary.json，wave1 54/54、wave3 32/32 均 fixed=true。
