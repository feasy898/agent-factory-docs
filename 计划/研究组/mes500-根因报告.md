## 3. 根因结论（分层）

### L1 直接根因（服务端，坐实）：CH 26.7 动态内存硬限额在宿主压力下塌陷
CH 26.7 新增行为：服务端总内存硬限额由后台 memory worker **周期性动态重算** `(常驻内存 + 可用内存) × max_server_memory_usage_to_ram_ratio`（现役 embedded 默认 ratio=0.9、`memory_worker_dynamic_hard_limit=1`）。10-21 15:14-16:28 本机深度内存压力窗口内，限额塌到 **1.77 GiB**，而 CH 自身内存跟踪值停在 **~1.79 GiB**（真实 RSS 仅 ~90 MiB——跟踪值虚高，来自缓存预留/未释放预留；加载配置后 mark_cache 从 embedded 默认 5 GiB 降为 512 MiB，实测跟踪值 1.92→1.27 GiB）。跟踪值 > 限额 → 任何新查询（连 0 字节记账分配）抛 `MEMORY_LIMIT_EXCEEDED`：

```
MEMORY_LIMIT_EXCEEDED  241  7  2026-10-21 16:27:58
(total) memory limit exceeded: would use 1.79 GiB (attempt to allocate chunk of 0.00 B),
current RSS: 89.66 MiB, maximum: 1.77 GiB. Untracked memory across all threads: -6.78 MiB.
```

（system.errors 全文，重启前捕获；7 次全部集中在 10-21，最后一次性 16:27:58。）500 是**服务端拒绝查询**，不是进程死亡、不是连接失败——进程同一 PID 跨两次 500，/ping 在 500 期间仍正常（这也是 ④组 ping 探针全程绿灯的原因）。

### L2 配置根因（坐实）：启动 cwd 错误 → config.xml 静默未加载
10-19 21:09 的启动命令在 af/ 目录下执行，CH 在**当前目录**找 config.xml，找不到就用 embedded config（有明确日志行）。后果链：users.xml（每查询 6GB 限额/网络白名单）、logger（文件日志）、mark_cache 512MiB、内存参数**全部丢失**；embedded 默认还开启动态限额（L1 的触发器）、mark_cache 5GiB（推高跟踪值）；且 query_log/text_log 未启用 → 两次 500 无逐条取证（只剩 system.errors 计数）+ console 日志 10-19 22:29 起莫名停止写入（末行半句，成因未定，无 query_log 可查）。anolis 侧同类安装用 `--config-file` + 正确 cwd 启动（pid 50003 实证），本机是反例。

### L3 容量根因（结构性，挂 D-26）：本机 14.9GiB 内存多租户争抢
现役：总 14.88GiB + swap 20G（当前已用 9G），跑着 zcode 多实例（~2G）、gnome、docker、ollama 等。MES 与产线/桌面争内存是常态而非偶发——10-21 15:23 内核压力簇、10-22 03:55 /ping 失败都是同源表现。单点止损（L1 修复）必要但不充分，统一资源治理归 D-26。

### L4 客户端缺陷（MES 自身，已修）：单次失败即弃 + 静默
① sched.ch_insert 与 bench-mes.py 对 500 无重试，整批事件丢弃（幂等键在，重跑可补，但无触发）；
② sched.finish() 的 bench-mes subprocess `capture_output` 后不看 rc → 7 次 500 中 5 次完全静默（只有 node_event 路径的 2 次留下了日志行）；
③ 失败只记"不致命"，无计数无告警——账本缺事件长期无人知。

### 排除项（有证据）
- **anolis CH 死亡/D-27"重启后无人拉起"**：与本地 500 无因果。本地 500 的服务端异常码/时间戳都在本机 CH 的 system.errors 里，且本机 CH 进程 10-19 21:09 起未重启；anolis 是另一实例（现健康，pid 50003）。
- **CH 进程崩溃/端口占用/磁盘满**：无。同 PID、/ 余 76G、无 OOM 击杀内核记录。
- **/tmp EDQUOT**：晚间事件，CH 数据在 /（非 /tmp），时间上也晚于两次 500。
