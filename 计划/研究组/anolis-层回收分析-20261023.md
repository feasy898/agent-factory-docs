计算（`analyze_layers.py` + `analyze_layers2.py`）：

1. **层归属**：122 对象 × `RootFS.Layers`（diff-id，老→新）→ 255 个去重层、每层 owner 集合；与 `docker image history` 逐步 Size 反转对齐 **122/122 全对齐**（校验层序正确性）。
2. **删集/保留**：保留 = 现场全部对象 − 删集（等价 keep-list-v2 ∪ 在飞 ∪ 悬空 485ab084e7e4 ∪ python:3.12-slim，差集已核对仅此两件池外幸存者）。**在飞容器命中删集 2 张（django-16938、xarray-4094，08:04-08:05 间新起）→ 强制剔除，有效删集 27 张**。
3. **可回收层** = 删集引用 − 受保护层引用 → 42 层（40 单主独占 + 2 删集内共享）。
4. **层尺寸口径判定**（本单关键修正）：
   - `image history` Size 是**压缩口径**：全池去重层和 135.4GB vs df Images 盘上 205.1GB（池级比 1.514）；且**逐层压缩比 1.3×~6.0× 不齐**（matplotlib env 层 ~6×，基座 ~1.43×）→ 均匀缩放不可用，旧 layer-est.json（est 27.7GB"未压缩口径"）系口径误标，作废；
   - **盘上权威口径 = `docker system df -v` UNIQUE SIZE**（daemon 层库实占，按镜像给单主独占层和）；
   - 删集内共享层（2 层，仅 django-15629/16263 一对）盘上尺寸 = SHARED(4.125) − 公共基座(2.176，逐层核验与 django-10097 同 7 层基座) = **1.95GB**。
5. **交叉校验**：① df -v UNIQUE/SHARED 与本文层 owner 图**集合级一致**（matplotlib-25122：3 独占层=UNIQUE 8.597GB ✓；matplotlib-25775：0 独占层=UNIQUE≈0 ✓）；② Σ UNIQUE(27 张)=28.41GB + 内共享 1.95 = 30.36GB，与压缩口径 23.3GB × 有效比 1.30 相符；③ df 摘要 RECLAIMABLE 140.7GB 是"无容器引用"口径，与本问题无关（回答了为何 `docker system df` 口径不可用）。

## 4. 结论建议（三选一）：**B 层感知定点清理**

- **B（推荐）层感知定点清理**：按 §3 排序执行 `rmi`，走 img-gc.py 既有 ps 三重避让（本次 2 张候选被在飞占用即为实证）。两档：

  - **B-top10**：仅删前 10 张（含 15629+16263 成对），回收 ~27.1GB，churn 仅 37%，后续按需扩。

## 5. img-gc.py「按镜像删」→「层感知」升级估计

- 现状：删集=白名单−三源保留（tag 粒度），plan 无回收量预估、apply 无排序；RECLAIMABLE/naive 均会严重误导（本单实测 141.6 vs 30.4）。
- 升级：① plan 增补 `docker system df -v` + `image inspect` 层归属（本单 `analyze_layers2.py` ~120 行可直接移植；df -v 解析注意 CREATED 为多词列，取行尾倒数 4 列）；② apply 按盘上贡献降序删或达目标 GB 即停；③ evidence JSONL 增 per-image UNIQUE 与预估/df 实收对账行。
- 工作量：移植适配 ~0.5 天 + 现池 dry-run 对数回归 ~0.5 天 ≈ **1 天**。
- 收益：plan 预估可信（误差从 4.7× → ±2%）；支持 top-N 目标驱动删除；每次 GC 可审计"删了 N 张实收 X GB"。
