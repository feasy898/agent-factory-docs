## 1. 查证证据（三源）

### 1.1 源一 · 提案 B §5 INV-1 原文——约束对象是「LLM-bound task 节点」

`DSL-语法提案-B.md:1347`（§5「INV-1 上下文完整性」，节标题 :1345）：

> **规则**：LLM-bound task 节点的上下文 = 且仅 = 其 `context.sections` 声明的来源（无隐式注入）；
> 每个 section 的来源可解析（……`edge.port` ∈ 本节点入边端口集……）；每段 `quota_tokens` 为正；
> **每个入边端口恰被一个 section 引用**；LLM-bound 节点不得声明 `reads`。

E2304 对应子句「每个入边端口恰被一个 section 引用」位于同一句内，**句子主语自始至终是
「LLM-bound task 节点」**——后续分句（来源可解析/配额为正/端口恰一引用/禁 reads）全部继承该
主语，无一另行扩大。两处旁证：

- `DSL-语法提案-B.md:113`（§1 节点表 `context` 行）：「`{sections: [...]}`——**仅 LLM-bound
  task 可用**（INV-1 判定对象）」——INV-1 判定对象被显式钉死为 LLM-bound task。
- `DSL-语法提案-B.md:101`（§1）：「**读权限在消费者侧声明**……agent 类节点经
  `context.sections`（INV-1），**其余节点经 `reads[]`**」——非 agent 节点的读侧声明面是
  reads[]，sections 根本不是为其设计的审计面。

## 2. 三岔判定

- **①成立（部分）**：违例 2/3 的节点非 LLM-bound，仅因「带 context」落入 E2304——按 §5 原文
  不应判。属实现过宽 → af-dsl 缺陷修复。
- **②成立（部分）**：违例 1/4 的节点是 LLM-bound（uses.model 在场），§5 对其明文要求入边端口
  恰一 section 引用；且 LLM 节点在现行语法下**没有第二条数据入口**（E2303 禁 reads、入边必经
  sections）——roster（激活名单，intake 播种提示的素材）与 brief（gather 汇出的收束工作简报，
  :353 边）语义上就是 prompt 上下文，是草稿漏写，不是语法缺口。
- **③不成立**：非 LLM 验证单元的声明式数据通道**已经存在**——`consumes: {patch: progress_report}`
  类型契约（E2201 两端核对）+ check 内建 `passed` 端口（提案 §1 kind×uses 判别表）。verify/
  fail_scan 误报消除后，其 patch 载荷经 consumes 正常流动，无须任何新语法。**无需缺层裁决。**
