## 3. 三缺陷修法与判定式

### ① log_parsed 零状态语义（R4）

- **v1 缺陷**：`log_parsed` 只查 Start/End Test Output 标记齐在——pytest 从未收集（collection/import
  崩溃）的日志同样 markers 齐在 → 记 true，与"真跑过但失败"同貌（8 例实证，2 例造成生产 T→F）。
- **v2 判定式**（可复算：任一持日志者按三项复现）：
  ```
  bad_codes（>>>> Patch Apply Failed / Reset Failed / Tests Errored / Tests Timed Out）在场 → eval_error
  否则标记缺失 → no_markers
  否则 swebench 官方 get_logs_eval 的 status_map 为空（含整日志回退为空）→ zero_state
  否则 → parsed
  log_parsed = (log_state == "parsed")
  ```
  输出新增 `log_state` / `tests_status_parsed`（解析出的测试状态数，零状态=0）/ `log_markers` / `bad_codes`。
  `resolved` 在零状态仍为 false（日志确实未证明解决），但 verdict=zero_state 与 not_resolved 明确可分——
  聚合/复核据此把"测试未运行型假阴性候选"从"真失败"中剥出（R4 修改要求 1 的"或新增字段"支线，
  取更保守的不翻转 resolved、只换证据标记）。
- **正反例**（selftest）：零状态三形态——0 tests（collected 0 items/no tests ran）、标记间空段
  （整日志回退为空）、截断日志（Start 无 End）→ zero_state×2 / no_markers×2；反例=真跑过日志 →
  parsed 不误伤；同零状态日志 v1 复现 log_parsed=true（缺陷复现钉扎）。

### ② judge hermeticity（R5）

- **v1 缺陷**：`make_test_spec` 每判实发 live HTTP（raw.githubusercontent.com 拉 environment.yml/
  requirements），网络不可达即 Traceback 崩溃、judge.json 落空、reward=null 无归因（49 键实证）。
  **本单回放期间再次实崩一次**（14:3x v1 对 flask-5014 清洁日志判分 ConnectionReset 崩掉，
  同输入 v2 暖缓存后离线判出同值 resolved=true——见 §5.4）。
- **v2 修法**：判分期装 `HermeticGuard`——`requests.get` 改走本地离线缓存
  （默认 `~/.cache/swev-judge-v2`，`SWEV_JUDGE_V2_CACHE` 可改；缓存含 404，env-yml 老实例 404
  合成回退行为与 v1 一致）；缓存未命中即拒（**外呼失败即判失败并留痕**：verdict=
  hermeticity_blocked、resolved=null、blocked_urls 列明被拒 URL、stderr 留痕）；
  `socket.connect`/`getaddrinfo` 设绊线，记录并拒绝一切非回呼连接/DNS。显式放行口子
  `SWEV_JUDGE_V2_ALLOW_LIVE=1`（仅缓存预热），此时每个实呼 URL 记入输出 `live_http`（hermetic=false）。
  判分只用 spec 的 instance_id/测试清单/repo（get_eval_report 不读 env/requirements 内容），
  故缓存化不改变判定值——与 v1 env-yml 回退同款原则。
- **正反例**（selftest）：冷缓存判分 → hermeticity_blocked + blocked_urls 含 raw.githubusercontent.com；
  假域（`judge-hermeticity-probe.invalid`）与本地 socket 探针（100.64.0.7:22）与 DNS 均被拒且留痕；
  缓存命中零外呼；暖缓存后同输入离线判出与 v1 同值（hermetic=true）。

### ③ diff 文本合法性（R7）

- **v1 缺陷**：`capture_diff` 把 ssh 取证失败文本（63 字节 CRLF，sha256 f5906672…，全库恰 3 个）
  当 agent.diff 落盘；判分链不校验 diff 内容——错误文本一路当补丁放行，与聚合"文件存在即可判"
  口径合谋造成假阳性（3 run 归"可判"、gate=ok 错配 1 例）。
- **v2 判定式**：非空 diff 须含 `diff --git`，或纯 unified diff（`--- `/`+++ ` 成对）；
  否则 verdict=invalid_diff、resolved=null、diff_valid=false + diff_reject_reason
  （ssh_error_text/docker_error_text/git_error_text/no_patch_header…），**拒判且零网络**
  （不构建 spec）。空补丁（0 字节）不拒判——照常判日志（C6 口径不变），仅标 diff_valid=false+empty。
- **正反例**（selftest + 回放）：R7 实证残片原文（63B，sha256 与裁决锚点逐位一致）与 docker
  错误文本 → invalid_diff；反例=真补丁（diff --git / 纯 unified）照常判定；
  反事实对（§5.3）：v1 对"好日志×ssh 残片"仍判 resolved=true——证明 v1 判定与 diff 内容完全无关的
  假阳性面，v2 明确拒判。

## 8. 局限与遗留（如实记账）

1. v2 的 diff 校验是**判分层纵深防御**：清洁管线里 poc 的 apply 闸在判分前已拦垃圾 diff
   （sphinx-8120 落 judge_failed 行），判分层拒判的价值在于给聚合层显式"不可判"信号、
   杜绝"文件存在即可判"口径（R7 修改要求 1 的消费端修订 truth-aggregate 仍待派单）。
2. R5 的 49 个历史 null 键**未做追溯重归因**（其 eval.log 多在，可用 v2 重判补归因——属 D-33/复核线）。
3. eval_error 分支全库 0 实例（仅合成日志测试覆盖）；若未来出现 bad-code 日志，v1 记
   log_parsed=true（标记齐在时）而 v2 记 false——此差异形态已在 docstring 契约声明。
4. 缓存目录默认落在 `~/.cache/swev-judge-v2`（非 /tmp，规避分流规则）；缓存无 TTL，
   requirements/env-yml 按 commit 寻址天然不变，无需失效机制。
5. 本单零容器、零写入既有 run 目录（回放/普查全部只读）；网络外呼仅发生在缓存预热
   （显式放行并留痕）与 v1 对判（v1 自身行为）。
