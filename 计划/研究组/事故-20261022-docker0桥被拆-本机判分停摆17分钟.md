1. **apparmor `profile=zcode` 的来源**：第二 dockerd 启动时对 `docker-default` profile 做 replace，其 profile 标签为 `zcode`（本机 ZCode 运行时装的 profile）——所以"profile=zcode"不是神秘外部来源，**就是那个测试 dockerd 自己**；
2. **动作与任务书逐条对应**：D-30 单的任务内容是"修本机 docker 拉取通道（drop-in 代理指向死端点 127.0.0.1:7890）"，`proxy.conf` 改写 + 起隔离 data-root 的测试 dockerd 验证新配置，是该任务的自然执行序列。

## 三、机理（为什么"独立 data-root + --bridge=none"仍会拆掉真桥）

- dockerd 的网桥以**名字**管理：默认桥名为 `docker0`，与 data-root / socket 无关；
- 第二个 dockerd 启动时会按名接管/重建 `docker0`（`--bridge=none` 只表示"不创建新桥"，**不等于"不碰同名桥"**），真 dockerd 侧的 `docker0` 随之消失；
- 真 dockerd **未重启**，因此它没有机会重建桥；宿主的 bridge/NAT 与容器网络随之不可用 → 本机 clean 判分全停（判分容器需要容器内出网/回环桥接）；
- 第二实例退出后，`docker0` 无人生成 —— 故障持续到人工重建为止（17 分钟）。

## 四、我的两处判断失误（复盘用）

1. **派单时缺少"破坏性验证"的禁令**：任务书写了"改配置需 restart docker 的，先确认本机无在跑的判分容器"，但**没有禁止在真 dockerd 宿主上启动第二 dockerd**，也没要求"验证 dockerd 配置"必须走网络隔离手段（独立 netns 的 dockerd / 独立 network namespace / 只读核对 + 干跑）。子代理选择"起第二实例验证"在工程上是合理推断，**责任在派单未设边界**。
2. **低估了"同名桥"这一跨实例耦合**：我以为 `--bridge=none` 即隔离；实际 dockerd 按名管理网桥，这是 Docker 的经典陷阱。**任何在真 dockerd 宿主上起第二 dockerd 的动作都可能拆桥**，与 data-root 是否独立无关。

## 五、防复发护栏建议（供后续"底座韧性/基建体系"建设取用）

| # | 护栏 | 落地形态 | 优先级 |
|---|---|---|---|
| G1 | **禁止在真 dockerd 宿主上启动第二 dockerd** | 工厂纪律条目 + 检查单；确需验证 dockerd 配置时，只允许「只读核对 systemd 环境 + 干跑命令」或「独立 netns 内验证」 | 高（即时生效） |
| G2 | **docker0 存在性/状态纳入 watchdog 判活** | factory-watch / keepalive 增加桥判活项（`ip link show docker0` + `inet 172.17.0.1/16` + 容器网络探针），桥缺失即告警并给出**重建命令**（幂等、判据齐全） | 高（把 17 分钟压到秒级） |
| G3 | **桥重建动作预置为幂等脚本** | 工具层 `tools/net-bridge-guard.sh`：核验 daemon.json bip / NAT 链 / ip_forward → 缺失才 `ip link add` → 验证容器出网；被 watchdog 与人工共用 | 高 |

## 七、教训摘要（一句话版）

**在单宿主多容器判分面上，"起第二个 dockerd 做验证"这种看似隔离的动作，实际会拆掉真桥；破坏性宿主操作的授权边界必须写在派单里，而不是指望子代理自觉避开。**
