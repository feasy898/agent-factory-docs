## ① 核心机制

CAMEL 要解决的是：单靠一段任务提示让 LLM 直接求解复杂任务时，缺少稳定的行为/格式先验，协作质量与可靠性都不可控。其核心执行模型是"离线生成 + 在线对话"两段式：先用 Inception Prompt（元提示）把原始任务描述转写为两份角色描述——每份含角色名、Profile 与一段 Chat Example——并把任务提示改写成"任务 + 助手角色 + 用户角色"三段式；再由扮演这两个角色的代理进入交替对话循环，用户角色方先发、助手角色方应答，每轮把新消息追加进对话历史，直至用户角色方判定任务完成，或触及 token / 轮次上限。核心命题是：显式的角色描述（画像 + 示例对话）本身就是可复用的"行为约束与格式先验"，使双代理协作比"纯任务提示"更可靠、冗余更低。

## ② 组件清单

| 组件 | 类型 | 职责 |
|---|---|---|
| Inception Prompt（元提示） | 初始化模板 | 给定任务描述，生成双方角色描述并改写任务提示 |
| Assistant Role Agent | 节点/代理 | 扮演助手角色，依据自身人设与对话历史给出解答 |
| User Role Agent | 节点/代理 | 扮演需求方角色，提出要求、澄清、给出完成信号 |
| Role Description | 静态提示工件 | 角色名 + Profile + Chat Example，常驻 system message |
| Task Prompt（改写后任务） | 任务工件 | "任务描述 + 助手角色 + 用户角色"三段式，双方共享 |
| Chat Example | 少样本工件 | 示范期望的问答格式与协作风格（双份，各存于各自人设中） |
| Message History | 短期记忆 | 每方一份消息列表，各自追加、互相可见对方发言 |
| Communication Channel | 通信 | 交替消息边；用户方先发，非对称启动 |
| Completion Judge | 终止判据 | 由用户代理判断目标是否达成并发出结束语 |
| Token / Turn Budget | 预算 | 单次回复 max_tokens 与总轮数上限 |
| Agent Society / Role-Playing Web | 拓扑扩展 | 运行时可扩展参与方角色（论文扩展部分） |

## ③ 数据与上下文流

1. **生成期**：任务描述 → Inception Prompt 单次调用 → 两份 Role Description + 改写后的 Task Prompt。
2. **装配期**：每方 system message = 角色提示 + 任务提示（Chat Example 内嵌在角色描述中）；Chat Example 随会话常驻，不随轮次衰减。
3. **对话期**：当前发言方读取 system message + 完整对话历史（含对方最新一条），生成一条消息并追加进 transcript；双方各自维护一份同源 history。
4. **状态归属**：角色描述与任务提示为只读静态工件，会话内不变；对话历史为节点私有运行态。
5. **可见性**：双方均见任务与各自角色描述；对方角色描述是否同时可见，论文未明确（存疑）。
6. **交接物**：除消息本身外无结构化工件交接（不同于 MetaGPT 的文档式交接），最终产物（代码、方案）沉淀在对话内容中，是否单独抽取存疑。

## ④ 失败处理与停止条件

1. **语义早停**：用户代理判定任务达成并发出结束语 → 立即停止。
2. **预算停**：单次响应 max_tokens 或总轮数耗尽 → 强制截断，无降级方案描述。
3. **人设质量不合格**：inception 产出的画像与任务不匹配或两角色重叠 → 论文依赖人工筛选/重新生成，是否自动重试存疑。
4. **对话跑偏/重复**：仅由角色描述与 Chat Example 提供软约束，无自省检测与修复模块。
5. **角色目标冲突**：靠角色分工隐式消解，无显式仲裁机制。
6. **模型/API 故障**：论文未描述工程级重试与降级策略（实现层通常重试，存疑）。

## ⑤ 预算与评估方式

**预算**：交替双代理使每轮产生 2 次 LLM 调用，成本约为单代理的 2 倍；控制手段为 per-node max_tokens、最大轮数上限、角色描述压缩上下文、两侧代理可绑定同一底座模型。论文主张角色描述使每轮消息更短、所需轮次更少（communication efficiency）。

**评估**：以 GPT-4 为主干模型（是否以 GPT-3.5-turbo 做对照存疑）；以"社会性分析"三维度衡量——cooperation（合作性）、communication efficiency（沟通效率）、role-playing web（参与方可扩展性）；消融对比为"完整 Inception Prompt" vs "仅任务描述的单代理" vs "仅给角色名、无人设画像"；任务场景以软件开发/代码生成等协作为主，配人工评估对话质量与最终方案质量。是否使用公开 benchmark（如 SWE-bench）存疑，倾向以案例研究 + 人工/辅助评分为主。

## ⑥ DSL 表达点清单

**(a) 可映射为"标准拓扑 + 组件"的机制**

- 双角色协作 = 双节点固定拓扑 + 交替消息边（assistant↔user）。
- 角色扮演人设 = 节点级 system prompt / persona 槽（Role Description）。
- Inception Prompt = 图前"初始化/编译阶段"的一次性提示生成节点，产出物作为变量注入下游节点。
- 改写后的任务提示 = 全局任务上下文变量，注入全部节点。
- Chat Example = 节点级 few-shot 示例槽。
- 对话历史 = 节点私有 message state，逐轮自动注入。
- 用户方先发 + 交替发言权 = 拓扑起始节点 + 轮次调度参数。
- 终止 = 语义完成判定 ∧/∨ 轮次/token 上限的组合条件。
- 每角色独立模型绑定 = 节点级 model 绑定；共享任务 = 全局变量/共享 memory scope。

**(b) 预计需要 DSL 逃逸舱的机制**

1. **Inception 运行时生成人设**：角色描述内容不可静态声明，只能声明"生成并注入自由文本工件"——需运行时文本工件逃逸舱。
2. **语义化完成判定**："任务已达成"是 LLM 语义判断而非字段匹配，DSL 若只有字符串/结构化匹配则无法表达，需 evaluator/predicate 逃逸舱。
3. **Role-playing web 动态增删参与方**：参与方集合与边在运行时变化，属于图结构运行时改写，逃逸舱。
4. **非对称发言权转交**：若 DSL轮次控制仅支持对称轮转，需"起始方/发言权"逃逸舱或扩展参数。
5. **多轮 Chat Example**：若示例槽仅支持单轮问答，需扩展或以自由文本注入逃逸舱。
6. **隐式协作风格约束**：角色描述中"如何配合"的软约束无声明式对应物，仅由提示语义承载。
7. **每轮双次调用的成本记账**：若无 per-node 计费/预算钩子，需额外记账逃逸舱。
