## ① 核心机制

Reflexion 解决的是"语言模型在试错中不会从失败中学习"的问题：标准 ReAct 式循环把每次试验的轨迹丢回上下文，但模型没有把经验固化为可跨回合复用的状态，因此在同一个任务上的重复错误无法被系统性减少。论文的核心主张是把"反思（Reflection）"显式化为一次额外的 LLM 调用，让模型用**自然语言**写下对刚才那次失败的诊断与可操作改进，再把这条语言化的反思存入一个按任务划分的**情景记忆 Buffer（Episodic Memory）**。执行模型因此是一个**双层循环**：外层是"Actor（策略/执行）"在环境里跑一条完整轨迹（Thought→Action→Observation 的 ReAct 链），内层是"Evaluator（打分/判定成败）"对轨迹做二元或启发式判定，然后"Reflector（自我反思）"在看到轨迹+打分后生成一段文字反思；这段文字不是塞回当前上下文当提示，而是作为一条新的经验记录写入 Buffer。下一次尝试同一任务时，Actor 在**构造初始上下文时**从 Buffer 里检索与当前任务相似的历史反思（通常 1~2 条），拼进 prompt 的开头，作为"你上次是怎么失败的、这次该怎么改"的先验。也就是说，Reflexion 的学习不更新任何模型权重，它是一次**上下文级的自我改进**：跨回合的持久状态由外部记忆承载，而不是由参数承载——这一点是它与 Reflexion 之外大量"自我改进 agent"工作的分水岭，也是它最容易被 Agent DSL 误译成"多轮对话"的地方。

## ② 组件清单

| 组件 | 类型 | 职责 |
|---|---|---|
| Actor / Policy | 角色（LLM） | 接收任务+（可选）检索到的反思，在环境中生成 Thought→Action 序列，是 RefLexion 循环中实际推进任务的执行者 |
| Environment / Task | 外部环境 | 提供 Observation（工具返回、编译/运行结果、最终答案），终止条件由环境/任务定义（pass@k、单元测试）给出 |
| Tools | 工具集 | 被 Actor 以 Action 形式调用的具体能力（代码执行、搜索、API），是轨迹中的 Observation 来源 |
| Evaluator | 角色（LLM 或函数） | 对整条轨迹做成功/失败判定与打分，供 Reflector 消费；可以是二元信号（编译通过/测试通过）、Heuristic 或 LLM-as-judge |
| Reflector | 角色（LLM） | 输入=轨迹+打分+（可选）参考信号，输出=一段自然语言反思（诊断+下次策略），是"语言化自我反思"的载体 |
| Episodic Memory Buffer | 记忆 | 按任务维度存储历史反思文本；跨尝试、跨回合持久化的唯一学习载体 |
| Reflection Retrieval | 记忆检索 | 在新尝试开始时按任务相似度/关键词从 Buffer 取出 top-k（论文中约 1~2 条）反思 |
| Trajectory / Scratchpad | 状态（短期） | 当前尝试的 Thought-Action-Observation 全序列，存在于上下文窗口中，任务结束即丢弃（不进入长期记忆） |
| Prompt Assembler | 状态（组装逻辑） | 决定"任务描述 + 检索到的反思 + 工具/环境说明 + 当前轨迹"的拼接顺序与插入位置 |
| Controller / Loop Driver | 运行时编排 | 驱动 Actor→Environment→Evaluator→Reflector→Memory 的多阶段流转与终止判定 |

## ③ 数据与上下文流

1. **回合开始**：Controller 拿到任务实例，从 Buffer 中用检索（按任务相似度，通常是 embedding 或关键词匹配）取出 top-k 条历史反思。
2. **上下文构造**：Prompt Assembler 组装 Actor 的初始 prompt，典型顺序为 `反思（若有，来自 Buffer）→ 任务描述 → 环境/工具说明 → 输出格式约束`。反思置于任务描述之前或之后在论文变体中有差异，但稳定事实是：**反思来自外部 Buffer，不来自当前轨迹自身**。
3. **执行阶段**：Actor 在循环中交替产出 Action 与接收 Observation，完整轨迹持续留在上下文窗口内（in-context scratchpad），供后续步骤条件化，也供之后交给 Evaluator。
4. **轨迹结束**：环境判定终止（任务完成 / 达到步数上限 / 报错），整条轨迹连同终止原因交给 Evaluator。
5. **评估阶段**：Evaluator 只看轨迹（+ 少量参考信号），输出成功/失败及信号强度；评估结果**不直接进入 Actor 的下一次提示**。
6. **反思阶段**：Reflector 读取轨迹+评估结果，生成 1 段自然语言反思（论文示例包含"诊断"与"改进方向"两部分）。这一步与 Actor 是**不同的调用**，反思质量不受 Actor 自身生成风格直接约束。
7. **写入记忆**：Controller 把反思文本作为一条记录写入 Buffer，键为任务标识（论文中通常按任务/实例分组）。Buffer 中的条目是**累积式**的，多次失败会产生多条。
8. **可见性**：Buffer 条目对**同任务的下一次尝试**可见；对不同任务不可见（除非检索命中）。轨迹本身在回合结束后不再可见；反思是轨迹的"压缩产物"，是被保留的那部分。

## ④ 失败处理与停止条件

- **动作级失败**：Actor 产生的 Action 无效/环境报错，Observation 中回传错误信息，Actor 在同一上下文内继续下一轮 Thought-Action——不重置轨迹，不回退到任务开头。
- **执行错误纠正**：论文中明确区分了"语法/执行错误"由环境直接反馈（compile error、runtime error）纠正，**不做反思存储**；反思只针对**任务层面的失败**（答错、策略无效）。这是 Reflexion 相对纯 ReAct 的关键区分：反思不是每次错误都触发。
- **自省式修复**：任务失败时由 Reflector 生成改进策略，下一次尝试以该策略为条件重新开始整个任务（不是局部重试，是整条轨迹重来）。
- **停止条件（轨迹内）**：环境返回 done（任务完成/通过测试）、达到最大步数上限、或 Actor 显式给出终止动作。
- **停止条件（反思触发）**：仅当 Evaluator 判定任务失败（或判定虽成功但质量不足、需改进）时触发 Reflector；成功回合通常不产生反思条目（这一判断依据不同实现略有出入，部分变体在"成功但可更优"时也写入）。
- **反思写入失败**：反思为空或格式不可解析时，通常跳过写入 Buffer，不中断流程（论文未详细规定，属实现细节，**存疑**）。
- **记忆膨胀**：Buffer 无显式上限，随尝试次数线性增长，通过检索时只取 top-k 来控制上下文开销。

## ⑤ 预算与评估方式

- **上下文预算控制**：单次尝试的上下文主要是任务描述+工具说明+当前轨迹（轨迹随步数线性增长）；反思条目作为**额外**注入，量级为 top-k 条短文本（论文量级为几百 token 级）。Buffer 本身无存储上限，是成本增长的主要风险点。
- **计算预算**：Reflexion 相对 ReAct 的额外成本 = 额外一次（或多次）Reflector 调用 + 每次重试时的一次完整轨迹重跑。论文中"actor 次数"是受限的（每个任务有限次尝试，通常 ≤ 3~4 次量级），因此额外成本是**乘性**而非无限循环。
- **基准**：论文主要在两类任务上评估——(a) **HumanEval / MBPP 类代码生成**（用单元测试作为二元 Evaluator，指标 pass@k / pass@1）；(b) **AlfWorld / HotPotQA / WebShop 等决策与问答环境**（用环境成功信号或答案匹配作为 Evaluator）。
- **消融**：论文的关键消融是 **去掉反思（Reflexion without reflection / 仅 Actor 记忆）**、**去掉 Evaluator**、**去掉 Buffer 的检索（用最新一条 vs. top-k 相似条）**、**去掉语言化反思改用标量分数反馈**。结果显示：反思文本本身比简单分数反馈更有效；带相似性检索的 Buffer 优于简单队列（这是滑窗/相似检索机制的直接证据）；Actor-only + 无反思时性能接近朴素 ReAct，几乎无跨尝试提升。
- **敏感性**：论文还分析了 Buffer 大小与 top-k 的影响。

## ⑥ DSL 表达点清单

**(a) 可映射为「标准拓扑+组件」的机制**

1. **主执行环 = Actor 单节点循环（ReAct 拓扑）**：Thought→Action→Observation 的图内自循环，可直接用"单节点 + 循环边 + 工具调用边"表达，无需逃逸。
2. **工具调用边 = Environment/Tools 组件**：Action 作为工具调用，Observation 作为返回值回灌同一节点，属标准 tool-call 边。
3. **Evaluator = 显式评估节点 + 条件边**：独立于 Actor 的第二个节点，接收轨迹与信号，输出判定分数/标签，用条件边决定"是否进入 Reflector"。
4. **Reflector = 显式反思节点（LLM 角色 + 独立 prompt 模板）**：单独的 LLM 组件节点，输入=轨迹+评估结果，输出=自由文本。
5. **Episodic Memory Buffer = 记忆组件（store + retrieve）**：记忆写入点（Reflector 之后）与检索点（新尝试上下文装配之前）都是拓扑上可静态声明的边；检索 top-k 与相似度度量属组件参数。
6. **Prompt Assembler / 上下文注入 = 可静态声明的上下文注入边**：即"在节点 N 的 prompt 组装中包含记忆组件 M 的检索结果"，这是 DSL 常见的 memory-injection 边。
7. **整条轨迹可见性 = 状态作用域声明**：trajectory 状态的作用域=单次尝试（任务开始写入、结束清空），reflection 状态的作用域=跨尝试（Buffer 持久）——可用状态生命周期/作用域声明表达。
8. **角色划分 = 多角色节点**：Actor / Evaluator / Reflector 三个不同 system prompt + 不同模型配置的节点。
9. **重试 = 外层重启边**：失败时以"重置轨迹 + 注入新反思"重启 Actor 节点，可表达为"带记忆条件的重启/多尝试（best-of-N 顺序尝试）"拓扑。

**(b) 预计需要 DSL 逃逸舱的机制**

1. **运行时动态决定"是否写记忆/写什么"**：写入触发条件依赖 Evaluator 的运行时输出而非静态拓扑——需要"条件写入记忆"逃逸舱（条件边可以近似，但"反思为空则跳过"这类空值守卫在静态声明下难表达）。
2. **相似度检索 + top-k 选择**：记忆条目的选取依赖运行时 embedding 相似度排序，不是静态连边可表达的固定依赖；若 DSL 不支持向量检索/排序，需要逃逸舱。
3. **反思文本的运行时内容影响下一步 prompt 长度与顺序**：上下文拼装的 token 预算分配是运行时动态的（任务描述与反思的相对占比、截断策略），静态 prompt 模板难以完全表达，需要 escape hatch 或运行时上下文钩子。
4. **多尝试间的"隐式策略共享"**：反思事实上承担了跨尝试的参数级策略记忆角色，但机制上仍落在 memory 组件；若 DSL 把 memory 限定为"静态声明的固定节点注入"，则"由失败驱动的策略更新循环"整体需要逃逸。
5. **Buffer 的无界累积与检索成本**：存储增长、淘汰策略、检索延迟属运行时行为，静态拓扑不表达。
6. **Evaluator 的异质性**：论文允许二元信号、启发式、LLM-as-judge 三种 Evaluator 混用，其中后两者需要运行时打分函数注入；若 DSL 的评估节点只支持固定类型判定，需要函数注入逃逸舱。
7. **"成功后也反思"等变体行为**（论文不同实验设置不一致，**存疑**）：这类以运行时条件决定反思粒度的行为难以静态声明。
