## ① 核心机制

ADAS 要解决的是「谁来设计 agent 系统」这一元问题：不预设人工写好的角色提示词与工作流，而是让一个 **meta agent** 以**程序代码（Python）作为 agent系统的表示**，在给定任务域、给定的 agent 代码模板（API 契约）和上一轮执行反馈的条件下，**编程式地生成/改写一个新的 agent 系统**：可以新增角色函数、分配职责、定义角色之间的调用关系与控制流。核心执行模型是 **Meta Agent Search (MAS)** 外层搜索循环——候选代码 → 沙箱执行 → 采集反馈（错误 traceback / 工具调用日志 / 任务输出 / 验证得分）→ 以文本反馈回灌 meta agent → 修订候选，迭代至收敛。论文的三条结论：代码化的 agent 系统可被自动发现且优于人工设计；发现物可**跨域迁移**；发现出的 agent 可**充当新的 meta agent**，形成自举（self-bootstrapping）。

## ② 组件清单

| 组件 | 类型 | 职责 |
|---|---|---|
| Meta Agent | 角色（单 LLM 节点） | 读任务描述 + 模板 + 反馈，产出候选 agent 代码 |
| Agent Code Template | 状态/接口契约 | 规定候选代码的导入约定、类/函数签名与调用入口 |
| Candidate Agent System | 工件（可执行程序） | 用源码表达的「角色 + 工作流 + 工具调用」 |
| Agent Functions / Roles | 角色集合 | 代码内定义的 LLM 调用函数，可运行时新增（不限于模板预设） |
| Tool Registry | 工具 | 候选系统可调用的外部工具（API、搜索、计算等） |
| Code Executor / Sandbox | 工具 | 执行候选代码，捕获 stdout/stderr/traceback 与退出状态 |
| Execution Feedback | 工件/消息 | 错误信息、工具调用轨迹、最终输出、验证分数的序列化文本 |
| Task Verifier / Reward | 组件（验证器） | 判断输出正确性，给出 success/reward 信号 |
| MAS Search Loop | 循环 | 生成→执行→反馈→修订的外层迭代与候选选择 |
| Self-bootstrapping Meta Agent | 角色 | 用已发现的 agent 顶替原 meta agent 继续搜索 |
| Candidate/Log Store | 记忆/状态 | 保存各代候选代码与评估分数，供择优、复用与迁移 |

## ③ 数据与上下文流

- **meta agent 可见上下文**（每次迭代重新构造）：任务域描述 → 代码模板/API 说明 → 上一版候选代码（通常可见）→ 上一轮执行反馈文本 →（部分实现保留若干历史迭代）。
- **消息构造**：反馈以「执行结果 + 错误日志 + 验证得分」的文本块追加进 meta agent 的上下文，不经独立检索；meta agent 一次性输出完整候选代码（可含 `def` 新角色、import、循环与分支）。
- **工件交接**：候选代码（源码工件）→ 沙箱执行 → 执行反馈（日志工件）→ 回灌给 meta agent。工具调用日志与最终答案在执行期产生，供验证器与反馈序列化共用。
- **状态存放**：候选代码与评估分数主要落在进程内变量与日志文件（存疑：是否另有独立文件/数据库归档）；跨轮长期记忆主要就是上下文窗口中的历史候选与反馈。
- **可见性规则**：候选代码只在执行沙箱内可见其工具与任务；meta agent 只通过文本反馈间接观察执行，不直接读沙箱内部状态；最终发现物（代码 + 一段描述）被保存，可作为新域的起点或新的 meta agent。

## ④ 失败处理与停止条件

1. **代码报错/无法运行**：捕获 traceback 与 stderr，作为反馈回灌，由 meta agent 修订代码（错误驱动的自修复）。
2. **运行成功但答案错误**：把任务、输出与失败判定理由反馈，让 meta agent 改 prompt、角色划分或工作流。
3. **执行挂起/超时**：由沙箱超时打断，把超时信息作为一类失败反馈（存疑：具体超时与重试策略的细节）。
4. **低效循环（meta agent 反复输出近似代码）**：靠迭代上限兜底，并保留历史最佳候选。
5. **停止判据**：达到最大迭代次数（上限量级存疑）；或验证得分/成功率达标（阈值由外部评估给定）；或 meta agent 自述无需继续修改；或人工终止。
6. **候选选择**：按在各训练/验证任务上的多次运行准确率排序，取最优版本对外报告，而非取最后一次迭代。

## ⑤ 预算与评估方式

- **token 预算**：meta agent 侧消耗（模板 + 代码 + 反馈构成的长上下文）与候选系统运行侧消耗分开计；论文报告了相对人工设计与同期自动设计方法的成本对比（具体数值存疑）。
- **迭代预算**：MAS 迭代次数上限；每个候选只在少量任务/样本上评估以控制开销；搜索曲线（准确率 vs 迭代）作为主要结果图。
- **基准**：以推理/谜题类与代码类任务族评测，比较「meta agent 发现的系统」与「人工撰写系统」（存疑：具体清单疑含 Maze、Tic-tac-toe、Wordle 一类谜题任务，是否另有 HumanEval/工具调用基准存疑）。
- **消融**：去除执行反馈、禁止新增角色函数、去除代码表示/模板约束、更换底座模型（GPT-4o / o1-preview）、跨域零样本迁移、**自举**（用发现物充当 meta agent）；并与同期自动 agent 设计方法对比（同期工作，存疑具体对比项）。

## ⑥ DSL 表达点清单

(a) 可映射为「标准拓扑 + 组件」的机制

| 机制 | 映射预判 |
|---|---|
| Meta Agent 生成候选 | 单节点 LLM 循环 + 代码生成工具（文本产物） |
| MAS 外层迭代 | 反思/修订回路（Reflexion 风格：生成→评估→反馈→再生成） |
| 候选代码交接给执行器 | 「工件交接」：源码工件 → 沙箱执行工具节点 |
| 执行反馈回灌 | 工件交接：执行反馈工件（错误码/日志/得分）注入下一轮上下文 |
| 任务验证 | 验证器节点（success/reward 输出） |
| 代码内角色函数 | 多角色 + 工件交接（角色间以返回值传递中间产物） |
| 候选与分数留存 | 记忆/工件存储（可枚举、可选优） |
| 跨域迁移 | 图复用/预置子图挂载（新域接入既有发现物） |

(b) 预计需要 DSL 逃逸舱的机制

1. **运行时动态决定拓扑**：候选系统的调用关系与循环写在 Python 控制流里，节点/边在运行前不可静态枚举 → 需要「代码执行沙箱 / 运行时动态图」逃逸舱。
2. **运行时新增角色**：meta agent 可在生成代码中 `def` 出模板之外的新角色函数，角色集合不可预先声明 → 需要「动态角色注册」逃逸舱。
3. **自举（meta agent 被发现物替换）**：拓扑发生递归替换、可无限嵌套 → 需要「自引用/递归拓扑」逃逸舱。
4. **任意 Python 能力**：候选代码可 import、读写文件、调用未列入工具表的库 → 需要通用代码沙箱逃逸舱（工具表约束被绕过）。
5. **不定形状的反馈与评估**：反馈是 traceback、工具日志、自由文本与数值的混合体，验证器亦为运行时脚本 → 需要「任意内容工件 / 可编程评估钩子」逃逸舱，固定 schema 难以覆盖。
6. **程序化选择与打分逻辑**（多次采样、投票、成功率聚合、多任务加权）→ 运行时可编程选择器，难以退化为静态边权。
7. **编译目标差异**：ADAS 的搜索空间是「程序」而非「图」，DSL 若只能表达图，需提供「DSL → 任意代码」的编译逃逸舱，否则无法覆盖 while/try/递归等嵌套控制流。
