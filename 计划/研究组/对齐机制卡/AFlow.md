## ① 核心机制

AFlow（MetaGPT 团队，Zhang et al. 2024）要解决的是"agent 工作流只能靠人工手写 prompt 与固定编排、无法自动优化到超越手工基线"的问题。它的核心做法是把一个 agent 工作流**写成可执行的 Python 代码**：算子（LLM 调用、定制模型、工具包、带角色与输出格式的 Agent）实例化为 DAG 节点，边表示数据依赖，节点体是真实函数体；这样一份"代码"就是搜索空间中的一个点。搜索用 MCTS：选择阶段按 UCB 在已有工作流中挑一个节点扩展；扩展阶段由一个元智能体（LLM）读取父工作流代码并做**代码级变异**（增删节点、改写节点代码/提示词、合并）；评估阶段让候选工作流在一组任务实例上真实执行，得到"质量分 + 成本分"并回传更新节点价值；跑满迭代预算后导出价值最高的工作流作为最终产物。论文主张"代码表示"同时带来可描述性（LLM 能读懂并改写）、高质量、高多样性、低成本四个搜索空间属性。

## ② 组件清单

| 组件 | 类型 | 职责 |
|---|---|---|
| 算子库 Operator Library | 代码库/白名单 | 定义允许出现在 DAG 中的节点类型，约束搜索空间，保证生成代码可运行 |
| Model 算子 | 节点/角色 | 单次 LLM 调用（指定模型、温度等参数） |
| CustomizedModel 算子 | 节点/角色 | 微调或定制模型的调用封装 |
| Toolkit 算子 | 节点/工具 | 一组工具的查询与执行接口 |
| Agent 算子 | 节点/角色 | 带 role/profile、输出格式、内部对话历史；论文分 Format、Reflect、ToolFunction 等形态 |
| 工作流代码 Workflow | 拓扑/工件 | 节点=算子调用，边=数据依赖，节点体为 Python 函数 |
| 共享上下文/记忆 | 状态 | 节点间传递数据的容器，算子内部另持有各自 scratchpad |
| MCTS 控制器 | 搜索控制 | 选择（UCB）、扩展（调用元智能体生成新代码）、评估、回传 |
| 元智能体/优化器 | 元层 agent | 依据父代码与评估反馈生成变异后的子代码 |
| 任务集与验证集 | 数据 | 训练/搜索用任务、评估用子集，搜索期用于打分 |
| 评估器 | 评估组件 | 执行候选工作流，算质量指标与 token 成本，合成总分 |
| 最佳工作流导出 | 产物 | 搜索结束后输出最优代码作为最终 pipeline |

## ③ 数据与上下文流

- 任务实例（自然语言题面或代码题输入）从入口节点进入 DAG，按拓扑序在节点间流动；每个节点的输出以结构化对象写入共享上下文，供下游节点按预定义键读取。
- Agent 算子节点内部把上游工件（上一个节点的输出、任务输入）按其"输出格式/角色画像"拼进 prompt，并保留自身多轮对话历史（scratchpad）；该历史是**节点私有**的，不跨节点共享。
- 元智能体在扩展时看到的是：父工作流代码、该节点已有的评估反馈（质量/成本）、变异指令；它**不直接看到评测任务的真实答案**（大致如此，是否可见部分样本存疑）。
- 搜索状态（代码、质量分、成本分、访问次数）存放在 MCTS 搜索树的节点上；不同候选分支彼此隔离，评估时各自在独立的任务子集上执行，互不可见对方的执行上下文。
- 结束后，仅最优节点的代码被导出为可独立运行的工作流。

## ④ 失败处理与停止条件

1. 元智能体生成的代码语法错误、导入不到算子、或运行即抛异常 → 该候选被判为无效/零分并丢弃，重新生成（无独立的"自省-修补"循环，是否有隐式重试存疑）。
2. 代码空间约束过滤非法拓扑：环、非法算子组合、上下文键不匹配、类型不合法等一律拒绝进入搜索树。
3. 单个任务实例上模型或工具调用失败 → 该样本按失败计入质量分，不中止整轮评估。
4. 迭代预算耗尽即停：论文主设置为有限轮 MCTS（常引用为 20 轮，具体数值存疑），每轮候选在有限任务子集上评估以控成本。
5. 早停：论文中是否有"达到目标质量分/成本上限提前终止"存在，存疑（主叙述更像固定预算跑满后取最优）。
6. 终止判据：搜索树中价值最高的工作流即为最终解；不依赖外部人工筛选。

## ⑤ 预算与评估方式

- 预算有四层：MCTS 迭代轮数上限；每个候选在评估时使用的任务样本数（小子集采样）；LLM token/成本上限（体现在打分中并反向抑制高成本工作流）；单节点质量目标阈值。
- 打分：质量分用任务指标均值；成本分按 token 用量归一化后作惩罚项（采用对数归一化的形式，具体公式存疑），总分 = 质量 + 成本（成本越高扣得越多）。UCB 选择时把质量、成本与探索项合并。
- 基准与指标：HumanEval、MBPP（代码生成，pass@1）；GSM8K（数学推理，accuracy）；HotpotQA（多跳问答，accuracy 与 F1）。
- 报告结论（数值需以原文核对，存疑）：相对人工设计的 GPT-4o 工作流平均提升约 4.98%，同时平均 token 成本下降约 52.8%。
- 消融：代码空间 vs 文本/提示词空间表示；MCTS vs 单步贪心与随机搜索；是否引入成本项；算子库与代码空间约束强弱；跨任务泛化与工作流可迁移性。

## ⑥ DSL 表达点清单

**(a) 可映射为"标准拓扑+组件"的机制**

- 工作流 = 有向无环拓扑，节点 = 算子实例，边 = 数据依赖 → 标准拓扑（图的节点/边声明）。
- Model / CustomizedModel / Toolkit / Agent 四类算子 → 组件目录中的"角色型节点 / 工具型节点"枚举，节点类型受白名单约束。
- 节点间通过结构化工件交接 + 共享上下文写入 → 工件交接语义与上下文注入点（artifact binding）。
- Agent 节点内部的多轮对话与格式/反思子步骤 → 单节点内的 agent-in-loop 循环 + 可插拔的节点内策略。
- 任务质量指标（pass@1 / accuracy / F1）与 token 成本计量 → 评估组件（可注册 metric 与 cost 回调）。
- 迭代轮数、每轮样本任务数、质量阈值 → 预算配置项；轮次上限与阈值达成 → 停止条件。
- 搜索结束导出最优工作流 → 编译/物化产物（最终可执行流水线）。

**(b) 预计需要 DSL 逃逸舱的机制**

1. **运行时生成/改写工作流图本身**：元智能体在运行期产出新的 Python DAG，拓扑不是静态声明的，DSL 无法直接表达"合成新图"，需程序合成/图改写逃逸舱。
2. **MCTS 是对 DSL 程序本身的元层搜索**：标准 DSL 只能描述一次执行，无法描述"搜索多个拓扑并按价值选择"，需搜索/进化元循环逃逸舱（允许 hook 干预节点增删与状态回传）。
3. **节点体是任意 Python 函数**：算子实现包含动态控制流、闭包、局部逻辑，静态拓扑 DSL 只能表达接口签名，无法表达函数体，需代码载荷/代码嵌入逃逸舱。
4. **token 与成本计量**：成本分依赖运行期调用日志与对数归一化，属运行时遥测，静态声明无法计算，需 telemetry逃逸舱。
5. **评估闭环回调**：候选执行结果必须回灌到搜索状态（价值更新、UCB 计数），需要运行时回调与可变状态逃逸舱。
6. **代码空间约束的完整性校验**（拓扑合法性、算子类型匹配、上下文键约束）：这些是跨节点/跨运行期的约束，纯拓扑 DSL 难覆盖，需约束校验逃逸舱。
