## ① 核心机制

GPTSwarm 的问题设定是：手写 agent（一条 ReAct 提示词或一整套角色剧本）是**一次性人工设计**的固定流程，无法被改进；论文要回答"agent 的结构本身能否被自动优化"。它的做法是把语言 agent 重述为一张**有向无环/可环的计算图**：节点是零状态的操作（一次 LLM 调用、一次工具调用、一次反思、一次格式化），边是信息流——声明"谁把什么消息喂给谁"，并因此隐式决定每个节点能看到多少上下文。执行语义是一次图执行：按拓扑遍历把消息沿边分发，节点只看到声明为依赖的上游消息，因此"并行分支互不可见、串行节点看到全量上游"是拓扑的直接后果，而非 prompt 里写出来的约定。优化阶段把**图的拓扑当作策略的动作空间**：一组图编辑算子（增删节点、增删边、改变节点依赖/信息流、替换节点实现）在候选图上采样，图在下游任务集上跑一遍得到标量奖励，用无梯度的强化学习/进化搜索（REINFORCE 类，带精英保留）反复编辑，直到收益不再提升。核心循环是"编辑图 → 执行图 → 记奖励 → 更新/回退 → 再编辑"，被优化的对象是**程序结构**，而不是提示词措辞。

## ② 组件清单

| 组件 | 类型 | 职责 |
|---|---|---|
| Node | 操作（无状态 callable） | 最小执行单元：think / act / tool / reflect / format；声明输入输出 schema |
| Edge | 信息流连接 | 规定上游输出注入哪个下游节点；"边"就是上下文可见性的唯一来源 |
| Graph | 数据结构（= agent 本体） | 节点集 + 边集 + 拓扑序；是"agent"被编译出来的形态 |
| Graph Edit 算子 | 策略动作空间 | node add/delete/swap、edge add/delete、node dependency change |
| Policy / 图优化器 | 优化器 | 以编辑算子为动作、任务表现为回报，做无梯度搜索并维护精英集 |
| Reward / 任务环境 | 评估器 | 在固定 agent 任务集上执行候选图，产出标量奖励 |
| Tool 节点 | 工具封装 | 外部能力（代码执行、检索、浏览器等）作为可插拔节点接入 |
| LLM 后端 | 模型 | 节点内部的推理来源，prompt 模板随节点实现走 |
| GraphAgent / 执行器 | 运行时 | 拓扑遍历、消息分发、节点异常捕获 |
| Memory / 长期状态 | 存疑 | 主线是函数式消息流，跨步记忆多以显式 scratchpad/工件节点 + 边实现，而非全局 store |
| 元信息（节点类型、schema） | 状态 | 供策略在"不看实例数据"的前提下做结构决策 |

## ③ 数据与上下文流

- **构图期**：编辑算子只看**图结构与节点元信息**（节点类型、边、输入输出 schema），看不到任务实例本身，避免把结构搜索过拟合到某个样本；奖励来自在一组任务上的执行结果（奖励是 task-level 还是 instance-level 存疑）。
- **执行期**：入口节点收到初始消息 → 节点产出消息体 → 沿出边分发 → 下游节点收到"上游消息 + 自身 prompt/工具描述"。没有边就没有信息流，这是"并行分支互不可见、串行节点共享全量上游"的机制来源。
- **工件交接**：代码块、检索结果、中间推理作为消息体沿边传递，等价于 MetaGPT 式的结构化工件交接，只是工件类型由节点 schema 约束。
- **状态存放**：图与节点实现是静态配置；运行期状态（消息、工具返回值、scratchpad）只存在于一次执行的内存中，图本身不携带跨任务记忆（这点与带全局 memory 的框架式 agent 有本质区别，存疑）。

## ④ 失败处理与停止条件

- 节点级失败（工具报错、解析失败、超时）：表现为图中的一个坏节点，修复手段是**在图层面删改该节点或改它的依赖**，而不是在 prompt 里加一句"如果失败请重试"——自省修复的粒度落在拓扑上。
- 优化循环停止：达到最大编辑轮数 / 最大候选图数 / 总调用成本上限，或奖励进入平台期（具体超参存疑），通常并存。
- 单步编辑可能变差：保留精英/最优图，必要时回退到历史最佳图再继续搜索（无梯度的典型做法）。
- 单次任务执行停止：节点产出终止型输出（最终答案）或触达最大步数/最大 token 上限。
- 失败样本作为负奖励回灌（是否显式区分"不可用图"存疑）。

## ⑤ 预算与评估方式

- **单次执行预算**：最大节点调用数 / 最大 token / 最大步数，防止优化出的图无限膨胀（论文强调这点，存疑具体数值）。
- **搜索预算**：最大迭代数、最大候选图数、最大总 LLM 调用与成本。
- **评估方式**：把搜索得到的图与人工设计基线对比（ReAct 单体、pipeline、反思/自检等），指标为任务成功率/准确率 + token/成本；同时报告"每张图平均节点数"等结构复杂度指标。
- **消融**：分别移除某类编辑算子（如只允许增删节点、禁止改边/改依赖）、用随机编辑或启发式编辑替代学习到的策略，验证"结构搜索"本身的增益。
- **基准（存疑）**：我记得覆盖了代码生成（HumanEval 类）、多跳问答（HotpotQA 类）与带工具/GUI 的 agent 任务（WebShop/OSWorld/BabyAGI 类），具体清单与是否含多智能体协作任务我不敢断言。

## ⑥ DSL 表达点清单

**(a) 可映射为"标准拓扑 + 组件"的机制**

- 「agent = 图」→ DSL 顶层是 **Graph/Topology** 对象，边必须是一等声明式数据流依赖，而不是隐式顺序列表。
- ReAct 单节点自循环 → 「带条件的自环节点 / DSL 原生 loop 结构」。
- Plan→Execute→Review 流水线 → 三节点链式拓扑，工件交接 = 类型化消息端口。
- Generate→Critique→Revise 反思 → 带反馈边的 cycle 拓扑。
- 多智能体辩论/投票 → fan-out 并行分支 + fan-in 汇聚节点。
- 工具调用 → `tool` 节点类型 + 参数 schema + 失败返回类型。
- 记忆/scratchpad → 显式 context 节点，通过边接到需要它的节点。
- 条件路由 → 条件边（DSL 需支持按节点输出选择下游）。

**(b) 预计需要 DSL 逃逸舱的机制**

1. **运行时生成/改写图结构**：拓扑是优化变量本身，静态 DSL 无法表达"产出一张新图"——需要动态图生成 + 图编辑原语逃逸舱。
2. **奖励驱动的优化控制环**：RL/进化搜索（策略、采样、精英集、回退）整体在 DSL 之外，必须以"调用外部优化器并把结果作为 DSL 子图回填"的逃逸形式接入。
3. **外部奖励/评分函数**：任务成功判据、测试通过率来自 DSL 之外的评测器，需要任意回调挂载点。
4. **任意 Python 节点体**：节点是任意 callable，DSL 只能声明结构不能声明函数体，需内联代码/自定义算子逃逸舱。
5. **执行期动态并发与拓扑重排**：动态 fan-out、节点级超时取消、异步语义难以静态表达（GPTSwarm 本身也偏静态执行，存疑其必要性）。
6. **图作为值**：图可被嵌套、复用、作为另一张图的节点，DSL 需把"图"提升为一等值类型，否则逃逸。
