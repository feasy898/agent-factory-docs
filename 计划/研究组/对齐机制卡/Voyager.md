## ① 核心机制

Voyager 面向 Minecraft 开放世界的"终身学习"难题：不微调、不人工示范、不使用人类动作接口，仅靠语言模型在 MineDojo 环境中**持续、无人干预地自主探索**并完成长程目标。其执行模型是"外层课程调度 + 内层代码生成循环"的双层结构：外层由一个独立的 LLM 提议器基于当前状态与已达成里程碑，**动态生成**下一个难度递增的目标并写入课程表；内层是一个 ReAct 风格的单节点循环——把任务指令、检索到的可执行技能、上一轮代码、环境执行反馈、自我验证结论拼装进固定槽位的提示词，让模型产出 Python 代码；代码在沙箱解释器中调用 Minecraft 动作 API 执行，返回成功/异常信息并回流为下一轮提示的一部分；若代码执行成功且自验证通过，该技能被**写入技能库**并以（名称+描述+代码）形式长期保存；此后任何时刻，任务描述经嵌入检索取回 top-k 相似技能注入上下文，实现跨回合复用。整套机制的本质是：把"会了什么"外化为可检索、可执行、可累积的工件，把"下一步做什么"外化为自动课程，二者通过迭代式环境反馈闭环耦合。

## ② 组件清单

| 组件 | 类型 | 职责 |
|---|---|---|
| 自动课程提议器（GPT-4） | 角色/外部 LLM 调用 | 依据当前状态+历史，提议下一个可达成的递进目标；经多轮可行性反馈修正 |
| 课程表（Curriculum） | 状态/工件 | 记录已提议目标、是否达成、难度档；既是提议器输入也是评估对照 |
| 任务-技能检索器（嵌入相似度） | 记忆原语 | 任务描述→向量→库内 top-k 相似技能，供提示注入 |
| 技能库（Skill Library） | 记忆/工件库 | 每条技能=名称+描述+可执行代码；跨回合持久化，只增不减 |
| 代码生成器（GPT-4） | 角色 | 在固定提示模板下产出 Python 代码 |
| 迭代提示模板 | 上下文构造 | 四槽位：任务指令 /技能代码 / 执行反馈 / 自我验证 + 计划 |
| 沙箱解释器 + Minecraft API | 工具 | 执行代码（craft/place/destroy/inventory 等），返回报错或观察 |
| 自我验证器 | 校验步骤 | 判断代码是否成功、目标是否达成；生成"下一轮是否修正"的结论 |
| 技能写入守门 | 条件/守卫 | 执行成功且自验证通过才入技能库 |
| 环境状态观察 | 状态 | 生命、饥饿、装备、库存、周围方块、已解锁物品等（文本化呈现） |

## ③ 数据与上下文流

- **提议器**：每轮外层循环仅见"当前游戏状态 + 已达成里程碑/课程表"，不见具体代码与完整对话历史；输出一个目标描述写入课程表，随后主循环把该目标与"当前任务指令"拼接为新的一步任务。
- **检索**：主循环每步开始时，用**当前任务描述**编码检索技能库，取回 top-k 技能（仅名称+描述+代码片段），拼装进提示；技能库内容对生成器始终只读可见。
- **生成→执行**：生成器产出代码；代码执行结果（异常栈/成功观察）作为"执行反馈"回填同一条消息的下一轮提示——这是上下文的**唯一回流通道**，非对话式历史累积。
- **自验证→写库**：自验证结论写入同一提示的"自我验证"槽；若两者皆通过，技能连同名称与描述写入技能库，并对后续所有步骤可见（被检索命中时）。
- **状态归属**：课程表、技能库为**跨回合持久化**的磁盘态工件；游戏状态由环境持有、每步以文本快照注入；对话上下文本身是短窗、单任务粒度。

## ④ 失败处理与停止条件

1. **代码异常**：解释器报错栈直接注入下一轮提示，由模型改写代码（迭代修正），无独立回退策略。
2. **自验证不通过**：触发下一轮重规划，任务保持不变，直至成功或轮次耗尽。
3. **技能写入门禁**：执行报错或自验证失败 → 该技能不入库（避免污染检索池）。
4. **目标不可达**：提议器经多轮可行性反馈仍判定不可行则换目标（课程回退）。
5. **步级停止**：一轮生成-执行-验证即为一个"步"；步数上限由运行时预算（游戏时长/调用次数）约束，非静态声明（存疑：论文未给出统一的单步硬上限细节）。
6. **会话级停止**：无固定 episode 终点；靠外部预算终止，长期运行、跨任务持续。

## ⑤ 预算与评估方式

- **上下文预算**：靠 top-k 技能检索压缩提示规模；每个技能条目保留描述与代码以控制注入长度（k 的确切取值存疑）。
- **调用预算**：以 GPT-4/GPT-3.5 调用次数与美元成本衡量，论文给出按游戏小时的费用对比（课程生成用 GPT-3.5 时代价更低、效果仅略降）；另有基于游戏时长的对比评测。
- **基准**：MineDojo 提供的 34 个里程碑（科技树可达任务）与若干"不可行/长尾"任务（钻石、黑曜石等）。
- **指标**：里程碑完成率、独特物品获取数、行进距离、任务完成率。
- **消融**：分别去掉自动课程、技能库、迭代提示/自我验证，验证三者各自贡献；并做 GPT-4 vs GPT-3.5 提议器的对比（存疑：消融的具体数值未逐项复核）。
- **结果**：相较基线，独特物品数约 3.3×、里程碑完成速度约 15.3×、行进距离约 2.3×；能在约 15 分钟游戏时间内取得钻石。

## ⑥ DSL 表达点清单

**(a) 可映射为「标准拓扑+组件」**

1. 迭代提示机制 → **单节点自循环（ReAct 型）**：环境反馈以工具返回通道回灌同一节点上下文，非多节点流水线。
2. 自动课程 → **双层循环拓扑**：外层"提议器节点 → 课程表工件"，内层"生成→执行→验证"节点；课程表是跨步更新的状态工件。
3. 技能库 → **持久化记忆组件 + 工件库**：条目为结构化记录（名称/描述/代码），可被检索、可被条件写入。
4. 任务-技能匹配 → **检索式记忆原语**：查询(任务描述)→top-k→注入上下文，属静态声明的数据流。
5. 自我验证 → **节点内的判据步骤 / 守卫**：非独立智能体，是同一次生成的固定槽位。
6. 技能入库条件 → **条件边**：执行成功 ∧ 自验证通过 → 写库。
7. 环境交互 → **工具集**：Minecraft 动作 API 声明为工具 schema，代码块调用即工具调用。
8. 上下文模板 → **固定槽位提示模板**：任务指令/代码/反馈/自验证/计划五段拼接。

**(b) 预计需要 DSL 逃逸舱**

1. **运行时生成并执行任意 Python 代码**：DSL 无法静态声明沙箱解释器与动态代码求值，需逃逸舱（如代码执行运行时接口）。
2. **运行时由 LLM 改写图与工件结构**：目标提议、任务生成使"下一节点"在运行时才确定，非静态 DAG，需可变的运行时工件写入/节点注入接口。
3. **代码与游戏 API 的动态面对接**：模型可能探索出 DSL 未声明的动作组合，逃逸舱需保留原始动作调用通道。
4. **向量/嵌入语义检索**：若 DSL 无向量索引原语，top-k 相似度检索只能以工具或逃逸舱实现（存疑：取决于目标 DSL 是否内置语义检索）。
5. **跨会话持久化状态**：技能库与课程表需跨 episode 存活，单会话图 DSL 通常不提供，需持久化工件读写接口。
6. **软性/概率性终止判据**：目标达成由环境隐藏状态 + LLM 自验证共同决定，缺乏客观信号，需"非确定性守卫/终止判据注入"逃逸舱。
7. **无固定终点的运行与动态预算注入**：持续探索模式下的停止条件由运行时预算决定，需动态终止条件注入能力。
