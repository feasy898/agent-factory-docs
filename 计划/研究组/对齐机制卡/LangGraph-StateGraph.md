## ① 核心机制

LangGraph 不是"智能体框架"而是一个**有状态的图执行引擎**：开发者把应用写成一个 `StateGraph`，声明一个带类型注解的共享状态（State，通常是 `TypedDict`/`dataclass`，含 reducer 合并语义），再把若干普通 Python 函数注册为**节点**（节点只做一件事：读当前 State → 返回状态增量），最后用**边**把节点连成有向图——固定边、**条件边**（由函数根据 State 决定下一个节点）、以及 `START`/`END` 哨兵。编译（`compile()`）后产出一个可调用的图运行器，它按**super-step（超级步）**语义执行：同一超级步内的所有节点基于同一份 State 快照并行运行，各节点的返回增量按 reducer 合并后成为下一份 State；图允许**环**，因此核心控制流是"节点 → 条件判定 → 下一节点 → …"的循环，条件边自然表达 ReAct 的"思考-行动-再思考"与多智能体 handoff。引擎另外提供**检查点（checkpointer）**把每一步 State 快照持久化，使图可中断、可恢复、可回放（time-travel），并支持 `interrupt()` 在节点内**挂起**等待外部输入后从同一位置恢复执行——这是"人在回路"与长时间运行的实现基础。

## ② 组件清单

| 组件 | 类型 | 职责 |
|---|---|---|
| StateGraph | 图容器 | 声明节点、边、入口/出口，持有 State schema |
| State schema (`TypedDict`/`dataclass`) | 共享状态 | 定义通道（channel）与 reducer 合并规则；是唯一的数据载体 |
| Reducer / `Annotated[list, add]` | 合并策略 | 定义同一步多个写入者如何合并（覆盖 / 追加 / 合并 dict） |
| Node（普通函数） | 计算单元 | `(state) -> partial_state` 或 `(state, config) -> ...`；纯函数式地读快照、写增量 |
| Conditional edge（路由函数） | 控制流 | 根据 State 返回下一节点名或 `END`；返回列表可扇出 |
| Edge / START / END | 图结构 | 固定有向边与入口/出口哨兵 |
| Graph compiler (`compile()`) | 运行时 | 校验拓扑、绑定持久化与中断机制，产出可执行图 |
| Super-step 调度器 | 执行循环 | 按代际并行执行同层节点，收集增量，合并成新 State |
| Checkpointer | 持久化 | 按 thread_id 保存每步 State/写入/元数据，支持恢复、回放 |
| Thread / checkpoint id | 会话标识 | 标识一条执行线，多轮/多线程隔离状态 |
| `interrupt()` / `Command` | 人在回路 | 在节点内挂起、抛出外部输入、写状态或跳转 |
| `Send` / `Command(goto=...)` | 动态扇出 | 运行时动态派发多个实例（map-reduce fan-out） |
| Subgraph | 组合 | 把另一个图作为节点嵌入，复用其 State 与中断语义 |
| `Pregel` 运行时内核 | 执行模型 | LangGraph 早期基于 Pregel 的 BSP 实现；super-step 源自此 |

## ③ 数据与上下文流

- **消息构造**：消息不是特例化的 Message 对象，而是普通 State 通道（如 `messages: Annotated[list, add_messages]`），由 LangChain 消息类承载；节点通过读取该通道拿到"到目前为止的对话"。
- **状态存放处**：State 存在图运行器的状态通道里，并在每个 super-step 结束后由 checkpointer 按 `thread_id` 落盘；调用方也可传入 `config`（线程 ID、回调、运行配置、tags/metadata）随调用进入节点。
- **可见性**：节点在**执行时**只看到自己所属 State schema 声明的通道 + `config`；节点之间不直接共享 Python 变量，只通过 State 交接。一个节点返回的是**增量**而非全量，框架用 reducer 合并；未返回的通道保持原值。
- **跨节点上下文**：语言模型调用时，节点自己从 State 里挑字段组装 prompt/messages；框架不自动注入记忆。记忆机制通常由**显式的 memory 节点**实现（读写 messages 通道、追加摘要节点），即"记忆=状态里的一个通道 + 一个函数"。
- **工件事物**：LangGraph 本身无独立工件层；可把大对象（文件、检索结果）放进 State 通道或用 `Store`（跨线程长期记忆）承载，通过 State 交接。
- **多智能体**：多个图（或一个图多节点）作为子图/节点共享或各自持有 State，通过共享通道或 `Command(handoff=...)` 传递。
- **并发读**：同一 super-step 内的多个节点读的是**同一份不可变快照**，互不可见彼此本步的写入（避免竞态），写入统一在步末合并。

## ④ 失败处理与停止条件

- **节点异常**：节点抛异常默认向上传播中断整个图；可用 `retry_policy`（如 `RetryPolicy`）对节点配置指数退避重试。
- **重试**：节点级重试策略（最大次数、间隔、错误判定），LangChain 表达式/模型调用层另有自身重试。
- **回退/自省修复**：框架不内置通用自省回路；常见的"检查-修正"由用户显式写成节点 + 条件边（校验输出 → 失败回修节点 → 再校验），或用 `Command(goto=...)` 手动重定向。
- **递归/循环上限**：`recursion_limit`（默认 25 步）作为硬性停止条件，超过即抛 `GraphRecursionError`，防止条件边成环导致无限循环。
- **终止判据**：到达 `END` 节点；条件边返回 `END`/`None`；节点返回显式 `Command(end=True)`。
- **中断与恢复**：`interrupt()` 抛出 `GraphInterrupt` 挂起，状态被检查点保存；恢复时传入 `Command(resume=...)` 外部输入，节点从挂起点继续（其之前的副作用不自动回滚）。
- **超时/外部失败**：依赖外部服务失败需自行在节点内捕获并转成状态更新（如 `error` 通道），由条件边路由到重试或兜底节点；框架只保证 `interrupt`/`checkpoint` 的状态一致性，不保证事务回滚。
- **背压/限流**：无内置并发限流，需要在节点或 `config` 中控制并发度。

## ⑤ 预算与评估方式

- **token 预算**：框架不直接计量 token；控制手段在节点内自行截断 State 中的消息历史（滑窗/摘要节点）、限制子图调用次数，或用 `LLM.max_tokens` 控制单次输出。框架无全局 token 计数器。
- **轮次预算**：以 **super-step 步数**为度量，`recursion_limit` 是唯一硬上限；建议在 State 中自建 `remaining_steps`/`budget` 通道，由条件边读取后决定继续或 `END`。
- **成本**：通过条件边限制进入昂贵节点的次数、把"是否需要调用模型"写成显式路由来控制；并可给不同节点配不同模型。
- **评估方式**：LangGraph 本身**没有论文式基准与消融实验**（存疑：官方文档主要给示例与模板仓库，未见系统性消融）。实践评估形态是：用 LangSmith 追踪每步 trace 观测延迟/成本/错误率，用 LangChain `evaluators` 或自建离线数据集跑"胜率/正确率"回归测试；"框架有效性"更多靠工程指标（可靠性、可恢复性、可观测性）而非学术基准。

## ⑥ DSL 表达点清单

**(a) 可映射为"标准拓扑+组件"的机制**

- **节点=函数** → 标准节点；参数为 State 快照，返回状态增量，天然可映射为"函数节点 + 增量写端口"。
- **共享 State + reducer 合并** → 单一状态通道 + 合并策略（覆盖/追加/合并）组件；多写入者并发写需显式声明合并语义。
- **固定边 / START / END** → 标准有向边与起止哨兵。
- **条件边（路由函数）** → 条件边 = 节点出边上的路由判定组件；返回下一节点名或 `END`。
- **图内循环（ReAct 形态）** → 标准拓扑"单节点/多节点循环 + 终止条件"；终止判据即条件边分支到 `END`。
- **多智能体 handoff / supervisor** → 条件边路由 + 多节点（supervisor 节点 = 一个 LLM 节点 + 一组 worker 节点）。
- **map-reduce fan-out（`Send`）** → 静态扇出可用"扇出节点 + 汇聚节点 + 列表 reducer"表达；`Send` 的**运行时**动态数量需逃逸舱（见 b）。
- **检查点 / 恢复 / time-travel** → 需 DSL 提供"状态快照持久化点 + 恢复入口"的组件（在每个 super-step 边界隐式或显式声明）。
- **`interrupt()` 人在回路** → 需"挂起点/外部输入注入点"组件；语义上等价于"节点在某个端口等待一个外部回填的输入并阻塞后续步"。
- **子图嵌套** → 图作为节点（层级化组件）。
- **记忆节点（读写 messages）** → 显式状态通道 + 摘要/检索节点，属普通节点组合。
- **预算控制** → 条件边读取预算通道 + `recursion_limit` 类步数上限。

**(b) 预计需要 DSL 逃逸舱的机制**

- **运行时动态改写图结构**（运行时决定下一个节点集合、临时插入/删除边）→ 逃逸舱：拓扑在 DSL 层必须静态声明，运行时的"改图"只能表达为状态驱动的路由，抑或提供动态图构造 API。
- **动态扇出数量（`Send`）** → 逃逸舱：需要运行时生成 N 个并行任务实例，超出静态节点/边数量。
- **条件边在运行时返回多目标 / 依赖运行期数据决定拓扑** → 逃逸舱或降级为"路由状态字段"，DSL 无法静态求值。
- **真正的 `interrupt` 挂起-恢复** → 部分逃逸舱：需要"任意节点内部可挂起、等待外部输入、从挂起点续跑且副作用不回滚"的过程语义，静态 DAG/图 DSL 通常只能表达"边界处暂停"。
- **节点内任意 Python 副作用与状态事务** → 逃逸舱：框架不提供节点级事务/回滚，DSL 若承诺事务性即越界。
- **跨线程长期记忆（Store）与任意键值访问** → 逃逸舱：跨执行线共享存储的读写语义不在单图状态内。
- **节点级重试/退避与错误分类** → 需 DSL 原生支持重试策略与错误路由；否则只能降级为显式的"错误状态 + 重试节点 + 计数通道"。
- **节点内并发调用/流式返回（token 级 streaming、async 取消）** → 逃逸舱：DSL 的执行模型是 super-step 级同步语义，节点内部并发与取消需宿主语言支持。
- **超级步内并行节点的写冲突消解** → 逃逸舱：多写者同时写同一通道的非确定性合并顺序与冲突处理难以静态表达。
- **子图与父图的状态可见性/隔离边界**（哪些通道向上暴露、哪些隐藏）→ 逃逸舱：需通道级可见性声明。
- **时间旅行（回到任意历史检查点并分支）** → 逃逸舱：属于运行历史操作而非图结构声明。
- **跨图/跨运行的编排与调度器语义**（多图并行、外部队列驱动）→ 逃逸舱：超出单图执行模型。
