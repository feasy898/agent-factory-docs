## ① 核心机制

MetaGPT 要解决的是"多智能体协作中流程无序、交接信息损耗大"的问题：把真实软件公司的**标准作业流程（SOP）**形式化为角色之间的**有向图**，并用**结构化工件（PRD→设计文档→任务列表→代码文件→测试用例）**充当角色间的接口，而非让 Agent 之间自由对话传递自然语言。核心执行模型是"消息总线上的轮转调度 + 因果链驱动"：环境按角色优先级逐个唤醒，角色订阅自己关心的消息类型（如架构师只对 PRD 消息作出反应、工程师只对设计/任务消息作出反应），每次反应把上游工件按**固定模板 schema**转成下游工件并发布；`cause_by` 字段记录血缘，使上下游激活与回环（QA 发现 bug→退回工程师修复）成为可追踪的因果链，而不以"轮到谁说话"作为唯一触发依据。角色内的 LLM 只承担"在 schema 内填内容"这一窄职责，流程拓扑与数据形状由代码固定。

## ② 组件清单

| 组件 | 类型 | 职责 |
|---|---|---|
| ProductManager | 角色 | 读用户需求，产出 PRD（产品名、愿景、功能点、竞品分析、目标/需求草案） |
| Architect | 角色 | 读 PRD，产出设计文档：系统架构、数据结构与 API 接口定义、文件清单 |
| ProjectManager | 角色 | 由 PRD/设计派生任务列表（任务含 id、指令、依赖、目标文件），派发给工程师 |
| Engineer | 角色 | 按任务写代码文件、执行测试、按 QA反馈修复 |
| QAEngineer | 角色 | 写测试用例、执行、按通过/失败发布结论与失败清单 |
| Designer（可选） | 角色 | 产出 UI 原型/描述（论文中非必需，常被消融） |
| SOP 图 | 执行模型 | 节点=角色，边=工件类型的有向图；由 Action 的 `required_previous` 元数据推导 |
| Action | 组件 | WritePRD / WriteDesign / WriteTasks / WriteCode / WriteTests / RunCode / Terminate，每个声明前置产物 |
| Environment | 运行时 | 消息总线 + 调度器：发布订阅、按优先级轮转角色、维持全局消息池、判定终止 |
| Message | 数据结构 | `id / content / cause_by / send_to / msg_type / timestamp`，支持广播与定向投递 |
| Role | 组件 | 角色内含 memory（本人收件箱）、`_watch` 订阅表、`react` 循环、状态序列化 |
| 角色记忆 / 全局消息池 | 状态 | 前者为角色私有的消息历史（按因果链过滤），后者为环境共享 |
| 结构化工件 | 数据结构 | PRD / Design / TaskList / CodeFile / TestCase，均为 JSON 化 schema |
| 工作区文件系统 | 工具 | 代码与设计文档落盘，跨角色共享同一仓库 |
| 代码执行器 | 工具 | RunCode 实际运行生成代码与测试并捕获输出 |
| LLM 调用 | 工具 | 按 schema 模板生成工件内容（受字段约束） |
| TaskFinished | 终止信号 | 终态消息类型，环境据此停止轮转 |

## ③ 数据与上下文流

启动时用户需求文本进入 PM；PM 发布 PRD 消息（cause_by 指向用户输入）。Architect 的订阅表命中 PRD 类型→被激活，注入 PRD 工件内容 + 与该 PRD 有因果关系的历史消息，产出设计文档并发布；ProjectManager 依设计/PRD 产出任务列表并定向发布给 Engineer；Engineer 对每个任务写文件并发布代码/状态；QA 订阅代码类消息，注入代码与任务清单，产出并运行测试用例，失败则把错误与失败用例作为新消息回传给 Engineer（cause_by 指向 QA 消息，形成回环），通过则发布 TaskFinished。

可见性规则：**角色只看到自己收件箱中与当前触发消息有因果链相关的历史**，看不到其他角色的内部思考与未订阅消息；工件不是靠共享内存变量传递，而是**编码进消息 content 后在下游 prompt 中注入**，因此工件 schema 既是接口也是上下文裁剪器。状态分布在三处：工作区文件（代码/文档产物）、环境全局消息池（所有已发布消息）、角色本地 memory（自己收到的消息历史）；三者均可序列化，支持中断续跑。

## ④ 失败处理与停止条件

- **代码/测试运行失败**：QA 发布失败用例与错误信息，Engineer 消费后修复并重新产出，进入"改→跑→验"回环。
- **LLM 输出不符合 schema**：Action 解析/校验失败时角色 react内部捕获异常并重试（**具体重试次数上限存疑**），仍失败则该轮空转或中断。
- **消息解析/模板字段缺失**：报错并跳过该角色本轮处理，环境继续轮转（是否直接终止**存疑**）。
- **无消息可消费**：角色本轮空转，调度器继续轮转下个角色，不触发提前终止。
- **终止判据**：环境收到 `TaskFinished`（QA 判定通过）即停止；`Terminate` Action 可提前主动终止。
- **硬性最大轮次/超时**：论文未给出通用上限，环境循环依赖终止信号（**是否存在默认 max_round 存疑**）。
- **人工介入**：预留 `send_to_user` 通道用于向用户提问/回传，但非标准闭环组成部分。

## ⑤ 预算与评估方式

- **Token/成本控制**：消息 payload 为结构化 JSON 摘要而非全量对话历史；角色只注入因果链相关消息；每个角色的 prompt模板固定、上下文窗口小，因此论文称单项目成本显著低于多智能体对话基线（**具体金额与"每项目约 1 美元量级"的数字存疑**）。
- **基准**：论文自建 Simple Software Dev 基准集，覆盖小游戏（如贪吃蛇、俄罗斯方块）、工具类项目、Web/Django/Vue 类应用、数据分析类任务等，以**生成代码能否通过单元测试**为核心判据。
- **指标**：pass rate（测试通过率）、成本/角色轮数，以及与基线的对比。
- **基线对照**：ChatDev、同类多角色框架、以及单 Agent 的 ReAct 式直接实现。
- **消融**：去 SOP（角色无分工自由对话）、去结构化接口（改为自由文本交接）、去 QA、去 Architect/PM（角色贡献度），验证"SOP + 结构化接口"两组件各自的增益。

## ⑥ DSL 表达点清单

**(a) 可映射为"标准拓扑 + 组件"的机制**

- MetaGPT ＝ **有向流水线拓扑 + 结构化工件交接**（PM→架构师→(PM/任务)→工程师→QA），不是 ReAct 式单节点循环。
- 角色 ＝ 带**输出类型声明**的 actor 节点（每个角色固定一种或少数几种产出工件类型）。
- 结构化工件 ＝ 节点间**端口类型化 payload**，schema 即接口契约（PRD/Design/TaskList/CodeFile/TestCase）。
- SOP 图 ＝ 静态声明的拓扑 + 边上的工件类型 + 节点优先级顺序。
- `cause_by` ＝ 工件**血缘/溯源元数据**，支撑上下游触发与回环定位。
- pub/sub 消息通道 ＝ 异步消息总线 + 主题（消息类型）订阅，角色级 inbox 隔离。
- TaskFinished ＝ **声明式终态信号**触发环境停止。
- 角色记忆 ＝ 按因果链过滤的滚动上下文（context scoping）。
- 模板化生成 ＝ **schema 约束的结构化输出生成**（非自由文本）。
- QA 回环 ＝ 带反馈边的拓扑（fix→run→verify 循环）。
- 工作区文件 ＝ 外部工件存储（代码产物落盘、跨角色共享）。
- 状态序列化 ＝ 检查点/恢复机制。

**(b) 预计需要 DSL 逃逸舱的机制**

1. **运行时由 Action依赖元数据推导/改写 SOP 图**——拓扑并非只写一次，用户可修改 `required_previous` 改变流程，静态图声明无法保真 → 需"运行时图重写"逃逸舱。
2. **`_watch` 订阅 + cause_by 链触发的激活语义**——角色由"消息类型是否命中订阅表"决定是否响应，而非由静态边唤醒，属运行时路由 → 需消息类型订阅/触发器逃逸舱。
3. **运行时决定消息收件人（定向 send_to / 广播 / all_agents）**——边在运行时才确定 → 需动态路由逃逸舱。
4. **代码生成与执行副作用**——RunCode 真实执行代码、写工作区文件，DSL需工具副作用与沙箱钩子。
5. **运行错误文本回灌 prompt**——执行 stderr/测试失败结果作为新一轮输入重新注入，属错误回流通道。
6. **LLM 判定的语义终止**——QA 的"通过/不通过"是模型判断而非类型化信号，需要 LLM-as-judge 终止钩子。
7. **双层上下文可见性（角色私有记忆 + 环境全局池）**——不是单一上下文窗口，需要作用域化上下文装配。
8. **用户通道与人工介入（send_to_user / 中断续跑）**——需要交互式挂起-恢复语义。
9. **异常与重试策略内嵌于角色循环**——重试次数与失败回灌策略由用户代码决定，静态预算声明不覆盖。
