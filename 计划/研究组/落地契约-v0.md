## 1. 执行单元注册与调用接口

### 1.1 现状证据

**参数面（af-bench）**。当前真实执行面是 `af-bench` 二进制，CLI 参数面为 `Args` 结构：`--suite/--data-root/--profile/--case-file/--limit/--offset/--out/--trial/--tasks/--host`（`af/crates/af-bench/src/main.rs:78-89`，解析 91-154）。套件分发是硬编码 match：`injecagent | terminal-bench | swe-v`（`main.rs:613-623`）。`--host` 是执行宿主别名（缺省 `anolis`，`local`=本机直执行；`main.rs:8,102-103`）；宿主桥接函数 `tb_ssh` 把"非 local 一律走 ssh 别名"（`af/crates/af-bench/src/swev.rs:268-293`），故 `mingda-bench` 等新宿主以 ssh 别名即接即用（实测记录 `状态/机器清单.md:52`）。

**环境准备/执行/取证/判分/清理**。以 swe-v 线为最完整样本：`swev::setup` 起容器（容器资源护栏 `--memory 6g --pids-limit 512`，常量 `tb.rs:116-117`；宿主差异化代理注入 `swev.rs:63-69`）；`TbEnv{container, task, host, workdir}` 是执行环境句柄（`tb.rs:94-98`），方法 `exec/verify/cleanup`（`tb.rs:186,226,294`）；`capture_diff` 取证写 `agent.diff`（`swev.rs:102-117`）；`verify` 容器内执行外部判分脚本并产出 `(resolved, note, eval_sha256)`（`swev.rs:145-258`，超时击杀落显式标记行 `swev.rs:194-200`，判分日志字节指纹 `sha256_hex` `swev.rs:261-266`）。

**agent 循环（af-harness）**。执行器外壳 `Opened::run(Launch{...})`（`af/crates/af-harness/src/run.rs:216-236`；`Launch` 全字段 `run.rs:89-108`：spec/run_id/vars/user_message/key/key_refresh/parent/public_key/namespace/spend_cap_cents/tool_spend_cents/budget/order/tools/stop_policy/breakpoint）。单 agent 节点的编译目标=四元组 `AgentSpec{endpoint, context_template, toolset, policy}`（`af/crates/af-harness/src/spec.rs:152-157`，信封 `{"v":1,"body":...}` 拒绝式解码 `spec.rs:174-214`）。

**生命周期 9 op（af-engine）**。工单状态判定引擎是无状态进程：一次进程读 stdin 一行 JSON、写 stdout 一行 JSON 即退出（`af/crates/af-engine/src/main.rs:7-21`；`handle_line` `lib.rs:87-89`）。9 个 op：`bind_line/attach_voucher/release/start/attach_artifact/complete/close/cancel/approve_decision`（`Op` 枚举 `af/crates/af-engine/src/lib.rs:61-71`，`parse_op` 159-177）。响应体 `{"ok":true,"order":...,"engine_version":...}` / `{"ok":false,"error":...,"engine_version":...}`（`Response` `lib.rs:37-45`，注释 83-86）；错误带 `kind`：`BadRequest/RejectionEnvelope/Gate/Decision`（`WireError` `lib.rs:52-59`）。请求可带 `engine_version_min` 语义门（`lib.rs:139-157`）。

**结果记录契约**。执行结果落 `results.jsonl`（append-only，`main.rs:644-648`）。swe-v 成功行 18 键：`suite/task_id/profile/trial/reward/status/scaffold/reasoning_tier/run_dir/eval_sha256/gate/attempts/http_retries/turns/model_calls/tokens{input,output,cache_read}/agent_wall_ms/verifier_note`（`main.rs:861-890`）。任务书所称"15 键"为早期代际口径（fix2 增补 `model_calls/reasoning_tier/tokens` 细分；待确认具体所指代际）。运行终态枚举 `RunStatus`：`Completed{signal}/MaxTurns/ToolFreeLimit/BudgetExhausted{fault}/Stopped{decision}/Unauthorized{...}`（`run.rs:111-131`），另有供给面 `setup_failed/run_failed` 两态（`main.rs:662-667,822-834`）。

### 1.2 v0 契约

**执行单元（Execution Unit）**= 可被统一执行面声明、拉起、观测、记账的最小工作体。v0 认可三种宿主形态，共用同一份声明文件与调用协议：

```jsonc
// unit.json —— 执行单元声明（拒绝式信封 {"v":1,"body":...}，同 AgentSpec 纪律）
{
  "v": 1,
  "body": {
    "unit_id": "u-<名>",              // 命名规则同 is_ref_name（spec.rs:294-296）：字母数字_.:-，≤128
    "unit_version": "<semver>",
    "host_form": "process-cli",        // v0 仅此一种；"stateless-judge"（引擎型）、"human-station"（工位型）为已识别的扩展形态
    "host_class": "any | container-capable",   // 执行宿主要求类别，非具体机器名
    "phases": ["setup", "execute", "verify", "cleanup"],  // 单元声明的阶段（可裁剪）
    "invoke": {
      "argv_template": ["<bin>", "--input", "{{input_ref}}", "--out", "{{output_dir}}",
                        "--selector", "{{selector}}", "--host", "{{host_alias}}"],
      "stdin_protocol": null,          // 非 null 时=单行 JSON 请求/单行 JSON 响应（引擎型）
      "env": { },                      // 只允许非敏感变量；密钥一律走 key_cmd 引用
      "record_stream": {               // 结果行契约（对齐 results.jsonl 语义）
        "path": "{{output_dir}}/records.jsonl",
        "append_only": true,
        "row_schema": "af.plan.record.v1"
      }
    },
    "resource_floor": { "container_mem": "6g", "container_pids": 512 }  // 泛化为通用资源下限
  }
}
```

**统一结果行契约 `af.plan.record.v1`**（执行单元必须按此落行，字段名抽象化）：

```jsonc
{
  "plan_id": "...", "node_id": "...", "item_id": "...",       // 三级定位
  "attempt": 1, "host_alias": "...", "unit_id": "...", "unit_version": "...",
  "status": "completed | max_turns | tool_free_limit | budget_exhausted | stopped | unauthorized | setup_failed | run_failed",
  "verdict": true | false | null,                             // 判定结果；null=无判定（供给面/未跑完）
  "evidence": { "run_dir": "...", "evidence_digest": null },   // 证据目录 + 证据字节指纹（可空）
  "gate": "ok | policy_violation_kind",                        // 完成度门禁记账（泛化 no_patch 类语义）
  "usage": { "turns": 0, "unit_calls": 0, "http_retries": 0,
             "quota": { "input": 0, "output": 0, "cache_read": 0 } },
  "wall_ms": 0, "note": ""                                     // 截断至 ~300 字符的自由文本（对齐 verifier_note 口径）
}
```

**生命周期调用协议**：计划内每个节点的工单语义跃迁，由执行面以 af-engine 9-op 之一驱动（每跃迁一次进程调用，幂等可重放）；节点执行前必须已过 `release` 门（绑定+凭证），节点合格终态工件经 `attach_artifact` 登记后方可 `close`（门控语义见 §5、§7 工单字段）。执行单元自身不持有工单状态——快照整单进出（`lib.rs:4-5` 注释）。

**调用语义**：执行面拉起执行单元进程时 stdin 置 DEVNULL（子进程不继承调度器输入，`tools/factory-sched.py:21,535-537` 教训已固化）；单元以 `record_stream` 落行即视为可观测产出，执行面以行扫描判定续跑集合（吸收 `done_tasks` 语义 `factory-sched.py:217-230`）。

### 1.3 缺口

- 无注册表：套件分发、档案选择均为编译期硬编码 match（`main.rs:613-623` 与 `profile()` 163-327），执行单元声明文件与运行时装载器不存在。
- 结果行契约未标准化：三套件三套行 schema（swe-v 18 键 / tb 12 键 / injec 14 键，`main.rs:861-890,1068-1085,1209-1228`），统一 `af.plan.record.v1` 需要迁移层或新一代 runner。
- `verdict` 与 `status` 的两轴语义目前混在 `reward/resolved` 单字段，且判分脚本路径、解释器路径硬编码（`swev.rs:205-209`）。
- host_class 到宿主别名的映射无声明处（`--host` 直传字符串）；宿主能力（容器可用性、出口形态）靠约定。
- 引擎型（stdin/stdout 单行协议）与 CLI 型尚未在一份声明里统一；`approve_decision` 的调用方（执行面还是组件）未定（待确认）。

## 2. 组件注册接口

### 2.1 现状证据

**模型路由**。`EndpointSpec`：`protocol(OpenaiChatCompletions|AnthropicMessages)/base_url/model/key_ref/reasoning_tier(Off|Low|Medium|High)/stream/auth(Bearer|XApiKey)/max_tokens/temperature_milli/top_p_milli`（`af/crates/af-harness/src/spec.rs:16-95`）。`key_ref` 只存引用名不存明文，禁 `sk-` 前缀与 URL userinfo（校验 `spec.rs:228-236`）。档案→端点的解析是 af-bench 内硬编码 `profile()`：名称 → `EndpointSpec + key_cmd`（`main.rs:158-327`）；密钥解析 `resolve_key` 跑 shell 命令取值，明文不落文档（`main.rs:329-350`；bao-agent 首选+回退双路 `main.rs:208-226`）。401 时 `KeyRefresher` 单次重取（`run.rs:534-574`）。

**记忆/上下文**。`ContextTemplate{system, slots}`，`{{name}}` 槽位字面替换（`spec.rs:98-103,307-320`）；对话快照整段落库 `RunRecord.transcript_json`（`run.rs:833-861`）并在续跑时恢复（`run.rs:359-374`）。**上下文压缩组件不存在**：transcript 在单 run 内只增不减（`run.rs` 无裁剪路径；长对话仅靠供应商端缓存读计数观测，`run.rs:488-493`）。

**工具**。`ToolDecl{name, description, parameters(JSON Schema 对象), effect: Pure|Persist|ExternalOnce}`（`spec.rs:38-45,106-115`）；运行期注册 `ToolRegistry::register(name, handler)`（`run.rs:40-68`）；副作用类经 af-effect-gateway 意图登记+幂等执行（`run.rs:719-779`，幂等键 `IntentKey{workorder_id, step_path, seq}` `run.rs:727-735`）；白名单=规格工具集∩父凭证事实（`af-harness/src/lib.rs:18-22`）。

**领域配置包现状**：提示词是 af-bench 内编译期常量（如 `SWEV_SYSTEM_PROMPT/SWEV_INSTANCE_PROTOCOL`，`main.rs:543-566`）；图模板 `GraphTemplate{graph_version, name, entry, nodes, edges, subgraphs}` 已版本化（`af/crates/af-graph/src/model.rs:26-38`）；优化配方 IR v1（拒绝式信封+JIT 护栏）在 af-dspy-ir（`af/crates/af-dspy-ir/src/lib.rs:1-18`）；产线绑定=`LineBinding{line_id, line_version}`（`af/crates/af-workorder/src/order.rs:33-38`）。

### 2.2 v0 契约

**组件=带类别与版本的声明文件**；执行面侧维护注册清单。五类组件 + 领域配置包：

```jsonc
// component.json —— 组件声明（拒绝式信封 {"v":1,"body":...}）
{ "v": 1, "body": {
    "component_id": "c-<类>.<名>",
    "component_class": "model_route | loop_policy | memory | tool | context_compaction",
    "version": "<semver>",
    "body": { /* 按类别，见下 */ }
}}
```

- **model_route**：`{ "endpoint": <EndpointSpec 原样>, "key_cmd": "<取密钥命令字符串，零明文>" }`。注册即档案：编译阶段 3 以 `component_ref` 引用，不再有调用方硬编码 match。约束继承 spec 纪律：`key_ref` 引用名、base_url 无 userinfo、无 `sk-`。
- **loop_policy**：`{ "max_turns": u32, "stop": <StopCondition>, "stop_policy": <af-stop StopPolicy JSON>, "turn_reminders": <可选策略> }`。推理循环本体（harness drive）是底座固定件，组件只声明参数，不注入代码。
- **memory**：`{ "context_template": { "system": "...", "slots": [...] }, "transcript_retention": "full" }`（v0 仅 full）。
- **tool**：`{ "decl": <ToolDecl 原样>, "implementation": "executor:builtin/<名>" }`——声明进规格，实现必须落在执行面进程内注册表（v0 不做跨进程工具端点；对齐 `ToolRegistry` 现实）。
- **context_compaction**：`{ "policy": "none" }`（v0 显式空实现占位，接口先立、语义后补）。

**领域配置包（domain pack）**：

```jsonc
{ "v": 1, "body": {
    "line_id": "...", "line_version": "...",          // 与 LineBinding 同键（order.rs:33-38）
    "graph_ref": { "graph_version": "..." },           // 图模板版本引用
    "prompt_bundle":   [ "c-memory.<名>@<版本>" ],      // 组件引用表（各 class 一列）
    "route_table":     [ "c-model_route.<名>@<版本>" ],
    "loop_policies":   [ "c-loop_policy.<名>@<版本>" ],
    "tool_bundle":     [ "c-tool.<名>@<版本>" ],
    "unit_bindings":   [ { "unit_id": "...", "unit_version": "..." } ],
    "registry_digest": "<对以上全部声明文件的摘要>"        // 编译阶段 3 绑定快照
}}
```

**绑定与校验**：编译阶段 3 输出的节点带 `component_refs`（各类别一个引用+版本）；执行面装载时按注册清单解析，**引用缺失/版本不符/digest 不匹配一律拒绝启动**（拒绝式信封点名缺失项，对齐 `decode_work_order` 的 `MissingField/UnknownField` 纪律，`af/crates/af-workorder/src/order.rs:144-163`）。工单 `bind_line` 时把 `line_id+line_version` 写入订单（`order.rs:364-373`），domain pack digest 随计划对象携带（§7）。

### 2.3 缺口

- 注册表本体不存在：无清单文件、无装载器、无 digest 计算；档案/提示词/判分器路径全部编译期钉死（`main.rs:158-327,543-566`）。
- 上下文压缩无任何实现可引（只有"需要"这一判断；v0 契约的 `policy:"none"` 是占位，语义待阶段 3 编译目标定稿——待确认）。
- 工具实现注册是进程内代码（`ToolRegistry::register`），跨执行单元共享工具实现无机制；`implementation: "executor:builtin/..."` 的枚举范围待执行面团队定。
- 组件与 `line_version` 的联合版本演进规则（换组件是否必须换 line_version）未定（待确认）。
- af-dspy-ir 优化配方如何回流为 model_route/loop_policy 修订（JIT 闭环）未设计（IR 现状只有 schema+护栏，`af-dspy-ir/src/lib.rs:1-18`）。

## 3. 调度与并行度控制接口

### 3.1 现状证据

**并发上限**。四层：per-(profile×host) `PROFILE_LIMITS`（:82-85；按主机分账防共享配额饿死 :377-382）、类别上限 `RELAY_LIMIT=6/BENCH_LIMIT=24`（:86-87）、per-host `HOST_LIMITS={anolis:14, local:3}`（:90），统一在 `capacity()` 判定（:371-389）。

### 3.2 v0 契约

计划对象（§7）携带 **resources 声明**，统一执行面按声明执行三闸与并发限制；语义继承现行调度器：

```jsonc
"resources": {
  "gates": [
    { "gate_id": "g-<名>",
      "metric": "fs_used_pct | fs_available_mib | mem_available_gib",
      "subject": { "host_alias": "...", "path": "/..." },   // 按需可省 path
      "threshold": 88, "comparison": "lt|gt",                 // 可用类 lt、使用率 gt
      "applies_to": { "node_kinds": ["..."] },                // 闸只拦这些类别的新启动
      "on_probe_failure": "fail_closed",                      // v0 唯一取值
      "cache_ttl_s": 120,
      "action": "block_new" }                                 // v0 唯一动作：拦新不杀旧
  ],
  "limits": [
    { "limit_id": "l-<名>", "scope": "plan | class:<执行单元类> | host:<别名> | route:<model_route 引用>×host",
      "max": 4 }
  ]
}
```

执行语义（均为现行实测行为的泛化）：
1. **就绪**：节点依赖集全终态（done/skipped）才可启动；
2. **准入**：按序检查 class 限额 → host 限额 → route×host 限额（防共享配额被单宿主占满，对齐 :377-382 的教训）；
3. **闸门**：probe 失败或越线 → 本轮不启动该类别新节点；在跑节点不动；读数缓存 `cache_ttl_s` 防探测风暴；
4. **热更新**：图与 limits 以文件为源，改文件即生效，运行态保留；
5. **fan-out**：map 节点按 `max_fanout` 并发展开子图实例；循环节点按 `max_iterations` 有界迭代，安全点缺失的计划拒绝装载（编译期已校验，运行期只信任声明）；
6. **MES 记账**：节点 started/done/partial/failed 事件经 af-mes writer（§4 观测/§6 恢复）写入，不再由调度器裸 HTTP 直写（迁移项，见缺口）。

### 3.3 缺口

- 三闸与四层限额目前是 Python 进程内实现，未沉淀为 af 内可复用库；统一执行面需把 `disk_gate/mem_gate/tmpfs_gate/capacity` 语义原样吸收。
- 闸的 metric 采集是 ssh 命令探测（`df`/`/proc/meminfo`，:403-405,430-437）与本地 statvfs（:460-461）拼装，无统一 metric 接口；新增宿主要逐个写探测。
- 调度器 MES 直写绕过了 af-mes 的 outbox/背压（`af/crates/af-mes/src/writer.rs:123-188`），两套写入路径（writer RowBinary vs 调度器 JSONEachRow HTTP）并存，收敛方案待定（待确认）。
- skipped 依赖态在图中存在（:368）但无产生 skipped 的节点级策略字段（如条件跳过谓词）；af-graph 的 `Predicate`（`af-graph/src/predicate.rs:51`）尚未接进调度。
- 放行闸（af-release-gate CONWIP）与调度准入的关系（串两层闸还是一个）未定（待确认）。

### 4.2 v0 契约

**四层 span 树与注入点**（OTel GenAI 语义约定对齐：`invoke_workflow → invoke_agent → chat → execute_tool`）：

| 层 | span 名 | 注入层 | 载体 | 现有对应物 |
|---|---|---|---|---|
| L1 计划 | `invoke_workflow` | 统一执行面（吸收调度循环后新增） | 执行面进程 | 无（调度器只写 MES 记账事件） |

3. **上下文传播**：执行面在拉起执行单元时经环境（v0：env `AF_TRACE_CTX=<trace_id>:<parent_span_id>` 之类，具体键名待执行面定）传递父 span；执行单元内 trace 以该 trace_id 建树，**替换现行"每 worker 新 trace_id + parent INVALID"**（`otel.rs:130,189-191` 为被改造点）；run_id（attempt 维）与 stable_id（订单维）必须双携带；
4. **MES 与 trace 分工**：MES `mes_event` 只承担记账聚合（line/hour 物化视图，`af/crates/af-mes/src/schema.rs:59-71`），不做 span 载体；判分/审计走 events.jsonl+索引+manifest（含字节指纹与 Merkle 根）；
5. **缺口不变量保留**：任何丢弃必须可对账（`Σ(gap)==gap_counter`，lib.rs:16-20）；流撕裂如实留证（金丝雀 3151-a1 案例，obs金丝雀:69）。

### 4.3 缺口

## 5. 预算执行与熔断接口

### 5.1 现状证据

**凭证语义（订单级）**。`BudgetVoucher{voucher_id, amount: u64, signed: bool}`（`af/crates/af-workorder/src/order.rs:40-46`）；release 门控要求"存在且 signed"，缺失类型化上报 `Missing::BudgetVoucherNotIssued / BudgetVoucherNotSigned{voucher_id}`（`order.rs:405-418`；`af/crates/af-workorder/src/error.rs:12-21`）。凭证只能在 Created 态登记，release 后换绑=绕门控，直接 `MutationForbidden`（`order.rs:364-399,670-690`）。af-bench 当前用法是占位：`amount:1, signed:true`（`bench_order` `main.rs:528-533`）。

**执行级账本（af-meter + af-harness）**。`BudgetLedger{budget_cents, spent_cents}` 是累计真相源，`try_spend` 三拒绝：负数/超 per-call 上限/超累计（`af/crates/af-meter/src/budget.rs:44-101`）；多消费者合并 `merge_consumers`（:117-160）。harness 侧绑定 `BudgetBinding::Cents{dimension, ledger, spend_cap_cents} | Count{dimension, meter}`（`af/crates/af-harness/src/budget.rs:14-25`）；**每轮模型调用前 probe（余额不足不开轮）**（`run.rs:422-423`；模块文档 `af-harness/src/lib.rs:16-17`），工具执行后 charge（`settle_turn` `run.rs:584-589`）；拒绝类型化 `BudgetFault{OverCap, OverBudget, NegativeSpend, InsufficientCount{recovers_at}}`（`budget.rs:187-209`）。预算落库 `BudgetRecord{declared, current}` 分离，**续跑递交的声明必须与首启一致，余额以库为准**（`budget.rs:44-107`）。

**熔断（止损）**。`StopEngine::feed` 事件流裁决：指纹连击 N=3 → `Stop(NoInfluence)`；确定性节点首败 → `Stop(CheckFirstFail)`；错误累计 M=5 → `Escalate`（`af/crates/af-stop/src/lib.rs:5-17,30-39`）；harness 逐工具喂事件，latched 决策 → `RunStatus::Stopped` 终态（`run.rs:643-675,593-596`）。预算耗尽终态 `RunStatus::BudgetExhausted{fault}`（`run.rs:119-121,422-423,586-589`），落 critical trace `harness.budget`（`run.rs:799-814`）。

**凭证链**。父凭证 `RootSpec{tools, namespace, budget_cents:10_000}` 签发（`main.rs:681-686`），衰减出 run 短期凭证；凭证 check 是 per-call（`spend_cents<=spend_cap_cents`），累计由账本管（`af-meter/src/budget.rs:1-13` 文档）。单 run 花费上限：swe-v 300 美分 / tb 100 美分（`main.rs:787,1021`）。

### 5.2 v0 契约

计划对象预算段（节点级+计划级两轴）：

```jsonc
"budget": {
  "voucher": { "voucher_id": "...", "amount": 100000, "signed": true },  // release 门材料（order.rs 语义原样）
  "dimensions": [
    { "dimension": "<名>",                    // 命名规则同 budget_ref.dimension（spec.rs:277-280）
      "unit": "cents | count",
      "per_turn": 1,                           // 每执行轮扣减（BudgetRef 语义）
      "node_cap": 300,                         // 单节点上限（spend_cap）
      "plan_cap": 100000 } ],                  // 计划级上限（对账用）
  "on_insufficient": "stop_node_terminal",     // v0 唯一语义：节点终态 budget_exhausted，不静默、不透支
  "reconcile": { "rule": "sum(node_ledgers.spent) <= voucher.amount",
                 "merge": "merge_consumers 语义" }   // af-meter budget.rs:117-160
}
```

执行语义（全部为现有行为的声明化）：
1. 节点启动顺序强制：`attach_voucher`（signed）→ `release` → `start`；未签凭证在 release 门被点名拒绝（`Missing::BudgetVoucherNotSigned{voucher_id}` 可程序化读取，`error.rs:54-62`）；
2. 执行中余额不足：**开轮前 probe 拒绝 → 节点终态 `budget_exhausted`**（fault 类型化随行），不产生第 N+1 次模型调用；已产生的消耗保留在账本（拒绝不回滚，`af-meter/src/budget.rs:72-101`）；
3. 续跑：余额从落库 `current` 恢复，递交声明与首启不符即拒绝（`budget.rs:77-107`）——熔断后的重试不重复扣历史；
4. 熔断：节点携带 `loop_policy.stop_policy`（§2），止损决策 latched 即节点终态 `stopped`，critical trace 留痕；
5. 计划级对账：执行面收尾时合并各节点账本（`merge_consumers`），超 voucher.amount 视为记账事故上报（v0 只上报不自动处置）。

### 5.3 缺口

- voucher 是布尔占位（bench 挂 amount:1），**签发方/签名机制/与真实计量的换算未定义**（`signed:bool` 无密码学内容；待确认签发主体）；
- 无计划级共享账本：每个 `Launch` 自带独立 `BudgetLedger::new(...)`（`main.rs:789-793,1023-1027`），跨节点合并不发生在执行期（`merge_consumers` 存在但无调用方）；
- 熔断的"确定性节点首败"规则面向 check 型节点，与图节点 kind 的映射（哪个 kind 视为确定性）未接通；
- 预算耗尽后的计划级行为（该节点判失败/整单 cancel/重派）没有声明位（v0 只定义节点终态；计划级策略待确认）；
- count 维度的恢复语义（`recovers_at`）未在调度层消费。

## 6. 失败恢复接口

### 6.1 现状证据

**失败分类现状**。三轴事实：① 终态轴 `RunStatus` 六值（`run.rs:111-131`，`status_label` 映射 `main.rs:579-588`）；② 供给面轴 `setup_failed / run_failed`（`main.rs:662-667,822-834,938-946`）；③ 判定轴 `reward/resolved ∈ {true,false,null}`，null=无判定（infra 不占分母口径，`main.rs:855-860`）。细分机制：HTTP 供给面抖动由 harness 层指数退避重试 ≤5 次并计 `http_retries`（`main.rs:12-13`；`Opened::http_retries` `run.rs:210-212`）；401 密钥过期单次重取（`run.rs:534-574`）；判分桥接超时显式标记（`swev.rs:187-200`）。

**断点续跑（run 级）**。`Opened::run` 对已终态 run 直接返回落库报告不再调模型（`run.rs:133-134` 文档、`bind()` :345-353）；未终态 run 从落库行恢复（transcript/止损快照/预算），**且递交声明（spec/vars/user_message/namespace/花费上限/工单 id/止损策略/白名单/预算声明）与首启逐项相等才准续跑**（`check_decl` `run.rs:376-410`）。提交前断点 `Breakpoint::BeforeTurnCommit`（副作用已落、运行行未提交）验证续跑安全（`run.rs:31-37,609-611`）。

**幂等键（副作用级）**。`IntentKey{workorder_id, step_path:"<run_id>/<tool>", seq: turn*1000+offset}`（`run.rs:727-735`）；重放同一幂等键不重做外部操作，`effect_replays/effect_fresh` 分开计数（`run.rs:759-768`）；at-least-once + 业务幂等键 = exactly-once 的实证见设计文档（`设计/Agent工厂底座_实施方案_v1.md:40`）。

**尝试序号（证据级）**。run 目录按既有同名前缀目录最大序号 +1 递增（a1/a2/…），**绝不覆写旧目录**（`next_attempt_index` `main.rs:594-610` + 测试 :48-73）；证据链：判分日志字节指纹 `eval_sha256`、超时标记行（`swev.rs:194-204`）。

**断点续跑（调度级）**。`done_tasks` 扫结果文件，`run_failed/setup_failed` 不算完成、可重试（`factory-sched.py:217-230`）；跨宿主同键并集去重防重复消耗（`done_union` :233-246）；partial 节点 600s 后重回队列（:683-687）；连续失败 `FAIL_LIMIT=3` → 终态 failed 需人工（`bench_arm_fail` :552-566）。

**账本恢复（MES）**。outbox 攒批：先 `.partial` 写入+fsync+目录 fsync 再改名 `.batch`，发送成功才删，删前崩溃会再送一次（至少一次）（`af/crates/af-mes/src/outbox.rs:84-115,161-167`）；重开丢弃 partial（:46-49,224-231）。

**跨 run 身份**。`WorkOrder::continue_as_new` 换 run_id、`stable_id` 不变且不记状态机履历（`order.rs:309-316`）；分片键只由 stable_id 决定（:303-307）。

### 6.2 v0 契约

**失败四分类**（v0 词汇表，执行面/计划对象共用）：

| 类 | 定义 | 处置 |
|---|---|---|
| F1 供给瞬态 | 传输/限流/密钥过期等可自愈抖动 | 层内退避重试（HTTP ≤5 次、401 重取 1 次），对上层透明，仅计数 |
| F2 环境失败 | 阶段 setup/取证/判分桥接失败（setup_failed/run_failed） | 节点记 partial，按退避重排队；连续 N 次（默认 3）→ 终态需人工 |
| F3 执行终态 | 六种 RunStatus 终态（completed/max_turns/tool_free_limit/budget_exhausted/stopped/unauthorized） | 不重试（语义已终态），按 verdict 决定节点 done/failed |
| F4 判定完成 | verdict=true/false | 节点结论落账，进入依赖解锁 |

**节点恢复预案字段**（进计划对象 §7）：

**恢复总则**：
1. **恢复只信盘上三账本**：run 级状态（harness.db 的 RunRecord，`run.rs:833-861`）、结果行（records.jsonl）、MES 事件（mes_event，at-least-once）——计划文件本身无运行态；
2. **重跑不覆写**：尝试序号单调递增，旧目录是复核证据（D-20 纪律，`main.rs:590-610`）；
3. **副作用重放同键**：断点后重放幂等键不重做外部操作（`run.rs:7-8` 模块文档）；
4. **终态即答案**：已终态 run 重复调用返回同一报告（`run.rs:133-134`）；
5. **跨 run 续接**：长任务换 run 走 continue-as-new（stable_id 不变）；变更图版本走后继工单（`WorkOrder::successor`，`order.rs:225-235`），原单封存。

### 6.3 缺口

- 四分类词汇表未在任何代码/文档统一（现在散在 status/reward/note 字符串；`verifier_note` 是自由文本）；
- 调度级断点续跑依赖扫结果文件（`done_tasks`），无结构化的节点检查点对象；跨节点依赖的中间工件传递只有 mes_event 计数与目录约定，无工件寻址（af-graph 的 Edge=工件引用 `af-graph/src/model.rs:123-137` 只有 schema，无存储实现）；
- `run_failed` 行的根因分类（供给面 vs 判定面 vs 宿主面）无结构化字段；
- 后继工单（supersede）链与调度器状态（图热更新）之间的对应关系未定义（换图版本时在跑节点如何处置——DrainAllInflight/HotTakeover 语汇已存在于 `af/crates/af-workorder/src/error.rs:107-110`，未接调度）。

### 7.2 已定裁决的影响：Tempo 常驻化暂缓，订单语义由 af-engine + ledger + MES 承载

裁决内容以本任务书为准：**不做 Temporal（Tempo）常驻化部署，订单/编排语义由 af-engine（无状态判定进程）+ ledger（本地运行账本）+ MES（追加事件账）三者承载**。书面记录检索情况：`计划/` 与 `状态/` 未检索到该裁决落文（2026-10-24 检索）；`设计/Agent工厂底座_实施方案_v1.md:40,66,98-102` 仍是第一阶段"选 Temporal、薄壳形态"的旧方向，本裁决为其在第二阶段的替代——**出处待确认，按任务书执行**。

对契约的直接约束（本文各节已按此收口）：

1. **计划对象必须自含**：没有 workflow 引擎历史可回放，§7.1 单文件即编排真相；运行态只存在于盘上三账本（run_store/records/mes_events，§6.2），恢复=重装计划+重读账本。
2. **生命周期跃迁=引擎 op 调用**：9-op 进程式调用（一次一行 JSON，`af-engine/src/main.rs:7-21`）天然无状态可重放；`engine_version_min` 语义门（`lib.rs:139-157`）承担规则演进兼容——计划对象可在 compiled_from 里携带该下限（v0.1 增补位，待确认）。
3. **审批/决策门不依赖常驻等待**：`approve_decision` 以决策工件+被签 payload 校验闭环（payload 绑 stable_id 与 graph_version，`lib.rs:239-255`、`order.rs:285-301`）；执行面重启后重查工件即可，无 signal 队列语义。
4. **长任务续接原语**：continue-as-new（stable_id 不变，`order.rs:309-316`）+ 后继工单（supersede，:225-235）承担"跨 run/换图版本"两种续接，替代 durable engine 的 run 续接。
5. **at-least-once + 幂等键是恢复地基**：MES outbox（§6.1）、effect gateway（§6.1）、调度重排队（§6.1）三层都建立在其上；契约中所有"恰好一次"效果只能由幂等键达成，不可假设传输层保证。
6. **放行闸走库形态**：af-release-gate 以执行面进程内库接入 release 前 admit（`af/crates/af-release-gate/src/lib.rs:1-9`），不引入常驻编排服务。
7. **观测的 L1 层（invoke_workflow）由统一执行面进程承担**（§4.2），不再有 workflow 引擎自动产 span——这是吸收 factory-sched 后执行面必须新建的注入点。
