## 1. 观测什么：schema 定稿（v1，swe-v 跑测路径）

### 1.1 设计原则（素材原文锚定）

调研结论 §2.1 的四层观测收敛结论，本 schema 逐条对应：

> 「**确定性结果行是主数据源**……但二值 reward 统计功效太低——必须解析判分器输出的**分级连续量**（FAIL_TO_PASS 成功/失败数）……**所有行必须携带身份与指纹**：run_id、task_key、profile、scaffold、判分器 eval_sha256、配置指纹……**缺任一项 → 不可归因，作废**。」
> 「**新增观测落独立 sidecar**（资产账本、评审标注库、指纹字段），不动判分账本本体——本地判分账本是『声明不符即拒绝打开且不迁移』的指纹库，加列属于高风险动作。」

落进实现的三条铁律（代码证据）：

1. **观测不闸断测量**（红队⑤修复，`/tmp/af-wt-obs/crates/af-bench/src/main.rs:826-830` 注释「观测失败不闸断测量」）：事件流建不起来时 stderr 告警、results.jsonl 照写——测量语义零变化，结果代号不变（e508c49 提交语）。
2. **append-only 证据流**：run 目录避让改名 `-x2` 不覆写（`obs.rs:328` 「目录已存在且有事件时按 -x2 递增避让（不覆写证据）」，D-20 同名覆写前科防线）；段名白名单 `^[A-Za-z0-9._-]{1,64}$` 拒绝 `.`/`..`（`obs.rs:53-68`，D-14/D-22 防线，含 AF_OBS_BATCH_ID 目录穿越封堵 `obs.rs:492-494`）。
3. **单一时间源**：ts_finished 由 `RunObs::finish` 取一次钟同时写进事件与索引行（`obs.rs:783` 注释「曾因两处各取一次钟被 checker 的互校抓出不一致——这是互校的设计目的」）。

### 1.2 事件信封与词表（12 类）

每行事件 = 信封 + payload（`obs.rs:367-391`）：

```json
{"ts_ms": 1792621647931, "seq": 0, "level": "normal", "kind": "harness.run_started", "payload": {…}}
```

- `seq` 在文件锁内分配，文件顺序与 seq 严格一致（红队②⑥修复，`obs.rs:363-369`）；
- `level=critical` 的事件保留 `sync_data`（fsync），normal 只 write+flush（本盘实测 fsync 8.195ms/次×70 事件 ≈0.6s/run 的主路径税，`obs.rs:363-365` 注释）——终态/重试耗尽/重取/判分是「必须不容错」的行。

词表与 level 配对（与 `工具状态备份/observability/obs-checker.py:59-71` KIND_LEVEL 一致，词表只增不改，改词表必须与 checker 同一提交）：

## 3. 怎么存储：布局、容量、备份与保留期

### 3.1 容量实测与外推

实测（本会话 `du`）：事件流 ≈306 B/事件（3151 run：31,857 B / 104 事件）；观测根现存 runs/ 424K、index/ 36K。外推：单 run 平均 ~150 事件 ≈ 46 KB events.jsonl；S2 组级 A/B 满配 1,680 runs（调研结论 §5.2 选项①）≈ **78 MB 事件流** + 索引 1,680 行 ≈ 0.5 MB——事件层全量永久保留**无容量压力**。重的是 run 目录里的 trace.db/harness.db/eval 日志（bench-obs4-out 实测 4.2M/4 run ≈ 1 MB/run 量级，长跑轨迹更大），这部分才需要保留期策略。

### 3.2 存储纪律（含 D-24 红线）

1. **落盘位置**：观测根固定在 `/home` 盘（工具状态备份/observability）；`resolve_root()` 在二进制内拒绝内存盘（§1.5），环境变量覆盖同样受检——D-24「全部结果目录/runs 在 /tmp（tmpfs）」的观测侧根治。
2. **判分与测量产物不混居**：af-bench `--out`（results.jsonl + runs/ legacy 布局）的迁盘属 D-24 归还路径（资源管理组统一方案），本方案只约定：**观测根永不随 --out 走**，两者以 run_id + index 行 `path` 字段互链。
3. **写路径幂等与避让**：目录冲突 `-x2` 避让不覆写；索引行 append+fsync；manifest 一次写整文件。
4. **零明文密钥**：事件流不落 key/token（run_started 只落 base_url 与 model 名，无鉴权字段——run_started payload 亲读核对）。

### 3.3 备份与保留期

先例：真相战役证据已做耐久备份（`工具状态备份/truth-20261021/`）；keepalive 已对图文件做 ~10 分钟级快照（`工具状态备份/factory-graph.*.json` 序列）。观测数据的证据等级与真相证据同级（判分争议、RSI 双门、A/B 结论都引用它），备份策略如下：

| 对象 | 热/冷 | 保留期 | 备份方式 |
|---|---|---|---|
| index/runs-YYYYMM.jsonl + batch manifests | 永久 | 永久（审计链根） | 每月末 tar 入 `工具状态备份/observability-archive/<YYYYMM>.tar.zst` + sha256 清单；tar 后原文件不删 |
| runs/**/events.jsonl | 热 | ≥90 天热存，之后 zstd 压缩就地冷存（**不删**） | 随月度归档 tar |
| runs/**/trace.db、harness.db、eval 日志等重产物 | 热 | 30 天热存；涉及未决判分争议/regrade 窗口的不压缩不清理；到期压缩冷存 | 随月度归档 |
| results.jsonl（测量面，--out 侧） | 按 D-24 迁移方案 | 沿用产线现行代际隔离纪律（fix<N> 结果不跨代比较） | 产线既有纪律 |
| 校验与告警流水 | 永久 | 永久 | checker 输出与 watchdog 告警随巡检日志归档 |

四条硬规则：
1. **观测证据只增不删**（D-20 同名覆写曾制造假阴性、D-31 agent.diff 缺未跟踪文件的教训——证据链任何"清理"都可能销毁翻案材料；删除类操作一律先归档后提请厂长裁决）；
2. 月度归档 tar 完成 -> 即时校验（解包抽验 merkle 与 sha256）-> 才算备份成功，失败记安灯；
3. 归档目录与观测根同盘不同目录（工具状态备份/ 下），**不引入跨机备份承诺**——anolis 侧备份（D-27 跨机监督未还）不在本方案范围，如实留空。
4. **证据更正协议（终审 O1 立，2026-10-22）**：观测证据派生值的修复（如 run_finished 的 tokens 实算、索引行/manifest 随新字节重导）必须三步齐全——①**归档原字节**：修复前 events.jsonl 连同其 sha256 落 `工具状态备份/observability-archive/corrections/<run_id>-<ts>/`，不得只留修复后字节；②**追加更正记录**：以 correction 行/事件（字段名、旧值、新值、依据提交 rev、操作人与时点）追加进证据链，词表新增须与 checker 同提交（§1.2 纪律，**2026-10-22 已落码：词表第 12 类 `harness.correction` + 写侧 `obs.rs::append_correction` + CLI `--obs-correct` + checker 第 12 项校验，af@59c1d6c，索引行/manifest 永不改写、钉住归档原字节——合成正/负/链式实测见状态账 §10.2**）；③**变更日志补记**。**已发生的 obs-smoke2/2905 案例（08:08:33 原地重导出）原字节无留存**——登记为既成破口：该流 run_finished 三字段为修复后值，修复前值（tokens=0）不可复原，索引行与 manifest 的 merkle 钉的是修复后字节；后续对该流的争议按「派生值修复、非伪造」口径处理，新值可凭修复提交 `d73338e` 独立复算验证（Σusage=50199/238139/2049160）。**教训**：append-only 在唯一一次真实压力下被绕过且无法自证——本协议即补该破口。
