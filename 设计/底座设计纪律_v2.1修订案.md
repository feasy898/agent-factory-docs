# 底座的设计纪律 · v2.1 修订案：用户无关性（反特化）

> **修订动因**：产品是一座任务无关的 agent 工厂**底座**。软件的规律是：feature 每增多一分，产品的未来性（futurity）就减少一分；要让 feature 不吃掉未来性，每个 feature 必须以抽象的形态进入，而不是以场景的形态进入。本轮审查发现 v2 及其后的专家采纳已出现明显特化——把"某一个运营者（包括老板本人）的具体处境"写成了产品设计。本修订案确立反特化纪律，并把已特化的元素重新归位。
> **日期**：2026-10-18

---

## 一、诊断：特化发生在哪里，为什么会发生

### 1.1 特化清单（现形的不合格品）

| # | 元素 | 它其实是什么 |
|---|---|---|
| 1 | **订阅 plan 余量路由器**（5 小时/周限滚动窗、海绵队列、高优专用账号、"个人订阅当产能"） | 是**某一个运营者的资源采购组合**。别的运营者可能全用 API、全用自建集群，或混合任意供给 |
| 2 | **交货期三档 / 15:00 截单次日达 / 按合格交付计价 / 预付额度包** | 是**某一个商家的定价与承诺方式** |
| 3 | **夜间预置 30% / 首件闸门 / 攒批每日集中开机** | 是**某一种排班与产能形状**（白班制、夜间电价、自有 V100）下的调度策略 |
| 4 | **评审校准方法论**（SPRT 样本量、POD 曲线、IRT 难度加权、TIP 比喻、计件系数 0.8-1.2） | 是**某一套人力管理制度**的参数 |
| 5 | **采购分级/期权/分批 1/3** | 是**某一个采购哲学** |
| 6 | **TDABC 会计口径、闲置产能单列** | 是**某一个财务制度** |
| 7 | JIT 升迁阈值（10 次/90% 一致性/50 次/99%）、CSP 参数（i, f）、WIP 余量系数 α=0.3-0.5 | 是**合理的默认值，却被写成了法律** |
| 8 | 订阅条款封号风险应对（备企业版/API 合同） | 是**某一个采购决策**，不是产品功能 |

### 1.2 流程根因（比清单更重要）

1. **红队与专家都以具体场景攻击**——"30 个 Run 跨夜等白班""订阅快过期""客户按自己标准整批拒收"。场景是对的（试金石就该具体），但**解药被以场景的形状直接写进了设计**，中间缺一道"这个场景背后的一般机制是什么"的强制工序。
2. **"老板=第一个用户"走了特权通道**：我自己的资源组合（个人订阅、白班、海南）天然离设计者最近，最容易滑进内核。
3. **"采纳"这个动作没有分层**：专家建议要么采纳要么不采纳，没有"采纳到哪一层"的问法。

## 二、修订后的第一原则：底座三无关

v1 有"任务无关"；本修订补全为三条，任何内核元素必须同时通过：

1. **任务无关**（原有）：换一种产品（代码/视频/文章/研究），底座零改动。
2. **运营者无关**（本轮新增）：**换一个运营者——不同的资源供给组合、人力制度、商业条款、合规立场——零内核改动可运行**（允许加载契约内的插件/适配器；"零代码"不可证伪，故标准定为"零内核改动"）。他的一切差异都能表达为配置、配方或契约内插件。
3. **部署形态无关**（明确化）：本地与云的比例、常驻与按需的形状，是配置不是架构。

推论：**老板本人也只是用户一号**。他的订阅组合、排班、定价，和未来任何客户一样，以"运营者配置"的形态进入系统，没有任何特权通道。

## 三、新增判据（接在原五判据之后）

- **判据 6 · 第二运营者测试**：取两个运营者之间的**差异**——若满足该差异需要改内核代码，则承载这个差异的内核元素即为特化（注意：是"差异"不需要改内核，不是"共性"；共性恰恰应该进内核）。防自我欺骗条款：第二个运营者不能由设计者虚构——画像须由第三方预注册（见 §八）。
- **判据 7 · 抽象归化测试**：任何新需求先问"能否表达为既有抽象的参数化"；不行再问"是否值得成为新机制"（须过三无关+判据 6-9，写进内核）；只是场景的，只能成为配方或运营手册。
- **判据 8 · 默认即数据测试**：**内核代码中出现策略常量即缺陷**。一切阈值、系数、规则、默认行为以配方数据存在——带版本、可 fork、可回滚、可按产线覆盖。**且本判据同样拦截两类结构性特化**：①封闭枚举（如"三种供给形态"——枚举必须可扩展或可组合）；②硬编码的状态机拓扑（状态与迁移必须可配）。配方 schema 本身同样受三无关与归化测试约束——**配方层不是法外之地**（防"逻辑即数据"后门：任何场景都能写成一条规则表达式混进数据层）。
- **判据 9 · 内核预算测试**：内核机制**按件数记账**（不按出身——"由场景件抽象而来"不减计数）；一等抽象基线 13 个。新增抽象或内核机制须完备性论证，论证须第三方（红队）评审通过，不允许自证。

## 四、产品四层形态（整个产品应该如何设计）

```
L4 运营者空间（配置·Git+CUE 独立命名空间·对底座只读）
     资源供给组合、费率与定价、日历与排班、商业条款、合规立场、采购策略
L3 配方库（随产品发布的默认配置·同样是数据·可 fork 可回滚）
     调度与放置策略、JIT 升迁/降级阈值、CSP 采样参数、校准注入率与样本方案、
     止损指纹库、时限→优先级映射、渐放（首件闸门）参数
L2 适配器层（插件接口·两侧都是数据契约）
     供给计量 provider、外部系统连接器、交付渠道、内容分类器
L1 内核（机制·唯一允许"写代码决策"的层）
     七抽象 + 六扩展抽象 + 规则引擎壳（CSP 采样/升迁降级/投放闸/采样注入/止损）
     + Meter 计量器 + 通用日历 + 观测与安灯
```

三条关键边界：

1. **JIT 的可写边界=本租户的配方 fork**。它可以提案修改自己 fork 的配方（人批准生效），**不可触碰内核，不可提案修改发行默认配方，对运营者空间只读**。这是宪法 4"程序性=数据"的自然延伸：**策略也是数据**——内核只有机制，机制只认配方。
2. **配方库随产品发行，但不比用户配置更高贵**：同一个 Git+CUE 仓库的不同命名空间，产品升级可以带新默认配方，运营者 fork 后自行演进——升级不覆盖；**冲突时运营者空间覆盖发行默认**（L4 盖 L3），合并只作为人工中介建议，永不自动改写运营者配置。配方中的可执行部分（规则表达式）限定为**类型化受限 DSL**（无图灵完备、无副作用、可静态校验），DSL 本身纳入抽象预算——防止"改不了内核就往配方里写程序"的后门。
3. **适配器准入判据**：适配器**只翻译、不决策**——它的职责是在外部世界的数据格式/协议与底座契约之间转换；一切判断逻辑（路由、阈值、放行）必须上浮到配方或内核，藏在适配器里的决策逻辑按特化处理。"两侧都是数据契约"只约束 I/O 不约束逻辑，故本条为强制评审项。

## 五、逐项重安置表（把 1.1 的不合格品重新归位）

| 特化元素（原形态） | 内核得到的机制（真正进设计） | 配方/运营层得到的 |
|---|---|---|
| 订阅 plan 余量路由器 | **Meter 计量器抽象**：端点池的供给状态是一等路由信号。Meter 是**可组合、可派生的表达式**而非封闭枚举——支持嵌套窗口（日限套周限）、多计量取 min/max、派生计量；三种常用形态（存量型/窗口型/并发型）仅作**配方预置**而非内核枚举；过期时区由 meter provider 报告，与运营者日历解耦。路由器统一消费"端点余量"信号，对供给形态无感知 | 配方：余量感知路由策略（快过期先用/匀速消耗/预留高优）与三种 meter 预置；运营者：接入了哪些供给=适配器+配置；"海绵任务"=既有可延迟优先级类+**Run 的可抢占/可恢复属性**（见下行）的参数化 |
| 交货期三档/截单时间 | WorkOrder 的 **SLA 字段族**（时限/优先级）+ **调度提示接口**（时限→优先级的映射是它的一个 provider，而非独立内核引擎）；**截单点不是一等字段**——由日历+时限偏移派生 | 配方：三档映射（作为 provider 的默认实现）；运营者：档位命名与定价 |
| 夜间预置 30%/首件闸门/攒批 | **时间窗放置偏好**（放置策略的通用参数；容量池与常驻策略同为日历消费者）+ **渐放机制**（任何配置变更上线先小流量、按**评估谓词钩子**判定放量——首件闸门是"0% 起点+门控放量"的实例） | 配方：夜间窗口、渐放比例与谓词；运营者：班表与电价 |
| （红队补）海绵任务的抽象遗漏 | **Run/TaskGraph 的可抢占性与可恢复性显式属性**（可延迟≠可抢占≠可迁移——软驱逐、checkpoint-resume、容量回收语义落在 Run 属性上） | 配方：哪些工作类可抢占/可恢复 |
| 班次日历 | **通用日历抽象**（班次/假日/时区/多日历并存），人工工位与 SLA 计时引用日历实例 | 运营者：真实班表 |
| 评审校准体系 | **已知答案注入器**（对任意工作队列按率注入金标件，并带**拦截契约**：金标件未按预期被拦下即告警——同一机制服务评审校准/评估器金丝雀/客户对齐）+ 行为信号 trace schema + **CSP 采样状态机**（全检→比例抽检→回退，拓扑可配可关，通用） | 配方：注入率、指纹规则、样本量方案；手册：POD/TIP/IRT 方法论文档 |
| JIT 阈值 | 升迁/降级**规则引擎**+熔断（机制） | 配方：10 次/90%/50 次/99% 等默认值，按产线可覆盖 |
| 采购分级/期权 | 容量规划器只产**瓶颈卡/TTB/影子价格工件**与安灯事件（测量是底座的事） | 运营手册：怎么买（分级/期权/分批）是运营者决策 |
| TDABC/定价/按合格计价 | 成本事件归集到工件血缘的**机制**（费率本身是配置） | 运营手册：会计口径、定价方案 |
| 密文寻址三条 | **个人数据命名空间**可选机制（开关式，默认关） | 运营者：是否启用 |
| 订阅条款风险 | 无（不进产品） | 运营者检查清单：核对条款、备替代供给 |

重安置的净效果：内核少了一个"订阅路由器"式的具体件，多了 Meter/日历/注入器/渐放/映射引擎五个通用件——**内核件数基本持平，但每件的形状从"解决某场景"变成"通用机制+配方实例"**。

## 六、需求进入纪律（防复发的工序）

**四级吸收漏斗**——今后一切输入（红队/专家/用户/老板本人）必经：

```
第零通道（缺陷/安全/合规阻断类）：直接修复，不进计数、不走漏斗——
  "等第三次出现"对缺陷与安全事故是荒谬的。判定权在评审，防止滥用为后门。
场景 → ① 能否参数化进既有抽象？（多数在此终止）
      → ② 是否成为新机制？（过三无关+判据 6-9，写进内核，计入预算）
      → ③ 是否成为配方？（带版本的默认数据）
      → ④ 是否只是运营手册/检查清单？（不进产品）
```

配套四条：

1. **延迟抽象（rule of three）**：拿不准的需求先进配方库兜着；**第二次出现**标记为候选机制；**第三次出现**（即第二个独立运营者/场景真实复现）才升格机制，升格时旧配方降为默认配方。宁可配方多兜一阵，不过早固化错误抽象——错误抽象比没有抽象更伤未来性。
2. **否决日志**：被判定为"纯场景"的需求登记在案（一句话+理由），防止反复重提；若它将来以更强的共性重新出现，按 rule of three 走。
3. **抽象预算**：13 个抽象为基线；新增须完备性论证，优先考虑把新能力归并进现有抽象（例如 Meter 归并进 Credential/端点池的语义，而不是另立门户）。
4. **无特权通道**：运营者（含老板）的一切需求以"我的配置"提交，产品侧只评审"抽象是否被穷尽"，不看场景多急。

## 八、一个验证性例子："我的工厂"如何在底座上配置出来

用这套底座，老板（用户一号）的工厂**不写一行代码**，只提交一份运营者配置 + 若干配方 fork：

- 资源：接入两个个人订阅（各挂一个窗口型 meter provider）+ 一家按量 API（存量型 meter）+ 本地 V100 池（部署形态配置：常驻=低，跑可延迟类）；
- 排班：一张白班日历（8×5），人工工位引用它；
- 商业：三档交期（在订单 SLA 映射配方里命名"经济/标准/加急"），按合格交付计价的规则写在运营手册里由人执行；
- 合规立场：个人数据命名空间=关（海南、企业内部客户）；
- JIT：用发行版默认阈值起步，跑两个月后 fork 配方自行调参。

第二年来了用户二号：一家全 API、全球分布式团队、7×24 排班、对欧盟出口（启用个人数据命名空间）、嵌套限额供给（月额度套日额度——用组合 Meter 表达，而非新机制）的视频工厂——同一内核，另一份配置。

**本节的通过判据（防循环验证）**：用户二号的画像由第三方（红队）**预先注册**、不由设计者虚构；验证方式不是"文档上跑通"，而是可执行的两条——①接入第二种真实供给形态时**内核 diff = 0**；②用户一号的既有配置在内核升级后**原样可运行**。两条任一失败，本修订案作废重来。

## 九、自研清单修订

- **内核新增**（机制）：Meter 计量器、通用日历、已知答案注入器、渐放机制、时限-优先级映射引擎、CSP/升迁规则引擎壳。前五个全部是从原"场景件"抽象化而来，不是净增。
- **内核删除**：plan 余量路由器（并入 Meter+路由配方）、夜间预置策略（并入时间窗放置配方）、具体校准方案（并入注入器+配方）。
- **新增工作物**：配方库的初始内容（把专家给的合理默认值全部收进配方而非内核）；运营手册模板（定价/采购/校准方法论进文档）。
- **流程新增**：四级漏斗 + 否决日志 + rule of three 登记表，作为设计评审的固定工序。
