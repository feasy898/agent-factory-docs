## 一、这个产品是什么（以及认知上最重要的一个转变）

**一句话**：我们在造的是一个 **Agent 工厂底座**——一套软件产品，任何人（第一个"任何人"是我们自己）在它之上提交一份配置，就能开出一座自己的"黑灯工厂"：用 AI agent 无人值守地生产代码、视频、文章、研究报告等数字产品，质量可验证、成本可核算、人的介入逐步减少。

**最重要的转变**：此前我们一直说"建一座工厂"。按新纪律，这个说法要修正为——

> **我们造的是"工厂底座"这个产品；我们自己那座工厂（海南、订阅混合供给、白班制），只是用户一号的部署实例。**

这个转变不是文字游戏，它决定每一个设计决策的去向：一个能力进来时，问的不再是"我们的工厂需要吗"，而是"**任何一座工厂都需要吗**"。需要的进内核；某座工厂才需要的，进那座工厂的配置或配方；只是经营手段的，进运营手册。老板本人没有任何特权通道——你的需求同样被抽象成配置。

**产品交付物因此有五件**：
1. **内核**——机制运行时（第七节清单）；
2. **配方库**——随产品发行的默认参数与策略（调度、关灯阈值、校准方案……），是数据不是代码，可复制可改可回滚；
3. **运营者配置模板**——"开厂向导"：接入你的资源供给、排班日历、商业规则、合规立场；
4. **适配器 SDK 与参考适配器**——连接外部供给（各类模型来源）、外部系统、交付渠道的插件接口；
5. **运营手册模板**——定价方法、采购策略、人员校准方法论等纯经营知识，以文档形态随产品提供，不进代码。

我们自己开厂 = 部署内核 + 提交运营者配置 + 使用发行配方。这个"吃自己狗粮"的部署同时是产品的第一个验收现场。

## 二、设计宪法与纪律（拍板对象之一：产品的"法律"）

### 2.1 三无关（底座的存在前提）

| 原则 | 含义 | 检验方式 |
|---|---|---|
| **任务无关** | 换一种产品（代码/视频/文章/研究），底座零改动 | 三个验证场景走通（改代码 / 每日自动重构 / 视频质检） |
| **运营者无关** | 换一个运营者（不同的资源供给、人力制度、商业条款、合规立场），**零内核改动**，只换配置/配方/适配器 | 第二运营者测试（见 2.3） |
| **部署形态无关** | 本地与云的比例、常驻与按需的形状，是配置不是架构 | 同一内核跑"全本地""全云""混合"三种形态 |

### 2.2 九条宪法（五条原有 + 四条修正案；2026-10-19 按拍板修订：控制面位置降为配置、决策工件增加多参与者权限、原"可删除性"条款整体删除——数据合规属运营者配置层事务，产品方案不再出现）

1. agent 之间只传工件引用，不传消息（可复现性的根基）；
2. 数据流图，不是自由对话拓扑（可分析性的根基）；
3. Trace 是正式接口，从第一天版本化（编译器的语料）；
4. agent 的程序性是数据不是代码（统一 harness 内核——即统一的 agent 执行器外壳——加"四元组"配置：端点、上下文模板、工具集、策略参数，也就是"一个 agent 是什么"的四项描述）；
5. 控制面的物理位置（本地/云/混合）是**运营者的部署配置，不是内核立场**——内核对部署形态中立，不劫持这个决定；不变的是安全属性：凡被声明为信任层的组件（凭证签发、预算记账、trace 完整性），无论部署在哪里都同等保证完整性，且信任边界的声明本身是显式配置；
6. 一切决策皆工件——人的批准/驳回/修订与机器决策同等物化为签名工件，告警系统只是传话筒不是事实源。**工厂不是单人系统**：人类参与者以角色进入（运营者、评审、仲裁、只读观察者……），各带不同的读写权限；每个决策工件记录决策者身份与其当时的权限，权限由凭证体系统一承载；
7. 版本贯穿——产线定义版本（graph_version）写进每条 trace、每个工件、每次发布，事故可按版本定位；
8. 副作用显式——每个工具声明状态语义（纯函数 / 需先落盘 / 一次性外部操作须走副作用网关），恢复不重复执行；
9. 资源预算要么硬闸要么显式降级——预算的计量维度是**可声明的**（token/美元、GPU 时、沙箱并发、人时只是配方预置的四个维度，存储、外部 API 配额等可按需声明）：凡声明为预算的计量，要么可拦截、要么必须明说"只记账不拦截"。

### 2.3 九条判据（宪法的执法标准）

判据共九条：**原五条运行判据**沿用自第一版架构（不可旁路测试、多主体复用测试、失效半径测试、接口稳定性测试、机制/策略分离——判定一个功能属于哪一层的老五样，此处不重复全文），加**新四条纪律判据**：

- **第二运营者测试**：两个运营者之间的**差异**若需要改内核才能满足，承载该差异的内核元素即为特化，必须移出。防自欺条款：第二个运营者的画像不得由设计者虚构，须第三方预先注册；最终验证标准是可执行的两条——接入第二种真实供给时**内核代码 diff 为零**；用户一号的旧配置在新版内核上**原样可运行**。
- **抽象归化测试**：新需求先尝试表达为既有抽象的参数化；不行才允许成为新机制；只是场景的，只能成为配方或手册。
- **默认即数据测试**：内核代码里出现策略常量（阈值、系数、枚举、写死的状态流转）即缺陷。配方层同样受三无关约束——配方里的可执行规则限定为**类型化受限 DSL**（无图灵完备、无副作用、可静态校验），防止"改不了内核就往配方里写程序"的后门。
- **内核预算测试**：内核按件数记账（不因"从场景抽象而来"减免），当前基线 = 13 个抽象 + 13 个机制（第五节逐项编号，共 26 件）。新增须第三方评审的完备性论证。

### 2.4 需求进入工序（防复发的流水线）

一切输入（红队、专家、客户、老板本人）必经四级漏斗：**参数化进既有抽象 → 升格为新机制（过全部判据）→ 降为配方 → 写进运营手册**。两个安全阀：**第零通道**（缺陷/安全/数据损毁类直接修复，不计数不排队）；**rule of three**（拿不准的需求先在配方层兜着，第三个独立场景真实出现才升格机制——宁可慢一步，不过早固化错误抽象，错误抽象比没有抽象更伤未来性）。被否决的"纯场景"进否决日志，防止反复重提。

## 三、产品四层形态（产品的构成方式）

```
┌─────────────────────────────────────────────────────────┐
│ L4 运营者空间（每座工厂自己的配置，对底座只读）              │
│    资源供给组合 · 排班日历 · 商业条款 · 合规立场 · 采购策略    │
├─────────────────────────────────────────────────────────┤
│ L3 配方库（随产品发行的默认值与策略，版本化数据）             │
│    调度与放置策略 · 关灯阈值 · 采样参数 · 校准注入率 · 止损指纹 │
├─────────────────────────────────────────────────────────┤
│ L2 适配器（插件：只翻译、不决策）                           │
│    供给计量 provider · 外部系统连接器 · 交付渠道 · 分类器      │
├─────────────────────────────────────────────────────────┤
│ L1 内核（机制，唯一允许"写代码做决策"的层）                  │
│    13 个抽象 + 规则引擎 + 计量器 + 日历 + 观测安灯 + JIT      │
└─────────────────────────────────────────────────────────┘
```

**四条边界规则**（这层的定义就靠它们）：

1. **JIT 编译器的可写边界 = 本租户的配方副本**。它可以提议修改你 fork 出来的配方（人批准生效），不可触碰内核、不可改发行默认配方、对运营者空间只读。优化器优化的是配方，永远不是产品。
2. **运营者配置覆盖发行默认**（L4 盖 L3），产品升级永不自动改写你的配置，合并只作为建议。
3. **适配器只翻译不决策**——格式与协议转换可以，判断逻辑（路由、阈值、放行）必须上浮到配方或内核，藏在适配器里的决策按特化处理。
4. **内核只认配方**：一切机制的参数行为由配方驱动，发行配方是"出厂设置"，与用户配置同库不同命名空间，没有特权。

## 四、内核的十三个抽象（产品的主干词汇表）

每个抽象一段白话。它们是"任何一座 agent 工厂"都需要的通用概念，与具体生产什么、谁来经营无关。

**七个基础抽象**：

1. **Run（执行单元）**——类比"进程"。一次有界的 agent 执行：领一张短期凭证（里面写着能用什么工具、花多少钱）、有生命周期（执行中/等待中/挂起/终结——核心四态为最小完备集，允许注册扩展子状态）、可以打检查点后暂停恢复、声明"可否被抢占/可否恢复"（供调度在资源紧张时软驱逐它）。Run 的稳定身份挂在订单上，执行引擎的内部编号只是实现细节——长任务在引擎里"续跑换段"不影响预算、追溯与成本账的连续性。
2. **Artifact（工件）**——类比"git 里的文件对象"。一切产出都是不可变的内容寻址块：改了就是新对象，同输入同转换直接命中缓存，任何成品能回溯全部祖先。人的审批与修订也是工件（带签名的决策记录，含决策者身份与当时权限）。
3. **Task Graph（任务图）**——类比"编译器的中间表示"。生产流程是声明式的图：节点是转换、边是工件依赖；支持受控分支、受控循环（有安全点的循环才能长期跑）、动态展开（分析完仓库才知道要开几条子线——"数量运行时才定"是合法表达）、一等人工节点。节点分四型（调模型的 / 人工门 / 确定性检查 / 纯数据变换——**预置分类，可注册新节点类型**）——确定与不确定成为类型属性，"关灯"统计因此有客观口径。
4. **Credential（凭证）**——类比"可打孔的车票"。全厂唯一签发点签发的短期凭证，编码工具白名单、工件命名空间、模型端点、多维资源预算（计量维度可声明：token/美元、GPU 时、沙箱并发、人时等为配方预置维度）；派生子 agent 时凭证只能收紧不能放宽；过期自动作废。权限词表与授权判定绑定，有效权限 = 策略引擎允许 ∩ 凭证持有。
5. **Trace（过程记录）**——类比"飞机黑匣子，但是正式接口"。每次模型调用、工具调用、决策点的结构化事件流，从第一天版本化；关键事件同步落盘（宁停勿丢），普通事件异步但有"缺了多少"的诚实计数；签名加 Merkle 锚定到外部见证——产生记录的 Run 自己事后改不了历史。它是编译器唯一的语料，也是审计的基线。
6. **Evaluation（评估）**——类比"质检规程"。对工件的可复现判定，输出三态：通过 / 不通过 / **需人工**（第三态触发安灯，人不在场也能安全运转的关键）。评估可以发生在三个位置：工具内部的即时反馈（编译器报错）、工序之间的门禁、订单终检。评估函数本身也是版本化工件，且在优化器的可写范围之外。
7. **Tool / Skill（能力）**——类比"系统调用"。agent 的一切外部能力经进程外 broker 验权后在沙箱内执行；Skill（打包的能力）带签名，装载时验签不可跳过；产生外部副作用的操作必须经副作用网关（先记录意图、可撤回窗口、防重复执行的幂等键、防"旧节点诈尸"的 fencing 令牌）。

**六个扩展抽象**（红队证明只有七个不够，如实扩编；全部通过三无关测试）：

8. **Trigger（触发器）**——订单不必都是人下的：webhook、定时、信息源变化、上游工件更新，都可以自动派生订单。事件是消息不是命令——触发内容只进收件箱等待确认，绝不直接执行。
9. **Channel（流式产物通道）**——有些产品没有"终态"（持续刷新的仪表盘、直播字幕）：通道=当前版本指针+保留窗口+逐快照评估，每个快照本身是普通工件。
10. **Resident Agent（常驻 agent）**——有些产品本身就是长期在线的 agent 服务（每日助理）：给它产品级身份租约与独立记忆层，其行为同样产生 trace、受预算约束。
11. **Delivery（交付）**——交付不只是把文件放仓库：出库清单（长命凭证边界、渠道推送、责任转移点）+ 发布投影（代码进 git 平台、模型进模型库、视频进媒资库——投影可从真身重建）+ 产品遥测（交付后的回归重放与漂移告警回连工厂）。交付不是出厂即失联。
12. **Human Station（人工工位）**——人在环中是常规生产模式而非异常：任务账本（唯一事实源，杜绝重复派单）、按技能与负载分派、修订语义（人改稿=新工件版本+署名，下游拿修订版）、法定人数会审（含一票否决）、超时的安全缺省是拒绝（宁停勿错放），超时后的升级与处置动作由配方定义；计时按班次日历走。工位消耗"人时预算"。
13. **WorkOrder（订单）**——订单是有一等身份的对象而非一次性请求：带 SLA 字段（时限/优先级）、验收协议（客户金标+抽样权+仲裁流）、变更单（长周期订单中途改需求的正规通道）、部分交付结算、与产线定义版本的不可变绑定。

## 五、内核的机制清单（抽象之外的运转规则）

机制=通用规则引擎，参数全部来自配方。共 13 项（内核预算按此记账）：

| # | 机制 | 干什么（白话） |
|---|---|---|
| 1 | **投放闸** | 在投料口控制生产节奏（工业上叫 CONWIP：保持恒定的在制品数量）：队列快满就放慢投放，而不是暂停生产线——安灯保留给真正的异常 |
| 2 | **CSP 采样状态机** | 任何"从全人工到自动化"的过程都走成熟工业抽样规则（CSP，连续抽样方案）：全检 → 连续合格转比例抽检 → 发现缺陷立即回全检；**拓扑可配可关**；抽检下限大于零，这条规则在优化器权限之外 |
| 3 | **升迁/降级引擎 + 熔断** | 渐进关灯的引擎（微软同款方法论生产实测）：任务从"全 agent"升到"人机混合"再到"全确定"，升迁看证据（成功率/一致性/回归），失败自动降回，连续干净再升；阈值在配方 |
| 4 | **已知答案注入器** | 往任何工作队列按比例埋入已知答案的"考题"：评审员校准、评估器金丝雀、客户标准对齐三处共用这一个机制；考题没按预期被拦下就告警 |
| 5 | **渐放机制** | 任何配置变更上线都先小流量：从 0% 或小比例起步，按评估谓词放量——"新产线首件检验"只是它的一个实例 |
| 6 | **止损规则** | 失败指纹库（配方维护）：连续相同的工具错误=模型已无影响力，立即停止——重试是赌注，不赌 |
| 7 | **副作用网关** | 发邮件/下采购单这类收不回的操作统一走闸门：记录意图→（可配置的撤回窗口）→执行→记回执；防重复靠幂等键（同一个操作永远只生效一次的键），键=订单+工序步骤；每次恢复换新的执行纪元号（fencing），旧纪元的请求一律拒绝——防"旧节点诈尸"；每日对账 |
| 8 | **Meter 计量器** | 供给状态的通用表达式：任何模型来源都可声明自己的额度形状（存量的美元、限时的窗口配额、并发上限，可嵌套可组合取 min/max），路由统一消费"余量"信号——接什么供给是配置，不是架构 |
| 9 | **通用日历** | 班次/假日/时区的通用时间模型；工位计时、SLA 承诺、时间窗放置、容量池都是它的消费者——日历内容是运营者配置 |
| 10 | **调度提示接口** | 订单时限、余量状态、放置偏好都以"提示 provider"的方式喂给调度器——时限转优先级只是默认 provider，可换 |
| 11 | **观测与安灯** | 安灯=工厂的异常呼叫系统（丰田车间的行话：亮灯叫人）。从 trace 持续汇总产线指标（良率/节拍/成本——行业叫法 MES，制造执行系统）、产出瓶颈卡；升级链与超时处置动作由配方定义（默认预案：逐级升级→无人应答暂停产线） |
| 12 | **容量测量** | 只测不策：四类资源的压力测量+反事实口径（记录"若不优化本来会怎样"，绕开某资源多付的钱=它稀缺程度的直接度量，即影子价格），为运营者的采购决策供料 |
| 13 | **JIT 编译器** | 消费 trace 与评估数据，只发射配方修改提案（人批准生效），永不直接干预执行；护栏三件套：审计下限（保留优化器碰不到的随机抽检）、优化集与评估集隔离、升迁须联合单调（人工介入率下降且漏检率不升） |

## 六、一座工厂的完整运转（含"用户一号"实例标注）

以下走查是通用流程；**方括号里标注用户一号（我们自己）的配置如何体现**——注意所有"我们的具体情况"全部落在配置与配方层，内核一处未改。

**第 0 步 · 开厂**。部署内核（部署形态自选：本地/云/混合）；提交运营者配置：接入供给（每个模型来源挂一个计量适配器）**[用户一号：两个订阅窗口额+一家按量 API+本地 GPU 池]**、排班日历 **[白班 8×5]**、商业规则 **[三档交期的 SLA 映射，定价写运营手册由人执行]**；fork 发行配方按需微调。

**第 1 步 · 接单**。订单从下单台或触发器进入 **[仓库出现新 issue 自动派分诊单]**：建立 WorkOrder、签发预算凭证 **[token 走订阅余量优先的计量路由]**、绑定产线定义版本。

**第 2 步 · 生产**。投放闸按配方限流 **[夜间只预置有限队列]**；图引擎按拓扑调度：节点执行（统一 harness 内核，模型调用经网关验预算，工具调用经 broker 进沙箱，外部操作过副作用网关）；产出以带版本键的工件入库；工序间门禁三态判定 **[代码产线：编译/测试的即时反馈+门禁]**。

**第 3 步 · 人在环**（如有）。「需人工」进人工工位：账本派单（技能路由）、班次日历计时、修订产签名工件回灌 **[审稿人改稿=工件 v+1，下游自动用新版]**；注入器按配方埋考题 **[2-5% 金标盲插]**。

**第 4 步 · 交付**。终检双口径（工厂评估+客户验收协议）；出库清单执行；发布投影 **[代码推 git 平台、报告发给客户]**；产品遥测上线。

**第 5 步 · 改善**。观察聚合（从 trace 持续汇总产线指标）：良率、节拍（机器节拍与人工等待分开算）、单位成本（沿工件血缘归集，费率是配置）；JIT 读取数据，向**我们的配方副本**发射优化提案 **[把某工序换小模型]**；CSP 规则+审计下限+升迁引擎把关，人批准生效；某工序人工介入率持续走低且漏检率不升 → 提议关掉那盏灯——提议本身也是安灯事件。

**第 2 年 · 用户二号**（预注册画像）：全 API 供给、7×24 分布式团队、月限额套日限额的嵌套计量（可组合 Meter 表达，无需新机制）、控制面部署在云端——**同一内核，另一份配置**。验收判据：接入时内核 diff 为零。

## 七、技术底座（速览，可跳过）

以下专有名词不展开解释，明细见《选型终局建议_第三轮.md》。内核的机制由 36 个经过三轮对抗验证的开源项目承载：内容寻址存储（zot+cosign+bazel-remote 分层）、不可篡改 trace（OpenTelemetry+签名+rekor 见证+Langfuse 查询层）、模型网关（Bifrost，只验不签）、推理引擎（vLLM）、沙箱（E2B，扩容走同协议的 CubeSandbox）、调度（k3s+Karmada+Kueue）、durable 执行（Temporal/DBOS 二选一，大载荷外置）、观察聚合（ClickHouse）、安灯（Alertmanager+自研状态机+ntfy）、优化（DSPy+GEPA）、产线定义（Git+CUE+Flux）。自研面积为 13 个薄层（图引擎四件、凭证签发、trace 接线、安灯状态机、副作用网关、人工工位、订单对象等），每件都有明确蓝本或宪法依据，且全部先经"全网搜索确认无现成实现"。

## 八、这盘生意（客户、收费、护城河——诚实版）

**卖给谁**：有批量数字生产需求的团队与企业——内容集团（稿件/视频流水线）、软件团队（自动重构/测试/文档）、研究与评测机构（实验与基准流水线）；第一阶段就是我们自己（内部降本+能力验证），第二阶段是兄弟团队，第三阶段是外部运营者（整套底座交付）。

**怎么收钱**：内部阶段按"节省的成本+产出的产能"计价验证；对外阶段底座按部署订阅+支持收费，配方库与适配器集随订阅发行。这部分的完整定价方法论（按合格交付计价、交期分档等）在运营手册层，不在产品内。

**护城河是什么（诚实回答）**：内核所依赖的开源件全部公开、内核本身可被复制——**壁垒不在代码**，在四层：①**配方资产**——默认值与策略是"跑过真实生产"的数据积累，抄不走；②**trace 语料飞轮**——JIT 靠生产数据越用越准，新进入者从零开始；③**运营知识的产品化**——校准/采购/定价方法论沉淀为手册与配方，是知识壁垒；④**抽象设计的先发正确性**——13 抽象的三无关设计一旦被验证，跟随者要么兼容我们的抽象（成为生态）、要么重走我们的弯路。坦率说：在第二个真实运营者出现之前，①②都不成立——这是本产品最大的商业风险，与第九节回音室风险同源。

## 九、拍板点（六项）

**D1 · 产品定位转变**：从"建一座自己的工厂"转为"**造工厂底座产品；我们自己的工厂是用户一号的部署实例与首个验收现场**"。这是本文件一切其他决定的前提。

**D2 · 宪法与纪律**：批准 2.1-2.4（三无关、九条宪法、九条判据、需求进入工序含第零通道与 rule of three）为产品根本法；今后一切设计评审以它为准绳。

**D3 · 四层形态与边界**：批准内核/适配器/配方/运营者四层结构及四条边界规则（JIT 可写边界=本租户配方副本；运营者覆盖默认；适配器只翻译不决策；配方 DSL 受限并同受三无关约束）。

**D4 · 内核基线冻结**：批准 **13 个抽象 + 13 个机制**（第五节编号清单，共 26 件）为内核基线，按件数记账；新增须经第三方评审的完备性论证。

**D5 · 一期范围、资源与选型基线**：一期 = 内核最小闭环 + 用户一号工厂投产。里程碑按波次推进（M1→M5，只讲依赖顺序**不设任何时间估计**——AI 优先开发，节奏由波次完成判据驱动）：M1 存储与身份 → M2 图引擎/trace/沙箱/副作用网关 → M3 评估与人工工位 + 首条产线【eval 产线：既是工厂自验收又产 JIT 语料】→ M4 网关/推理/计量器 + 配方库初版 + 运营者配置面 → M5 观察安灯容量 + JIT 护栏上线；扩展抽象（触发器/通道/常驻/交付遥测）按需排后。**开发语言基线：自研内核全部 Rust**（安全性/性能/编译器反馈；凭证域的 biscuit-auth 与 cedar-policy 本就是 Rust 原生库）；例外仅限生态绑定处——LLM 推理（Python/CUDA 生态）、前端与工作台交互（TS/AI SDK）、JIT 优化器外壳（DSPy/GEPA 为 Python 库，其配方校验器仍用 Rust）；开源组件在语义判据同等时优先选 Rust 实现，语义判据优先于语言偏好（详见《实施方案》语言章节）。**同时批准第七节选型为基线**（允许随 PoC 调整）；其中 durable 执行引擎 Temporal vs DBOS 以 PoC 定夺（判据：订单状态机实现 footprint、断连恢复、审批等待语义、运维半径）。

**D6 · 组织工序**：四级漏斗、否决日志、内核预算、第二运营者预注册画像，成为设计评审的固定流程；老板需求一律走"用户一号配置"通道提交。**附注（需一并批准的显式修订条款）**：rule of three 允许一条放宽通道——某需求第二次出现且已有两个独立实现证据时，可申请"候选机制+证据"提前升格，须经与完备性论证同规格的第三方评审；未获批前仍留在配方层。

## 十、风险与边界（诚实清单）

1. **回音室风险**：产品早期只有用户一号一个真实运营者，抽象正确性缺第二实例校验——这同时是最大的商业风险（第八节：护城河的①②在第二个运营者出现前不成立）。缓解：预注册画像 + 内核 diff 判据；中期寻求第二个真实部署（内部兄弟团队或早期客户）。
2. **配方 DSL 表达力风险**：受限 DSL 可能满足不了某些合法策略，诱发"要求开洞"的压力。缓解：开洞申请走判据 9 完备性评审；rule of three 收集实例后再扩 DSL。
3. **内核预算的节奏代价**：通用机制升格要等第三个场景，可能拖慢紧急的通用需求。缓解：第零通道只覆盖缺陷安全；紧迫且通用的需求走 D6 附注的"候选机制提前升格"通道（评审把关）。
4. **明确不做**（边界）：通用对话式 agent 平台、面向公众的消费级服务、执行物理动作的产线（底盘可为机器人"软在环"开发供数据流与质检，但不管硬件）、为任何单一运营者特化的内核分支。
5. **继承的已知风险**：模型网关开源版单点（预算兜底在凭证层）、沙箱单机起步（扩容路径已备）、评审质量机制未经生产验证（注入器上线首月重点观察）——三项均有登记的缓解与 PoC 闸门。
