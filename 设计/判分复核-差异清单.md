## 四、机理定位（12907，非 judge 解析缺陷）

**关键证据链：**

1. **记录 note 的形状**：results.jsonl 该行 `judge: {"resolved": false}` **没有 f2p 字段**。swev-judge.py 在日志能解析出测试状态时必然输出 f2p_success/f2p_failure（哪怕 0/0）；只有 swebench `get_logs_eval()` 返回 `found=False` 时（日志缺 `>>>>> Start/End Test Output` 标记，或含 `>>>>> Patch Apply Failed / Reset Failed / Tests Errored / Tests Timed Out` bad-code；grading.py:39-72 先查 bad-code、再查标记）才会输出裸 `{"resolved": false}`。⇒ **初判时那份 eval.log 是无标记的截断/失败日志**（第一跑），judge 对它判 false 本身没有错。
2. **现存日志是另一跑的**：现存 eval.log（13:08:56 落盘）L11510/L11575 有完整 Start/End 标记、L11559–11573 共 15/15 PASSED（含 F2P 2 例），对它判分必得 true 且必带 f2p 字段——与记录 note 形状矛盾 ⇒ 它不是产出该记录的那份日志。
3. **同题确有第二跑**：/tmp/bench-fix1-d1-step5/results-void-429storm.jsonl 存有同题另一条完整记录：turns=41、`resolved true, f2p_success 2, f2p_failure 0`；现存 run 目录 harness.db 转录恰为 41 个 assistant 轮、critical.jsonl turn-41 harness.stop @13:07:08——现存产物属于被 429 风暴作废的第二跑。而 results.jsonl 记录 turns=27、wall 336576ms，是第一跑。
4. **覆写原因**：两跑的 run 目录名同为 `runs/swev-astropy__astropy-12907-step-5-a1`（命名只含 task/profile/attempt，无唯一 id），第二跑复用同一目录名静默覆写了第一跑的 eval.log/agent.diff。429 风暴期间同题重复投递（d1-kimi 亦有同模式，见 §五）。

**一句话**：judge 解析器无任何不确定重跑差；缺陷在**run 目录可被同名覆写 + 无标记截断日志被当作模型 reward=false 记账**。第一跑的 eval 疑似被桥接 `timeout 1200` 击杀或容器内 eval 中断（429 风暴时段），日志无测试标记 → 裸 false 入账；而同一补丁第二跑实证可解。

## 六、修复建议（未实施，待厂长裁决）

1. **run 目录唯一化**（根修，af-bench）：run 目录名加入投递唯一 id（时间戳/短 uuid），或覆写前拒绝并归档旧目录——杜绝 12907 式静默覆写。
2. **结果行带产物指纹**：results.jsonl 每行附 eval.log sha256（或 size+mtime）+ turns，离线即可校验记录↔产物联动（今日本可凭 turns 27≠41 当场识破 12907）。
3. **judge 透传 found=False**：swev-judge.py 在 `get_logs_eval` found=False 时输出 `{"resolved": false, "log_parsed": false}`，让"eval 未产出可解析结果"与"测试真失败"在 verifier_note 可区分；af-bench 可将前者记 `status=eval_incomplete` 而非静默 reward=false。
4. **桥接超时语义**：`timeout 1200` 击杀（exit 124）时当前静默产出无标记日志→false。建议 eval 仅重跑一次（非 agent 重试）或显式记 eval_timeout。
