## 一、一句话结论

**先不换现役模型本身；把现役的配置和 harness 的两个缺口先修掉（零下载、当周可完成），同时把 Qwen3.6-35B-A3B 作为"并行臂"打榜，而不是作为替换件。** 理由三条：

1. **现役的瓶颈是配置不是模型**：`/data/models/Modelfile` 只有一行 `FROM`（任务书材料，本轮 anolis 一手核实），`~/.config/ollama/env` 只有 `OLLAMA_NUM_PARALLEL=2`（同上），所以 ollama 以 **2 slot × 262,144 ctx** 装载、KV cache 占 **49,152 MiB**、两卡 **94–95% 满**（【本会话读档案】`notes/our-workload.md:18,191`）；而 7,974 次真实调用的上下文深度 **p99 只有 28,776 token、max 63,157**（`notes/our-workload.md:74`）。**262K 是纯浪费，32K 才是生产档**。
2. **135.7 tok/s 不是我们的产量口径**。它是 num_ctx=8192 + 短 prompt 的微基准；真实深度 6–16K 上现役只有 **38.0–39.2 tok/s**，整题有效吐字速率中位只有 **16.4 tok/s**（【本会话读档案】`notes/our-workload.md:354,361`）。拿 135.7 当分母，会把所有候选都比得比实际慢。
3. **核心假设只成立一半**（这一条直接回答任务书点名的假设）：
   - ✅「MoE 比同体量稠密快，在 V100 上是真事实」——同卡同日 Qwen3.6-35B-A3B **98.8** vs Qwen3.6-27B **32.9 tok/s = 3.0×**（`notes/v100-speed-data.md:49,62`）；llama.cpp #27366 在 V100 上实测稠密 Qwen3.8-27B **tg128 = 33.25** vs 我们现役 135.7 ≈ **1/4.1**（`notes/engines-volta.md:160,197`）。
   - ❌「80B-A3B 会比现役更快」——**不成立**。80B-A3B 与现役都是 3B 激活，每 token 读取字节同量级；Coder-Next 更实测到 **每 token 2.9–3.2 GB vs 现役 1.92 GB**（任务书材料 verify-4 的 HTTP Range 逐张量求和），且 512 路专家的散点读比现役 128 路更吃亏。第三方同栈实测 AA：**Coder-Next 97 t/s vs 现役 158 t/s**（任务书材料 verify-7）。
   - ✅「45–50GB 的 80B 级 Q4 能塞进 64GB」——**成立**，且分母要修正：ollama 官方 `qwen3-coder-next:q4_K_M` blob 实测 **51,741,599,936 B = 48.19 GiB**（【本会话读档案】`notes/our-workload.md:294-296`；任务书材料 verify-6 用 registry manifest 独立复核同一数字）。
   - ✅「放不下时的 `--n-cpu-moe`」——**可用但更慢的降级手段，不是提速手段**。同卡实测：现役 30B-A3B 仅 8 层专家走 CPU 就掉到 **35.7 tok/s**（同卡全 GPU 110，掉 68%）；235B 全专家走 CPU 只有 **2.13–4.18 tok/s**（【本会话读档案】`notes/v100-speed-data.md:188`）。

**读出来的三条硬结论**：

1. **11/62 的 D1 题连补丁都没产出（no_patch）+ 10 题打满轮数 = 34% 的失败与解题能力无关**（`notes/our-workload.md:373`）。前期结论"真正的成本瓶颈是模型不努力"被这批数据再次支持——**任何换模型的收益都要先用它自己的完成度纪律去争，不能靠分数榜推定**。
2. **32K 是生产必需的 ctx 下限**（覆盖 p99 28,776），**64K 是保险档**（覆盖实测 max 63,157）。
3. **600s HTTP 读超时 ÷ 40 轮 = 单轮只有 15s 预算**，而长上下文下单轮固定注意力开销就有 1.6–1.7 s（`notes/our-workload.md:162`）——这正是 `max_tokens` 缺失会直接变成"白烧 GPU"的原因。

## 四、逐个重点候选展开

### 4.1 Qwen3.6-35B-A3B —— 唯一值得作为"并行臂"打榜的候选

**它强在哪（证据是谁给的）**
- **最硬的一条是第三方同口径**：Artificial Analysis 2026-10-21 实测（`intelligenceIndexIsEstimated=false`，非估算）：**TB-Hard 34.85% vs 现役 15.15%，2.30×，两个都是实测**（任务书材料 verify-3/verify-8）。TB-Hard 是我们四个题型（TB 是其中之一）里最干净的第三方可比项。
- 同一张表：II 18.23（thinking）/ 15.23（non-reasoning）vs 现役 9.59 —— 但**现役的 9.59 是模型化估算**（`IsEstimated=true`、`microevalsEnabled=false`、AA 已标 deprecated），所以 II 这一项是"实测 vs 估算"，**不能当 2× 的干净结论**。TB2.1 44.94% 也只有 35B-A3B 一侧有值。
- **有一个确定的缓解手段**：AA 的 non-reasoning 变体 **reasoning token = 0**，II 只掉 3.0、TB2.1 只掉 3.4pt（任务书材料 verify-3）。配合 verify-8 证实的 `reasoning_effort:"none"` 能关思考 ⇒ token 膨胀这个最大风险有了定量对策。
- ⚠️ **官方 SWE-V 73.4 / TB2.0 51.5 必须降级为"待验假设"**：官方 README 脚注写明用 "Internal agent scaffold"，且"we correct some problematic tasks in the public set of SWE-bench Pro"；49.5 高于 SWE-Pro 公开榜第一名 43.72 ⇒ 非公开榜口径。SWE-bench 官方榜 323 条记录里 **0 条**本模型（verify-3 抓 `leaderboard-data` 2.36 MB 解析）。

**在 V100 上怎么跑**
```
# 0) 磁盘：/data 现剩 17G、94% 满；先回收（实测 docker system df → images 可回收 131.2GB，任务书材料）
ssh anolis 'docker system df; df -h /data'

# 1) 建档（模板不动——现役 Modelfile 无 TEMPLATE 行，模板走 GGUF 内嵌）
ssh anolis 'cat > /data/models/Modelfile-35b <<EOF
FROM qwen3.6:35b
PARAMETER num_ctx 32768
PARAMETER temperature 0.0
PARAMETER top_p 1.0
EOF
ollama create qwen3.6-35b-local -f /data/models/Modelfile-35b'
```

**代价是什么**
- **每 token 墙钟大概率变差 1.2–1.9×**：第三方同口径微基准 98.8（ctx16K/thinking ON）→ 折算 ~89 vs 现役 135.7。但**不能用 135.7 判它更慢**：现役的真实深度口径只有 38–40 t/s，且 35B-A3B 的 **KV 只有 20 KiB/token vs 现役 96 KiB/token（省 4.8×）、全注意力层只有 10 层 vs 现役 48 层**（任务书材料 verify-3/verify-8 的按 GGUF 元数据复算）⇒ 同深度下注意力与 KV 成本显著更低。**两个口径方向相反，必须靠我们自己的 A/B 定案。**
- 0.84 GiB 视觉塔在纯文本负载下关不掉（是 VLM）。
- 默认 thinking ON + presence_penalty 1.5/top_k 20，不关会 token 爆炸。

**什么条件下值得用**：冒烟六关全过（见 §6.3），且在 af-bench 上 **D1 解题率 ≥ 调参后基线 +3pt、单题墙钟中位 ≤ 基线 ×1.2、10 轮工具调用零解析失败/零崩溃/零重复循环**。

### 4.2 North-Mini-Code-1.0 —— 低风险替补（不是替代）

**强在哪**：**结构性优势**——cohere2moe 是纯 MoE + 滑窗交错注意力，**没有 GDN/SSM/Mamba**，因此完全避开 #29255 / #27623 / #23577 / #19794 这一整类 sm_70 混合线性注意力风险。**可加载性已在本机实证**：verify-2 用零张量合成 GGUF 走完 cohere2moe 架构分派 → hparam → SWA pattern 校验 → tokenizer，对照 bogusarchxyz 立即报 unknown architecture（任务书材料）。

**证据**：AA 实测 TB-Hard 31.06% vs 现役 15.15%（**2.05×，实测对实测**，verify-2）；TB2.1 35.58%（低于 35B-A3B 的 44.94%）；**τ²-bench 37.43% vs 现役 34.50% = 只 +8.5%**；II 9.91（实测）vs 现役 9.59（估算）。SWE-V 与 InjecAgent **零第三方证据**。

**在 V100 上怎么跑**：`ollama pull north-mini-code-1.0`（q4_K_M 18,593,955,136 B）→ Modelfile `PARAMETER num_ctx 32768` → `CUDA_VISIBLE_DEVICES=0/1` 单卡独立实例。**必须先做真实 tool-call 往返**：它用 Cohere 自有 `<|START_ACTION|>[{"tool_call_id","tool_name","parameters"}]<|END_ACTION|>` 格式（chat_template.jinja 实读），llama.cpp 侧有 `common_chat_params_init_cohere2moe` parser（PR #24615，在 ollama 的 `libllama-common.so` 里），但**我们的 af-bench 自己做 JSON 抽取，仍需按 §1.8 三处接入点加 profile**。

**代价**：每 token 权重流量 2.2775 vs 现役 1.9196 GB/token = 1.186× ⇒ 微基准口径墙钟变差约 19%；但它 49 层里只有 13 层是全注意力、32K ctx 的 KV 只要 1.17 GB，在我们的 6–32K 真实深度上注意力成本远低于现役。公开 GGUF 的 442 个张量里 nextn/MTP 为 0 ⇒ **投机解码不可用，吞吐账里不能计入**。

### 4.3 Qwen3-Coder-Next 80B-A3B —— 前期"首选"，本轮推翻

前期结论是"本地最强可行选项"。本轮调研把它降到"不上"，三条各自独立成立的理由：

1. **速度明确变坏**：逐张量精确字节（HTTP Range 拉 GGUF 头按 ggml block 尺寸求和）：UD-Q3_K_XL **2.899 GB/token**、UD-Q4_K_XL **3.234** vs 现役 **1.920** = **1.5–1.7×**（任务书材料 verify-4）。独立佐证：AA 同栈 **97 t/s vs 现役 158 t/s**（verify-7）；llama.cpp #18102（open）在 Blackwell 上也只有 45–55 t/s，作者写"pre-blackwell cards get ~38–40 t/s"。
2. **唯一同口径第三方评测里现役胜出**：AA Intelligence Index **Coder-Next 9 分 < 现役 10 分**（verify-7）。而且质量侧**零第三方 agentic 复现**：SWE-bench 官方榜 0 命中、TB 榜 0 条目、aider 榜 0 命中；SWE-V 70.6 是官方自报，用 SWE-Agent，而现役的 51.6 用 OpenHands 500 轮——**两把尺子**（verify-6 明确指出这条口径警告比原判断更严重）。
3. **sm_70 专属坑最密集，而且正中我们的使用形态**：#28185（2× 卡 tensor-split 下"MoE 专家几乎不被再平衡" + 增长型多轮输出退化到 14MB/15 分钟，**OPEN**）、#29255（layer-split + 前缀复用崩溃，**OPEN**，原话"long agent sessions…heavy prefix reuse"每天崩约 6 次）、#19794（hybrid 前缀缓存反复作废 ⇒ 每轮全量重 prefill）、#28241（`-cmoe` 在 sm_75 恰 94 token 必崩）。
4. **TB 维度倒退**：自报 TB2.0 34.2/36.2 vs 35B-A3B 的 51.5（verify-3/verify-7 独立指出这个方向），而 TB 是我们四个题型之一。

**一条需要澄清的技术点**：前期"输出损坏"这一条，在 ollama 0.40.6 pin 的 llama.cpp **b11669（v0.7.0, 2026-10-15）** 上对 Coder-Next 已消除——#19305 "Poor Outputs" 已由 #19324 "correct vectorized key_gdiff"（2026-02-04）修复（任务书材料 verify-6）。所以 Coder-Next 剩下的不是"输出损坏"，而是上面第 3 条的稳定性/速度问题。

### 4.4 `--n-cpu-moe` 的正面核查（任务书点名项）

**结论：可行，但它是"可用而更慢"的降级手段，不是提速手段；64 GiB 装得下就不要用。**

- **实测代价（不是数量级，是 1–2 倍）**：carteakey 在 4070 上 N_CPU_MOE=40 → tg128 40.6，全专家上 CPU → 33.7，`--fit`+q8_0 KV → 39.93（任务书材料 verify-5）。同卡 V100 上更狠：现役 30B-A3B **仅 8 层**专家走 CPU 就掉到 35.7 t/s vs 全 GPU 110（**掉 68%**）；235B 全专家走 CPU 只有 2.13–4.18 t/s（【本会话读档案】`notes/v100-speed-data.md:188`）。
- **我们这台机的天花板**：Coder-Next 专家走 PCIe Gen3 x16（12–14 GB/s）约 58–77 ms/token ⇒ **13–17 t/s**，比现役真实深度的 38–40 t/s 还慢 2.4×（`notes/our-workload.md:341`）。
- **有专属崩溃向量**：#26609（35B-A3B 部分专家卸载第二个请求必崩 illegal memory access）、#28241（Coder-Next + `-cmoe` 在 sm_75 必崩）、#25582（CUDA MoE 专家路径输出静默损坏）。
- **暴露方式**：ollama 没有 `--n-cpu-moe` 的 CLI，但 `llm/llama_server.go:476 cmd.Env = os.Environ()` 让 llama-server 继承环境变量，而 llama.cpp 的开关都带 `set_env("LLAMA_ARG_*")` ⇒ 可以用 `LLAMA_ARG_N_CPU_MOE` 打开（任务书材料 verify-5，**源码级结论，未实测**）。

## 七、可执行的评测方案

### 7.1 题集与对照

- **主对照题集**：D1 全量（62 题，fix1 同代题集）+ Terminal-Bench 短任务子集。**不复用 API 臂的结果做对照**——`notes/our-workload.md:232` 明确 fix1 各臂分母不同（infra 题被剔出分母），跨臂比"通过数"会误导，必须比通过率。
- **版本隔离纪律**：`notes/our-workload.md:47,232`——现有 122 题结果行 `scaffold=v2` 且**无 `judge_mode` 字段**（POC-1 判分口径切换前），与 fix2/fix3 不可混算；P0 改了 max_tokens/reasoning_effort 后**必须 bump 结果代号**（建议 `fix4`）。
- **防抄答案**：SWE-V 题集必须**断网 + 洗 `.git`**（SWE-bench Multilingual 上 72.1% 的任务是被漏洞帮着解出来的，`notes/eval-landscape.md` §1.3）。

### 7.2 记录哪些指标（每题一行）

| 指标 | 来源字段 | 为什么记 |
|---|---|---|
| **解题率** | `reward != null` 的通过率 | 主指标 |
| **单题墙钟中位/p90** | `agent_wall_ms` | 次指标；现役 D1 中位 302s / p90 986s 作参照 |
| **轮数分布** | `turns` | 打满轮数 = 纪律失败，不是能力失败 |
| **输出 token 中位** | `tokens.output` | 现役 5,756 作参照；35B-A3B 若不关思考会远超 |
| **有效吐字速率** | `tokens.output ÷ agent_wall_ms` | 现役 16.4 t/s 作参照 |
| **工具调用成功率** | 新增：解析失败次数 / 总 tool_call 数 | 直接命中"跨轮崩"风险 |
| **失败模式分布** | `status`（completed/max_turns/run_failed）+ `gate`（ok/no_patch/test_edit） | 现役 D1 是 `no_patch 11 / max_turns 10 / test_edit 5`，**这是最可改进的部分** |
| **归因失败数** | 400「2 个以上连续 assistant」等协议级失败单列 | P0-5 之后应有独立计数 |
| **HTTP 重试数** | `http_retries` | 现役为 0；35B-A3B 上去后若 >0 说明 max_tokens 还没修对 |
| **上下文深度 p99** | 从 ollama 日志 `n_tokens = N` 解析（现役 p99 28,776） | 验证 32K ctx 够不够用 |

### 7.3 判定阈值（提前定死，避免自欺）

**上量门槛（35B-A3B）**——四条同时满足：
1. af-bench D1 解题率 **≥ 调参后基线 + 3pt**；
2. 单题墙钟中位 **≤ 基线 × 1.2**；
3. 10 轮工具调用 **零解析失败、零崩溃、零重复循环**；
4. 归因失败数（400 协议级）= 0。

任一不满足即淘汰回现役。

**为什么是 +3pt 而不是 +15pt**：`notes/our-workload.md:352-373` 的 122 题样本量下，D1 62 题的通过率标准误约 6pt；+3pt 是"值得留"的门槛，+15pt 是早期 Coder-Next 提案里的门槛（`notes/v100-speed-data.md:320`），按我们的题集规模那是不可达的。

**结果代号纪律**：P0/P1 的结果**不得与 fix1/fix2/fix3 混算**；换臂、换 ctx 档、改 harness 旋钮，三个变量每次只动一个。
